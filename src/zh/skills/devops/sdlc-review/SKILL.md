# SDLC 审核技能

该技能可独立验证从看板执行流程流转至审核环节的任务，随后决定是否批准、要求修改或上报问题。它仅对交付成果及其相关证据进行审核，不会替代执行者完成实际工作。

## 适用场景

当同时满足以下条件时，可使用此技能：

- 分配器因您负责处理来自“审核”环节的任务而指派您；
- 执行者已提交需要审核的任务流转请求；
- 该任务在完成前需要独立的审核结论。

请勿将其用于独立的下游审核卡片。下游卡片属于常规的实施任务，仅带有以审核为导向的规范，并会按照自身的生命周期完成流程。

## 先决条件

- 拥有包含当前任务及执行流程标识符的看板工作上下文；
- 必备的看板工具：`kanban_show`、`kanban_comment`、`kanban_complete`、`kanban_request_changes` 和 `kanban_block`；
- 若交付成果为代码，还需具备通过 `read_file`、`search_files` 和 `terminal` 访问工作空间的权限；
- 必须能够通过 `kanban_show` 查看该任务的原始规范、验收标准、任务流转摘要以及之前的执行历史记录。

## 使用方法

此技能会由审核分配器自动加载。在查看文件或确定审核结论之前，应首先调用 `kanban_show` 命令。

1. 阅读任务规范以及最新的 `review_requested` 状态信息。  
2. 检查实际交付成果并执行相应的验证测试。  
3. 仅可选择一种判定结果：通过、要求修改或升级处理。  
4. 在终端的看板状态转换记录中留存具体证据。  

## 快速参考表

| 判定结果 | 适用场景 | 最终操作 |
|---|---|---|
| 通过 | 满足验收标准且验证测试通过 | 设置为 `kanban_complete` 状态 |
| 要求修改 | 仍存在可修复的实现缺陷 | 先添加评论 `kanban_comment`，再转为 `kanban_request_changes` 状态 |
| 升级处理 | 需要人工决策或外部资源支持 | 将状态设为 `kanban_block` |

当选择“要求修改”时，任务会退回给最初的执行者。若该执行者再次请求审核但未指定审核人，系统会依据已记录的审核人信息，将重新审核的任务派发给同一位审核者。  

## 审核视角  

无需每次都采用相同的检查方式，可在每轮审核中更换不同的审视角度。不同的审核视角能发现不同类型的缺陷：初次通读代码可发现设计与正确性方面的问题，这些往往会被执行者的描述所掩盖；运行测试可找出那些无法复现的异常情况；而严格的契约审计则有助于发现隐性范围偏差。在第三轮审核时重复使用第一轮的审核方式，大多只是再次发现第一轮已经找出的问题而已。

你可以通过任务记录已提供的历史信息来确定当前轮次：统计工作上下文“该任务的先前尝试”部分中的 `changes_requested` 记录数量（在 `kanban_show` 中也会显示为之前的运行记录）。当前审核轮次即为该数字加一。因此，第一轮的 `changes_requested` 计数为零；第二轮为 one，以此类推。

| 轮次 | 审核视角 | 应用方式 |
|---|---|---|
| 1 | 工件本身 | 在查看实施者总结之前，先直接阅读代码差异或交付成果。独立形成判断，再将其与交接说明进行对比，并逐一排查所有不一致之处。 |
| 2 | 执行过程 | 查看相关代码并通过 `terminal` 实际运行它：自行进行构建、测试并验证所描述的功能行为。通过实际操作来核实每一项交接内容，而非仅重新阅读工件文件。 |
| 3+ | 合同规范 | 重新阅读原始任务描述和验收标准，然后严格依据这些标准对交付成果进行审核。同时确认在之前所有 `kanban_request_changes` 轮次中提出的各项要求都已得到落实。 |

“流程”部分中规定的基础职责在每一轮都依然适用；不同审核视角则决定了你应优先关注并重点核查哪些方面。

### 针对临时性审核任务的视角调整方案

在看板审查流程之外，同样适用这一原则。当通过 `delegate_task` 分配多名并行审查人员时，应为每位审查人员提供不同的任务说明——一份仅包含差异点的说明、一份包含完整上下文的说明、一份包含检查与运行要求的说明——而非完全相同的说明。相同的说明会导致一致的审查结果和重复的问题发现；而不同的说明则能在相同的审查投入下覆盖更多类型的缺陷。

## 操作步骤

### 1. 基于持久化的任务记录进行了解

调用 `kanban_show` 并获取以下信息：

- 原始的任务内容及验收标准；
- 最新的实现总结与结构化元数据；
- 被修改的文件、提交标识以及测试证据；
- 之前各次运行中的评论与决策记录；
- 以往审查轮次中发现的问题。

应将任务交接视为需要验证的内容，而非工作已正确的证明。

### 2. 对比预期行为与实际实现行为

将每一项验收标准对应到具体的实现结果或输出证据上。在决定是否进行更深入的检查之前，先记录下遗漏的内容、语义上的变化以及无关的范围问题。

针对代码类工作：

1. 使用 `read_file` 和 `search_files` 功能来查看发生变更的路径及其调用方。  
2. 使用 `terminal` 功能查看代码差异，并运行项目现有的相关测试、代码检查工具、类型检查或构建命令。  
3. 在条件允许的情况下，实际执行报告中的失败路径以及至少一条常规控制路径。  
4. 检查与此次变更相关的错误处理机制、边界情况、并发限制、数据完整性、安全边界以及跨平台行为表现。  
5. 确保测试能够验证程序的实际行为，而不仅仅是捕获源代码或常量的静态状态。  

对于非代码类工作：  
1. 需全面审查交付成果，而不仅仅是其概要内容。  
2. 检查内容的正确性、完整性、格式规范以及来源可靠性。  
3. 若引用的网址或外部信息会影响最终判定结果，需使用相应的本地工具进行验证。  

### 3. 选择一种判定结果  

#### 批准  

仅当所有验收标准均得到满足且证据充分时才予以批准。操作方式：

```text
kanban_complete(
    summary="Reviewed and approved. <what was verified>",
    metadata={"review_outcome": "approved", "reviewer_checks": [...]}
)
```

请列出所有已通过的检测项，以及那些不会妨碍任务被接受的有限制性注意事项。

#### 提出修改请求

此功能适用于那些具体且可修复的缺陷。首先需记录下可行的发现结果：

```text
kanban_comment(
    task_id="<current-task-id>",
    body="Changes requested:\n1. <file or artifact + defect>\n2. <required correction>",
)
```

然后将同一任务反馈给其执行者：

```text
kanban_request_changes(
    reason="<concise summary of the required corrections>"
)
```

请说明缺陷的当前状态、重现方式、为何不符合任务要求，以及达到何种最低标准才能解决该问题。此流程不采用阻碍因素重复计数机制。

#### 提级处理

仅当审核人员与实现人员无法在没有人工决策或外部前置条件的情况下解决问题时，才可使用提级处理功能：

```text
kanban_block(
    reason="escalation: <decision or prerequisite required>"
)
```

说明被阻塞的决策原因以及继续推进所需的最少信息。

### 4. 维护职责分离

在担任审核者时不得直接修改实现代码。应提出修改要求，让实现者生成下一个候选版本；然后在后续的审核中独立验证该候选版本。

## 常见误区

- **流于形式：** 简单的交接总结并不能作为独立的证据。
- **审核者代劳实现：** 直接修改交付物会掩盖责任归属，削弱再次审核的边界。
- **描述模糊：** “需要改进”这样的表述无法为实施者提供可复现的修正目标。
- **仅因风格问题阻塞：** 若功能表现和代码库标准均已符合要求，则不应因细微的风格问题要求修改。
- **跳过前期审核环节：** 再次审核必须同时确认所要求的修改内容以及之前已通过功能的稳定性。
- **将普通返工也用阻塞功能处理：** 可修复的缺陷应记录在`kanban_request_changes`中；仅将真正的外部障碍或人为决策用`kanban_block`标记。
- **无依据便通过审核：** 每份审批总结都必须明确列出实际检查过的项或成果。

## 验证

在提交最终判定之前，务必确认：

- [ ] 已读取当前任务的相关信息并调用了 `kanban_show` 命令。  
- [ ] 每项验收标准均已对应到相应的证据。  
- [ ] 实际交付成果已经过检查。  
- [ ] 已执行了相关的专项检测；若无法执行，则记录了明确的理由。  
- [ ] 在重新审核时，之前要求过的变更已再次进行测试。  
- [ ] 已考虑了无关的回归问题及范围变更。  
- [ ] 最终判定仅使用了一个终端操作命令。  
- [ ] 摘要中包含了具体且非机密的证据。  
- [ ] 审核人员未对任何实现文件进行过修改。
