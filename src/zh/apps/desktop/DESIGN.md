# 桌面设计系统

本文档规定了 Electron 桌面应用（`apps/desktop`）的规范。在添加任何组件、覆盖层或样式之前，请先阅读本内容。核心原则为：**一个功能对应一个来源，优先使用符号而非硬编码值，采用扁平结构而非嵌套结构**。若你需要使用原始颜色、一次性阴影、定制按钮，或是为控件硬编码 `px-*` 值——请立即停止，因为系统早已提供了相应的基础元素。

本文件定义了视觉呈现与交互规则。有关架构、状态管理、解析机制、传输方式及测试规范，请参阅 [`AGENTS.md`](./AGENTS.md)。

本文档包含两类内容，其维护方式各不相同：

- **设计原则**（如扁平性、意图性、反馈机制、动画效果、取消操作等）是长期不变的。无论组件如何更替，这些原则始终有效。
- **命名规范**（如符号、`Button` 的不同变体、基础元素名称等）代表了设计系统当前的 API 接口。这类内容需与代码同步维护：一旦修改了某个基础元素、符号或变体，必须在同一份代码修改中更新此处的对应条目——若文件中的名称过时，就会像类型过时一样引发问题。

当规则与代码出现冲突时，应修正错误的部分，而非在调用处临时创建特殊处理方案。

## 设计原则

1. **扁平结构，避免嵌套**。不得使用卡片套卡片的布局，面板内也不允许有分隔边框。应通过空白区域和细边框进行分组，绝不能使用多层圆角嵌套结构。
2. **浮动面板采用无边框凸起效果**。覆盖层应通过 `shadow-nous` 和 `--stroke-nous` 细边框实现悬浮效果，而非厚边框框定。面板内的结构可偶尔使用符号形式的细边框。
3. **一个功能对应一个基础元素**。一个 `Button`、一组控件变体、一个 `SearchField`、一个 `Loader`、一个 `ErrorState`——应直接使用这些标准元素，避免自行创建新元素。
4. **优先使用符号，而非硬编码值**。在组件中应引用 CSS 变量（如 `--ui-*`、`--shadow-nous`、`--theme-*`），严禁直接使用十六进制颜色值或临时指定的 rgba 值。
5. **样式定义在基础元素中**。各变体及尺寸类型会自行决定内边距、圆角大小、颜色及边框样式。调用方只需传递 `variant`/`size` 参数，无需通过 `className` 覆盖来重新指定这些属性。
6. **先体现意图，再实现自动化**。应首先展示有用的操作和预览内容，但不得仅因工具生成了某些结果就自动打开新面板、切换焦点或进行导航。
7. **即时反馈**。直接操作应首先更新界面显示。网络请求或磁盘持久化操作随后再进行同步处理，若失败则需明显地撤销之前的更改。

## 信息架构

- **聊天界面是核心区域**。对话记录和输入框始终处于主导地位；工具、预览内容、文件、审核功能以及终端窗口则用于补充对话流程。
- **页面是长期存在的目标界面**。聊天、技能应用、消息功能以及文档管理等功能都应保留在主界面框架内。不得将某个独立的产品功能隐藏在无关的页面中。
- **路由覆盖层用于处理短期任务**。设置选项、命令中心、定时任务、用户配置、智能体列表以及星图等功能均以 `OverlayView` 卡片形式呈现，关闭后会返回到之前的界面。模型/会话选择器及对话框则叠加在当前界面之上，不属于导航栈的一部分。
- **面板用于承载当前工作内容**。预览窗口、文件管理、审核功能以及终端窗口都应与当前任务保持关联。即使暂时隐藏这些面板或切换聊天界面，只要底层工具仍需保持状态，这些面板的状态也应保留。
- **一个操作对应一个统一处理方式**。某个命令可能同时提供键盘快捷键、调色板选项及可视化操作入口，但它们都应触发相同的操作并产生一致的状态。不得为不同的操作入口设计不同的行为逻辑。
- **项目拥有独立的工作目录**。建议通过侧边栏的“项目”功能来管理本地文件夹和工作树，无需再引入针对会话或右侧边栏的独立文件夹选择流程。

导航系统必须保持上下文一致性。后台会话结束、工具处理结果返回或项目刷新时，虽然可能会更新徽章和缓存数据，但绝不能替换当前显示的对话内容或抢占焦点。

## 界面与凸起效果

浮动面板（基础类型为 `Dialog`）、路由覆盖层、启动/安装/更新界面、模型选择器、引导界面、提示框以及通知等元素均采用以下设计方式：

```
shadow-nous           /* downward-weighted, layered contact→ambient falloff */
border-(--stroke-nous) /* currentColor hairline, theme-adaptive */
```

这两者均为 `src/styles.css` 中的 CSS 变量——只需在一处进行调整，所有组件都会自动继承该设置。  
请勿为每个叠加层单独添加 `shadow-[…]` 或 `border-(--ui-stroke-secondary)` 等一次性样式；若需改变层级效果，应直接修改对应的变量值。

菜单与弹出框会使用统一的 `shadow-md` + `--ui-stroke-secondary` 样式规则。可拖动的控件则可使用带符号的虚线目标及局部模糊效果。这些均为语义化的表面样式类，而非允许在调用处自行创建阴影或边框样式的许可。

## 轨迹与颜色变量

| 变量名 | 用途 |
| --- | --- |
| `--ui-stroke-primary…quaternary` | 线条宽度，强度从强到弱排列 |
| `--ui-stroke-tertiary` | 面板内分隔线及列表细线的默认样式 |
| `--stroke-nous` | 叠加层的细线样式（与 `shadow-nous` 搭配使用） |
| `--ui-text-primary / -secondary / -tertiary` | 文本层级颜色 |
| `--ui-bg-quaternary` | 软填充背景色（用于次要按钮） |
| `--chrome-action-hover` | 静态控件悬停时的填充色 |
| `--theme-primary`, `--ui-accent` | 品牌色/强调色 |

切勿直接硬编码 `border-gray-*`、`bg-white`、`text-black` 等值。`BrandMark` 中的白色背景块是唯一被允许使用的固定值（因为品牌标识需要固定的背景）。

## 按钮——单一组件

所有按钮的实现均来自 `src/components/ui/button.tsx`。只需选择 `variant`（样式变体）与 `size`（尺寸），**不得**传递 `h-*`、`px-*`、`py-*` 或图标尺寸相关的覆盖值。

**样式变体：** `default`（主色款）、`destructive`、`secondary`（软填充款——默认的非主色外观）、`outline`（透明背景加 1px 内凹圆环，无填充与阴影）、`ghost`、`link`、`text`（无边框的行内控件——“取消”、“清除”）、`textStrong`（加粗下划线的行内控件——“更改”、“打开日志”）。

**尺寸：** `default`、`xs`、`sm`、`lg`、`inline`（紧贴左侧，无边框——适用于嵌入在标题或句子中的按钮；可替代 `h-auto px-0 py-0`）、`micro`（用于状态栏/表格底部），以及图标系列 `icon` / `icon-xs` / `icon-sm` / `icon-lg` / `icon-titlebar`。

**仅包含图标的按钮必须配有工具提示。** 所有带有 `icon*` 尺寸的按钮均无可见文本标签，因此必须将其包裹在 `<Tip label={...}>` 中，并提供描述性标签（需与按钮的 `aria-label` 一致）。切勿使用 HTML 原生的 `title=` 属性——因为它没有样式、触发延迟较高（系统默认约 500ms），且视觉效果与经过主题设计的 `Tip` 不一致。若仍有按钮或 `<Button>` 元素使用 `title=`，则对应的检测测试（`src/components/ui/__tests__/no-native-title.test.ts`）将会失败。

**工具提示中可包含快捷键提示。** 当某个按钮对应可重新绑定的热键时，可使用 `<TipKeybindLabel actionId="..." />` 作为工具提示的标签——该组件会自动读取国际化标签以及存储中的当前快捷键组合，因此当用户重新绑定快捷键时，提示内容仍会保持最新。仅当工具提示的内容依赖于上下文时（例如根据状态显示“显示”/“隐藏”），才需传递 `text={...}` 参数。切勿在组件中直接硬编码快捷键组合，而应始终通过 `useKeybindHint` 或 `TipKeybindLabel` 从 `$bindings` 存储中读取。

注意事项：  
- 文本按钮为正方形形状（无圆角），尺寸由内边距与行高决定（无固定高度）。仅有图标按钮会采用统一的 4px 圆角。  
- SVG 图标会继承 `size-3.5` 的尺寸（在 `xs` 尺寸下为 `size-3`），无需重新设置图标大小。  
- 当按钮需要以链接或 Slot 的形式渲染时，可使用 `asChild` 进行多态处理。

## 表单控件

- **`controlVariants`**（位于 `src/components/ui/control.ts`）是 `Input`、`Textarea`、`SelectTrigger` 等控件的通用样式基础。新的文本输入控件均基于此构建。  
- **`SearchField`**——无边框，聚焦时显示下划线，宽度自动适应。这是唯一的搜索输入框。请勿为其创建带边框的搜索栏，也无需将其包裹在带边框的背景块中。列表为空时会隐藏该搜索框。  
- **`SegmentedControl`**——用于处理少量互斥选项的场景（如颜色模式、工具调用显示方式、使用周期等），可替代传统的单选按钮组或药丸状选项行。  
- **`Switch`**（尺寸为 `xs`）——仅包含基础样式及 `aria-label` 属性，无带边框的文本包裹层。

## 布局

- **内边距：** 使用 `PAGE_INSET_X`（位于 `src/app/layout-constants.ts`）设置页面两侧的内边距；使用 `PAGE_INSET_NEG_X` 可将子元素推向边缘。请勿在页面中直接硬编码 `px-6`/`px-8` 等值。  
- **主内容/详情叠加层：** 采用 `OverlaySplitLayout` 结合 `OverlaySidebar` / `OverlayMain` 的结构。任务调度、用户资料等功能均基于此布局实现，无需重新构建标题栏外壳。  
- **行结构：** 使用 `ListRow`（定义于 `settings/primitives.tsx`）来组织标签/描述/操作等行内容。这些行为水平排列、紧贴左侧，且不会因每行单独缩进而影响顶部标题的对齐。  
- **除非列表确实需要分隔线，否则不应在行之间添加分隔线**；优先使用适当间距即可。若确实需要分隔线，只需使用一条 `--ui-stroke-tertiary` 颜色的细线。

## 反馈及空状态/错误状态/加载状态

- **加载中：** 使用 `Loader` 组件（位于 `src/components/ui/loader.tsx`），通过动画化的数学曲线或 ASCII 图形（长时间操作时使用 `lemniscate-bloom` 动画）来展示加载状态。切勿直接显示“Loading…”这样的文字。  
- **错误状态：** 使用 `ErrorState` 组件搭配标准的 `ErrorIcon`（无背景色块），即可统一呈现 React 边界错误、对话框内错误以及启动失败提示等不同类型的错误信息。可通过传递标题与描述节点，让 Radix 的 `DialogTitle`/`Description` 组件能够正常渲染，从而提升无障碍体验。  
- **日志显示：** 使用 `LogView` 组件——无背景色，仅有细线边框，内边距紧凑，字体为等宽字体。所有需要展示原始日志的地方均应使用此组件。  
- **空状态：** 空白的页面内容区域可使用 `EmptyState` 组件；而带有图标与操作按钮的叠加层主内容/详情空状态则应使用 `PanelEmpty` 组件。无需自行创建第三种居中的空状态组件。

## 聊天、工具及启动界面

- 聊天记录与消息编辑功能均基于 `@assistant-ui/react` 构建。应在 `src/components/assistant-ui` 以及 `src/app/chat/composer` 目录下扩展现有组件，而非为单个功能单独创建第二个 Markdown、消息、工具调用或审批渲染器。  
- 工具结果中可包含用于打开预览的行内操作，但该操作不得自动打开侧边栏。  
- 安装、引导、连接、启动失败以及重新认证等状态虽各不相同，但可使用通用的视觉元素来表现。在统一外观设计时，仍需保留这些状态对应的恢复逻辑。  
- 需尊重 `AppShell` 叠加层的控制权。永久性的终端/内容层、路由叠加层、对话框以及启动界面，均不得通过随意设置 z-index 值来争夺显示优先级。

## 图标与品牌标识

- **Tabler** 是默认的组件及图标集。应从 `src/lib/icons.ts` 中导入其精选的别名及 `iconSize` 缩放方案，切勿在功能代码中直接导入第三方图标包。  
- **`Codicon`** 是用于表示编辑器、工具及状态等场景的紧凑型图标集。应使用 `src/components/ui/codicon.tsx`，并在需要 Tabler 风格组件的地方调用 `codiconIcon()` 函数。  
- 应根据语义上下文选择合适的图标集，并复用现有图标来表示相应操作。切勿在同一个控件组中引入第三套图标集或混合使用不同风格的图标。  
- **`BrandMark`**（位于 `src/components/brand-mark.tsx`）是品牌标识——即白色背景块上的 `nous-girl` 图标，具有柔和的圆角设计，在浅色与深色主题下外观一致。它已取代了旧版本中分散在各处的小星星图标，用于更新页面、引导流程及关于页面等场景。应将其用于展示品牌核心形象的时刻，切勿再次引入装饰性的星星或闪光图标。

## 动画效果

- 动画过渡应快速且功能性强（控件动画时长约为 100ms）。对于非淡入淡出类的动画效果，应尊重用户的 `prefers-reduced-motion` 设置。  
- 复杂的退出动画（例如引导流程中的“矩阵式”淡出效果）应让各个元素依次动画，随后再整体定格——外层容器的淡出动画应设置延迟，以避免覆盖内部的动画效果。切勿让全局淡出动画抢在细节动画之前完成。  
- 动画应跟随状态变化而变化，绝不能因此延迟状态更新。选择、拖动目标、取消操作以及按下反馈等效果都应在当前帧内立即呈现。  
- 在涉及高频交互的操作中，切勿使用 `transition-all` 来为布局几何属性添加动画。应明确指定需要动画的属性，避免在元素移动过程中触发背景模糊重绘，并在出现性能问题时及时移除相关动画。

## 直接操作与性能优化

即使在负载较高的情况下，应用也应保持即时响应——例如处理长篇聊天记录、多个分屏界面或实时流媒体内容。设计时应以此为目标：  
- 首先立即渲染直接操作相关的元素；持久化数据应在之后进行同步处理，若出现错误则需明显地回滚到之前的状态。  
- 保持交互反馈的轻量级：高频使用的状态应保持在本地或通过简单方式计算得出，避免深入复杂的嵌套结构；指针相关操作也应在每一帧内集中处理。  
- 每个放置区域仅有一个视觉上的主导元素，且所有放置目标在不同文件、会话、标签页及分屏界面之间都应使用统一的可操作性表达方式。若出现重叠目标，应以当前处于活动状态的元素为准，而非简单堆叠多个叠加层。  
- 容错性更强的几何布局优于像素级精确的触发机制；边缘操作元素应靠近其实际位置，而非集中在中心区域。  
- 高成本的带状态界面在隐藏时也应保持挂载状态。可见性并非决定组件生命周期的关键因素。

应以真实的内容来证明应用的快速响应能力。一个快速的空状态演示并不能反映应用在处理长篇聊天记录或繁忙终端界面时的表现。

## 键盘操作与取消功能

- 键盘控制权随焦点变化而转移。处于焦点状态的界面可占用相应的键盘按键；标题栏中的快捷键不得占用终端或编辑器已绑定的按键。  
- 应通过统一的层级结构来注册全局快捷键，而非使用临时的监听器。  
- 一个取消手势仅能执行一个操作：要么取消当前正在进行的交互，要么关闭最顶层的可关闭界面——绝不能同时执行这两项操作，也绝不能影响下方的控件。  
- 即使后续的清理操作是异步执行的，UI 层面的取消操作仍应是同步的：叠加层、光标以及待处理的手势状态都会立即清除。  
- 那些刻意设计为无法关闭的流程（如安装流程、破坏性操作确认界面）必须明确告知用户这一点。

## 国际化支持

- 所有面向用户的字符串内容均需经过 `useI18n()` 函数处理（位于 `src/i18n/context.tsx`），JSX 代码中不得出现硬编码的字符串。  
- **所有语言版本应同步更新**——包括 `en`、`ja`、`zh`、`zh-hant` 四种语言。如果在 `en.ts` 文件中修改了字符串而未同步更新其他语言版本，即属于功能退化（如标点符号位置变化、标签内容过时等）。四种语言版本的标点符号及语气表达均需保持一致。

## 状态管理（TypeScript）

详细的状态定义位于 scoped 文件 `[`AGENTS.md`]` 中。代码实现应遵循以下基本原则：  
- 共享的/跨组件的状态应使用小型 **nanostores** 管理，避免通过属性传递方式层层传递状态。每个功能模块应自行管理其内部状态，共享状态则存储在 `src/store` 文件中。  
- 渲染组件应通过 `useStore` 函数来订阅状态变化；非渲染相关的操作则通过 `$atom.get()` 方法读取状态值。  
- 当组件无需显示状态的完整值时，可直接订阅派生出的粗略状态信息，而无需频繁读取原始状态数据。  
- 操作相关功能模块应与通用钩子函数分开编写，每个钩子仅负责处理单一特定的任务。  
- 状态持久化逻辑应与对应的状态变量放在一起，避免路由根节点的代码过于臃肿。  
- 公共属性推荐使用 `interface` 类型定义；对于 React 原生属性，则可直接扩展使用（如 `React.ComponentProps<'button'>`、`Omit<…>` 等）。

## 可操作性设计

- 在最基础层面，按钮、下拉菜单及选择框等控件应默认设置为 `cursor-pointer` 状态——无需在每个调用点单独硬编码该属性。  
- 全局焦点环应重置为初始状态；标题栏中的操作按钮不应具有活动背景色状态。  
- 按下 `Esc` 键可关闭所有可关闭的叠加层或对话框（安装流程及引导流程除外）；关闭操作应使用 X 形图标，而非“关闭”文字。

## 在添加新功能之前——检查清单- [ ] 是否应复用基础组件（如 `Button`、`SearchField`、`SegmentedControl`、`ListRow`、`Loader`、`ErrorState`、`LogView`），而非自行创建？
- [ ] 是否使用令牌（如 `--ui-*`、`shadow-nous`、`--stroke-nous`）来实现零原始颜色值/一次性阴影效果？
- [ ] 是否禁止通过 `className` 覆盖基础组件的内边距、尺寸、圆角或边框样式？
- [ ] 是否将仅包含图标的按钮包裹在带有描述性标签的 `<Tip>` 元素中？
- [ ] 按钮是否不使用原生 `title=` 属性，而是改用 `<Tip>` 元素？
- [ ] 键绑定提示是否通过 `useKeybindHint`/`TipKeybindLabel` 从配置存储中读取？
- [ ] 叠加层是否采用 `shadow-nous` 和 `border-(--stroke-nous)` 样式，而非固定边框？
- [ ] 设计风格是否为扁平化——不使用嵌套卡片，也不添加多余的行分隔符？
- [ ] 是否禁止通过背景事件实现自动导航、焦点抢占或面板打开功能？
- [ ] 直接操作是否能立即生效，并在失败时干净地撤销？
- [ ] 热交互处理是否避免了广泛的订阅、布局抖动以及 `transition-all` 动画？
- [ ] 键盘控制逻辑及单次按 `Esc` 的行为是否正确？
- [ ] 所有新增或修改的字符串是否都已更新到四种语言版本中？
- [ ] `cursor-pointer`、焦点环以及通过 `Esc` 关闭的功能是否正常工作？
- [ ] 若修改了基础组件、令牌或其变体，该文件中对应的命名合约条目是否也会同步更新？
