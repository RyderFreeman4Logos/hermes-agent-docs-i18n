# 每周回顾与规划

在用户指定的系统中执行定期的每周重置操作。这属于具体的重复性任务，而非通用的效率提升方法——`weekly-review` 自动化蓝图会以 cron 作业的形式安排其执行。

## 适用场景

- “运行我的每周回顾。”  
- “我承诺完成了哪些任务，哪些正在滞后？”  
- “根据我的日历、任务和笔记规划下周的工作。”  
- “查找已搁置的项目和待处理事项。”  
- 定时任务会在预定的每周回顾时间触发。

**不适用场景**：日常简报（请参考 `google-workspace` 的日常简报功能）或单一收件箱分类处理（使用 `email-inbox-triage` 功能）。

## 执行步骤

### 1. 设置系统参数与时间范围

确认时区、回顾周期、规划时间范围、权威的任务/项目存储库、日历、收件箱以及允许的写入操作。默认设置为仅读取推荐内容或草稿，禁止直接修改数据。当所有冲突的“真实数据源”均被明确判定后，此步骤完成。

### 2. 查看日历相关信息

加载 `google-workspace` 或相应的日历连接器。首先查看已结束的周内的会议与已承诺的任务，再查看接下来1-2周内的截止日期、出差安排、准备工作及时间安排情况。同时梳理过去事件中隐含的后续行动以及未来可能出现的冲突。当回顾内容与规划范围均覆盖完毕后，此步骤完成。

### 3. 清理各类信息收集点

检查任务收件箱、笔记（如 `obsidian`、`notion`）、标记过的邮件（由 `email-inbox-triage` 负责按主题进行分类处理），以及其他已设定的信息收集渠道。将每项内容转化为下一步行动、项目、待处理事项、已安排事项、未来计划、参考资料、归档或删除的建议。在范围得到确认之前，不得对任何数据进行修改。当所有未处理的项目都被统计并明确处理方式后，此步骤完成。

### 4. 整理当前进行中的项目

针对每个项目，需明确期望达成的结果、下一步行动、负责人、截止日期、阻碍因素、最近一次有意义的活动记录以及相关来源链接。对于那些没有明确下一步行动、错过截止日期、存在重复记录或状态相互矛盾的项目，需予以标记。当所有待处理项目要么具备可执行的下一步计划，要么已被明确暂停时，即视为任务完成。

### 5. 审核待办事项与已承诺事项

梳理用户做出的承诺以及他人尚未完成的事项，并为这些事项提出包含具体日期和沟通渠道的后续跟进方案。切勿将沉默视为任务已完成。当每项待处理事项都有明确的负责人以及下次审核或跟进的日期时，即视为任务完成。

### 6. 制定兼顾工作负荷的计划

先估算固定的日程安排负担，再选定少量每周需完成的目标以及近期的下一步行动。根据事项的重要性、截止日期、依赖关系及所需投入精力对任务进行排序；无需将所有空闲时间都填满。当计划符合实际工作能力，并且明确了需要延后处理的任务时，即视为任务完成。

### 7. 应用已获批的更新内容

只有在获得批准后，才能更新任务/项目信息、设置日历占用提醒、归档已处理完毕的事项，或起草后续跟进内容。所有修改后的记录都需从数据提供方处重新读取确认。当经过验证的更新内容与审核总结一致时，即视为任务完成。

## 输出结构

1. 已完成的承诺事项
2. 逾期或存在风险的事项
3. 待处理/需跟进的事项
4. 进展停滞或状态不明确的项目
5. 下周的目标计划及日程限制
6. 需要审批的更新建议
7. 覆盖范围存在的缺口

## 常见误区

- 在日历容量不足的情况下基于任务进行规划。  
- 将所有未完成的任务均标记为高优先级并延续处理。  
- 对那些没有后续行动的计划标记为“进行中”状态。  
- 默默删除或重新安排个人日程。  
- 将对方的沉默视为任务已完成。  

## 验证标准

- [ ] 已涵盖已完成周及规划周期，或明确说明了存在的缺失部分。  
- [ ] 每个处于停滞/等待状态的任务都能追溯到具体的记录、事件或对话线程。  
- [ ] 未经批准不得修改任何任务、事件或备注；所有已获批准的更改都会被重新读取。  
- [ ] 规划内容需明确列出被推迟的事项，而不仅仅是已选定的事项。
