# 简化代码 —— 并行审查与清理

通过三个专注的审查智能体并行审查您最近的代码变更，汇总它们的发现，并仅应用那些确实需要修复的问题。

**核心原则：** 三个专注的审查者胜过一个宽泛的审查者。每个审查者都会深入代码库，专门针对某一类问题——如代码复用、质量或效率——进行排查，而不会分散注意力到其他方面。由于它们是同时运行的，您只需承担一次审查的延迟，而非三次。

## 适用场景

当用户说出以下任意语句时，可触发此技能：

- “简化” / “简化我的代码变更” / “简化这些变更”
- “审查我的代码” / “审查我最近的变更” / “清理我的代码变更”
- “/simplify”（适用于习惯使用 Claude Code 的用户）

用户可能还会添加一些可选的修饰词——请予以尊重：

- **专注方向：** “简化，重点关注效率” → 仅运行专注于效率的审查智能体（或让汇总结果更侧重于效率方面）。支持的专注方向包括：`reuse`、`quality`、`efficiency`。
- **模拟运行：** “简化代码，但不要做任何修改” / “仅报告问题” → 运行三个审查智能体，呈现发现结果，但不应用任何修复。在实际应用前请先征得用户同意。
- **范围限定：** “简化最后一次提交的代码” / “简化已暂存区的代码” / “简化 src/foo.py 文件中的代码” → 按照要求缩小代码对比的范围（详见第一阶段）。

请勿在每次编辑后自动运行此技能。它需要消耗三个子智能体的计算资源——仅应在用户明确请求时才调用。

## 工作流程

### 第一阶段 —— 确定需审查的变更

首先获取需要审查的代码差异。根据用户的请求选择对应的代码来源，顺序如下：

```bash
# 1. Default: uncommitted working-tree changes (tracked files)
git diff

# 2. If that's empty, include staged changes
git diff HEAD

# 3. Scoped variants the user may request:
git diff --staged                 # "staged changes"
git diff HEAD~1                    # "the last commit"
git diff main...HEAD              # "this branch" / "my PR"
git diff -- src/foo.py            # specific file(s)
```

如果 `git diff` 和 `git diff HEAD` 的输出均为空，且既不存在 Git 仓库也没有任何更改，那么就转而处理用户明确指定的文件，或是当前会话中最近创建或修改过的文件。如果确实找不到任何被修改的代码，请如实说明并停止操作——此时无需再做简化处理。

需完整捕获差异文本，并记录其大小：若文本体积极大（例如超过2000行被修改内容），应提醒用户，让三个子代理分别处理完整差异会消耗大量令牌，建议在继续之前缩小检查范围（按目录或按提交来处理）。

### 第二阶段——并行启动三个审查器

使用 `delegate_task` 的**批量模式**，将三个任务一次性放入同一个 `tasks` 数组中，使其同时运行。对于这种工作模式而言，三个审查器是合适的数量；在任何默认安装环境下，这一数量都处于 `delegation.max_concurrent_children` 允许的范围内。

需将**完整的差异内容**（而非片段——跨文件的问题会隐藏在片段中）以及仓库的完整路径提供给**每个**审查器，以便他们能够搜索更广泛的代码库。每个审查器都会获得 `terminal`、`file` 和 `search` 工具集（从而能够执行 `git`、`read_file` 以及 `search_files`/grep 等操作）。

需告知每位审查器以下要求：
- 在现有代码库中搜索相关证据（不要仅依据差异文本进行推断）；
- 以结构化的列表形式汇报发现结果，格式为：`文件:行号 → 问题描述 → 建议修复方案`；
- 为每项发现标注 `高`/`中`/`低` 的置信度；
- 跳过细微问题及仅涉及代码风格的改动，仅标记那些能显著提升代码质量的问题。

需传递以上三个目标（若用户的关注点不包括某些内容，则可省略）：

**审查器1——代码复用**
> 检查此差异中是否存在重复利用代码库中已有功能的代码。在工具模块、共享辅助函数以及相关文件中（可使用 `search_files`/grep）查找现有函数、常量或模式，新代码应直接调用这些现有内容而非重新实现。需标记的内容包括：重复现有函数的新函数；那些本可由现有工具处理的手动逻辑（如手动字符串/路径操作、自定义环境检查、临时类型判断、重新实现的解析逻辑）。对于每项问题，需明确指出应使用的现有功能及其所在位置。

**审查器2——代码质量**
> 检查此差异中是否存在代码质量问题。需关注以下方面：冗余状态（重复的或可从现有状态推导出的值；不必要的缓存）；参数过多（本应重构函数却新增了大量参数）；近似重复的代码块（本应通过抽象来共享）；抽象层次不当（暴露内部实现，破坏现有的封装边界）；强类型字符串使用（明明已有常量/枚举/注册表却仍使用原始字符串——在标记前需先核对标准注册表）。对于每项问题，需给出具体的重构方案。

**审查器3——效率优化**
> 检查此差异中是否存在效率问题。需关注以下方面：不必要的操作（重复计算、多次读取文件、重复调用API、N+1访问模式）；未充分利用并发性（独立操作被顺序执行）；热点路径性能瓶颈（在启动或每次请求时执行耗时/阻塞性操作）；TOCTOU反模式（在操作前先进行存在性检查，而非直接执行操作并处理错误）；内存问题（内存无限制增长、缺乏清理机制、监听器/处理程序泄漏）；读取范围过大（本只需读取部分内容却加载了整个文件）。对于每项问题，需给出具体的修复方案，并说明为何该方案能提升效率或减少资源占用。

### 第三阶段——汇总与应用

等待三个审查器同时返回结果（批量模式会一次性返回所有结果）。

1. 将所有发现结果合并到一个列表中，若不同审查器的发现有重复则进行去重。
2. **排除误报**——作为任务发起方，你拥有最全面的上下文，无需与审查器争论，可直接忽略那些不合理或质量较低的建议。
3. **解决冲突**。不同审查器可能会给出不同意见（例如审查器1认为“使用现有工具X”，而审查器3认为“X效率低下，应直接内联”）。默认的解决优先级为：**正确性 > 用户指定的关注点 > 可读性/复用性 > 微性能优化**。除非相关路径确实属于性能热点，否则不要应用会降低代码清晰度的性能“修复”。当两个建议相互矛盾但都有一定合理性时，选择改动范围更小的方案，并注明另一种可选方案。
4. 直接使用 `patch` / `write_file` 应用经过筛选的修复方案——除非用户要求先进行模拟运行，否则应先列出所有修改内容并征得用户确认。
5. **验证**修改未造成任何问题：针对被修改的文件运行项目中的相关测试（无需运行全部测试套件），并重新执行仓库中配置的代码检查工具。如果某个修复导致了测试失败，则需撤销该修复并予以报告。
6. **总结**所做的更改：按审查器类别列出已应用的修复方案，同时说明有意跳过的发现及其原因。

## 常见误区

- **审查器数量不宜超过3个**。审查器越多，成本越高，需要协调的冲突建议也越多，反而无法提升检查覆盖率。三个类别已足以覆盖大部分场景。
- **需将完整差异内容提供给每个审查器**。将差异拆分给不同审查器会违背设计初衷——只有查看完整差异，才能发现跨文件的重复问题及N+1访问模式。
- **审查器应基于实际搜索结果，而非猜测**。仅指出存在重复问题却未指出对应的现有工具（如“可能已有相关辅助函数”）属于无效信息。必须要求提供 `文件:行号` 等具体证据，缺乏此类证据的发现应直接忽略。
- **应用修复 ≠ 重写代码**。此功能仅用于清理用户最近的修改，而非允许随意重构整个模块。所有编辑应限制在差异涉及的范围内，以及修复方案所需的最低限度的周边修改。
- **需遵循项目惯例**。如果仓库中有 `AGENTS.md`/`CLAUDE.md`/`HERMES.md` 文件或代码检查配置，应将相关规则纳入审查提示中，确保建议符合项目的风格规范，而非与之冲突。
- **过大差异会导致上下文丢失**。如果差异内容过于庞大，应在分配任务前先缩小检查范围——让三个子代理分别处理5000行左右的差异会消耗大量资源，还可能导致内容被截断。
