# 适用于 CLI/API 智能体的 Claude Design

当用户需要执行通常适合在 Claude Design 中完成的设计任务，但智能体运行在 CLI/API 环境中而非托管的 Claude Design 网页界面时，可使用此技能。

其目标是在保留 Claude Design 高效的设计功能与设计风格的同时，去除普通智能体环境中不存在的托管工具相关组件。

**在开始之前，请先确认是否需要其他网页设计相关的技能，例如 `popular-web-designs`（适用于 Stripe、Linear、Vercel、Notion 等平台的即用型设计系统）和 `design-md`（遵循 Google 的 DESIGN.md 令牌规范格式）。** 如果用户希望采用某知名品牌的视觉风格，可同时加载 `popular-web-designs` 与该技能，由其提供相应的视觉元素。若最终输出的是令牌规范文件而非渲染后的成品，则应使用 `design-md`。完整的决策表见下文。

## 何时选择该技能、`popular-web-designs` 或 `design-md`

Hermes 在 `skills/creative/` 目录下提供了三种与设计相关的技能，它们各自承担不同的功能——请根据需求选择合适的技能（或组合使用）。

| 技能 | 能为你带来什么 | 适用于用户想要……的场景 |
|---|---|---|
| **claude-design**（即本技能） | 帮助确定*设计流程与风格*——包括如何明确需求范围、收集相关背景信息、生成多种设计方案、验证本地 HTML 文件的质量，同时避免 AI 设计中常见的低质量问题 | 需要从零开始创建设计作品（如登录页、原型、演示文稿、组件库、动态演示），且无需遵循特定的品牌风格或规范体系 |
| **popular-web-designs** | 提供 54 组可直接复制使用的设计系统——包含 Stripe、Linear、Vercel、Notion、Airbnb 等平台的标准颜色、字体、组件及 CSS 值 | 希望作品呈现与 Stripe/Linear/Vercel 等知名平台相似的风格，或按照某个特定品牌进行页面设计，亦或是从真实产品中获取视觉参考 |
| **design-md** | 支持遵循 Google 的 DESIGN.md 规范格式——可对设计规范文件进行编写、验证、差异对比及导出，同时具备 WCAG 对比度检测功能，还能导出 Tailwind/DTCG 格式的内容 | 需要创建正式、持久且可供机器读取的设计系统*规范文件*（包含设计规范值及其设计依据），此类文件可存储在代码仓库中，供后续的智能体持续使用 |

实用选择指南：

- **需要兼顾设计流程与风格，且仅需生成一次性作品** → 选用 **claude-design**
- **希望作品风格与知名品牌一致** → 选用 **popular-web-designs**（同时可由 **claude-design** 协助完成设计流程）
- **需要自行编写设计规范文件** → 选用 **design-md**

三者可组合使用：若需视觉设计元素，用 **popular-web-designs**；若要将需求转化为结构完整的本地 HTML 文件，用 **claude-design**；而当输出结果为设计规范文件而非可视化作品时，则选用 **design-md**。

## 先从整体入手：在调整设计规范参数前先确定整体结构

效力最强的防“设计冗余”规则。大多数人工智能设计中的冗余问题属于**结构性而非表面性**——模型总会为每个展示区域选择居中的核心内容，再搭配三张权重相同的特征卡片，最后才进行装饰处理。即便重新配色或调整样式，也无法解决根本问题，因为早在选定任何颜色之前，布局本身就已经存在缺陷。

在设定任何颜色、比例或组件之前，**先明确锁定仅一种展示区域类型**。这样能迫使模型先依据高层次的规划进行生成，从而降低输出结果的随机性——这与其说理过程通过“思维链”步骤得到优化，原理如出一辙。

七种展示区域类型：

1. **监控**——用户用于观察状态变化（仪表板、状态页面、可观测性工具）。设计注重信息密度、直观的层级结构，避免营销化元素。  
2. **操作**——用户对事物执行具体动作（控制台、管理面板、队列、收件箱）。界面以操作功能和选择状态为核心。  
3. **对比**——用户用于相互权衡不同选项（价格、套餐、规格表、搜索结果）。设计需确保列对齐、结构统一，并突出一个核心差异点。  
4. **配置**——用户用于设置各项参数（设置项、表单、向导、入门流程）。采用渐进式展示方式，清晰显示保存/验证状态，减少装饰元素。  
5. **决策/学习**——用户用于接受说服或获取知识（着陆页、文档、营销内容）。每个板块仅传达一个核心信息；这也是唯一允许使用醒目标题的区域。  
6. **探索**——用户用于浏览开放式空间（图库、地图、搜索筛选功能、产品目录）。界面主要由筛选器、结果网格以及缩放/查看功能构成。  
7. **命令/检查**——用户通过键盘操作或深入查看单个对象（命令栏、检查器、详细信息面板、属性编辑器）。设计注重操作速度与专注度，而非信息广度。  

规则：

- 在开始设计之前，先用一句话明确界面所属的类型（例如：“这是一个**监控型**界面，因此其密度与易读性应优于核心展示区”）。
- 仪表板属于监控型界面，而非决策型界面——切勿为其设置居中的核心展示区和三张功能卡片。
- 如果某个屏幕确实同时涉及两种界面类型，需明确指定**主要**界面类型，将另一种视为次要类型；切忌将两者混为一谈。
- “核心展示区加三张卡片”的布局仅适用于**决策/学习类**界面。在其他任何场景中使用该布局，都是最明显的设计失误表现。

相比其他任何美学规则，这一约束更能有效避免出现缺乏特色的通用化界面。

## 工作流程

1. **明确设计需求**
   - 正在设计什么？
   - 目标用户是谁？
   - 最终应产出何种设计成果？
   - 存在哪些固定约束？

2. **收集相关资料**
   - 阅读提供的文档、截图、代码仓库文件或设计资源。
   - 在编写代码之前确定界面的视觉规范。

3. **选定界面类型**（参见“以界面类型为先”原则）
   - 在定义任何视觉元素之前，先明确界面的类型归属。
   - 这一决定将决定整个布局的结构，后续的所有设计元素都将以此为基础。

4. **为该设计成果定义设计系统**
   - 颜色方案
   - 字体类型
   - 缩进间距
   - 圆角参数
   - 阴影或立体感效果
   - 动画表现方式
   - 组件处理规则
   - 交互逻辑

5. **选择合适的呈现形式**
   - 静态视觉对比：使用单个HTML画布，将不同选项并排展示。
   - 交互式流程演示：可点击的原型界面。
   - 演示汇报：固定尺寸的HTML幻灯片集，支持页面切换。
- 组件探索：支持多种变体的组件实验室功能。  
- 动画效果：基于时间轴或状态驱动的动画实现。  

6. **构建成果文件**  
- 除非任务要求使用代码仓库形式，否则建议创建一个独立的HTML文件。  
- 对重大修改需保留之前的版本。  
- 避免引入不必要的依赖项。  

7. **验证**  
- 确认相关文件是否存在。  
- 运行所有可用的语法或静态检查工具。  
- 若有浏览器调试工具，打开文件并检查控制台错误信息。  
- 若视觉效果至关重要且具备截图工具，至少检查主要视图区域。  
- 运行Slop自检工具（参见“Slop诊断”），仅修复该工具标记的问题。  

8. **简要汇报**  
- 文件的准确路径  
- 最终生成的内容  
- 需注意的要点  
- 后续决策或迭代计划  

## 成果文件格式规范  

默认使用本地文件格式。  

对于独立型成果文件：  
- 为文件起一个具有描述性的名称，例如 `Landing Page.html`、`Command Palette Prototype.html`、`Design System Board.html`。  
- 将CSS代码嵌入到 `<style>` 标签中，JS代码嵌入到 `<script>` 标签中。  
- 确保该文件可直接在浏览器中打开。  
- 除非某些远程依赖确实有用且稳定，否则避免使用。  
- 除非格式明确要求固定尺寸，否则需确保文件具备响应式设计功能。  

对于重大修改版本：  
- 将旧版本保留为 `Name.html`。  
- 创建 `Name v2.html`、`Name v3.html` 等新版本文件。  
- 若任务属于组件变体探索类，也可保留一个文件，并通过页面内的切换功能来管理不同版本。  

对于基于代码仓库实现的成果：

- 遵循代码仓库实际使用的技术栈  
- 尽可能使用现有的组件与令牌  
- 若用户要求提供生产环境代码，则不得创建独立的构建产物  

## HTML / CSS / JS 标准  

合理运用现代 CSS 技术：  

- 使用 CSS 变量管理样式参数  
- 采用 CSS 网格布局  
- 在适用情况下使用容器查询  
- 在支持的情况下启用 `text-wrap: pretty`  
- 确保有真实的焦点状态与悬停状态  
- 对非简单的动画效果处理 `prefers-reduced-motion` 设置  
- 实现响应式缩放  
- 在可行情况下使用语义化 HTML  

应避免以下情况：  

- 当期望规范的代码仓库结构时，出现庞大的单一文件  
- 使用脆弱的、硬编码的视口假设  
- 设计过小的、无法正常点击的目标区域  
- 会妨碍可用性的装饰性 JavaScript 代码  
- 除非没有更安全的选择，否则避免使用 `scrollIntoView`  

移动端的目标区域尺寸应至少为 44px。  

打印文档中的文字字号应至少为 12pt。  

对于 1920×1080 分辨率的演示文稿，文字大小通常应不低于 24px。  

## 独立 HTML 文件中的 React 使用指南  

默认情况下应使用纯 HTML/CSS/JS。  

仅在以下情况才使用 React：  

- 构建产物需要具备有意义的状态管理  
- 不同样式变体或开关功能通过组件实现更为便捷  
- 交互逻辑的复杂性要求必须使用 React  
- 目标开发环境为 React/Next.js，且需保持高度一致性  

若在独立 HTML 文件中通过 CDN 引入 React：  

- 必须锁定确切的版本号  
- 避免使用未锁定的 `react@18` 类型 URL  
- 除非必要，否则避免使用 `type="module"`  
- 避免出现多个名为 `styles` 的全局对象  
- 为全局样式对象赋予具体名称，例如 `commandPaletteStyles`、`deckStyles`  
- 若拆分 Babel 脚本，需明确将共享组件挂载到 `window` 对象上
如果在真实的代码仓库中进行开发，建议使用该仓库的包管理工具及组件架构。

## 幻灯片设计规范

对于幻灯片展示，应使用固定尺寸的画布，并根据视口大小进行缩放以适配显示。

默认幻灯片尺寸为 1920×1080，比例 16:9。需满足以下要求：

- 支持键盘导航
- 显示当前幻灯片编号
- 使用 localStorage 保存当前幻灯片状态
- 在可行情况下采用便于打印的布局
- 为重要幻灯片添加屏幕标签或唯一标识
- 除非用户明确要求，否则不得包含演讲者备注

切勿将幻灯片内容简单以 Markdown 列表的形式呈现。如需制作幻灯片文件，应创建经过精心设计的成品。

背景颜色最多使用 1–2 种，除非品牌规范要求更多。应保持幻灯片内容简洁，若某张幻灯片显得空旷，应通过布局调整、节奏控制、比例优化或图片占位符来解决，而非添加冗余文字。

## 原型设计规范

对于交互式原型：

- 确保主要操作路径可点击
- 根据需要展示关键状态：默认状态、悬停/聚焦状态、加载中状态、空状态、错误状态及成功状态
- 在必要时通过页面内控件展示不同方案
- 除非控件本身就是原型设计的一部分，否则不应将其包含在最终成品中
- 当需要保持页面状态在刷新后不变时，需将重要状态保存到 localStorage 中

如果原型旨在模拟产品使用流程，应整体规划整个流程，而不仅仅是第一个界面。

## 变体设计规范

在探索不同设计方案时，至少应准备三种方案：

1. **保守型**——最贴近现有设计模式，风险最低
2. **贴合型**——最符合需求文档要求的方案
3. **创新型**——更具新颖性，有助于探索不同的设计方向
可通过以下方面进行变体探索：

- 布局
- 层级结构
- 字体大小比例
- 密度
- 颜色方案
- 表面处理方式
- 动画效果
- 交互模型
- 文本结构
- 组件形状

除非颜色确实是核心调整点，否则避免仅进行颜色替换的变体设计。

用户选定某个方向后，应立即整合结果，切勿让项目长期停留在一堆可选选项的状态中。

## CLI/API 模式下的可微调设计

此处不存在 Claude Design 的托管编辑模式工具栏。

但仍需遵循同一原则：在合适的情况下，添加名为“Tweaks”的页面内控件。

一个完善的“Tweaks”面板应能控制以下参数：

- 主题模式
- 布局变体
- 密度
- 强调色
- 字体大小比例
- 动画开关
- 文本变体
- 组件变体

该面板应保持简洁，不显突兀。在隐藏微调选项时，设计应呈现出最终形态。

在有必要时，可使用 localStorage 保存微调参数值。

## 内容规范

严禁添加填充内容。

每个元素都必须有其存在的必要理由。

应避免以下情况：

- 虚假数据指标
- 装饰性统计信息
- 通用的功能列表
- 不必要的图标
- 占位文本评价
- 由 AI 生成的冗余内容
- 可能改变策略或虚假陈述的编造内容

如果新增章节、页面、文本或声明能提升作品质量，应在添加前先征得确认。

当某些文本为必要但尚未定稿时，应将其标记为草稿或占位内容。

## 避免低质设计规则

避免出现常见的 AI 设计缺陷：

- 强烈的渐变背景  
- 默认采用玻璃拟态效果  
- 除非品牌有特殊要求，否则使用表情符号  
- 到处都是图标的通用型 SaaS 卡片  
- 带左侧边框的强调提示卡  
- 充满随机数字的虚假仪表板  
- 使用库存照片作为首页视觉元素  
- 用过大的圆角矩形来替代层次结构  
- 彩虹色调方案  
- 如“洞察”“增长”“扩展”“优化”之类缺乏具体内容的模糊标签  
- 伪装成产品实拍图的装饰性 SVG 图像  

极简并不一定就是好的设计，信息密集也未必意味着杂乱无章。一切需经过深思熟虑后才能决定。

## 设计冗余诊断：修复前先评分  

AI 设计中的冗余问题具有某种规律性的表现特征——当要求设计师对 AI 用户界面进行评估时，他们通常会将“这是 AI 生成”的特征归纳为大约十种迹象。在优化或修改某个设计成果之前，应先进行此项自我审计并撰写简短报告。**先诊断，再处理**——试图一次性完成审计与修复往往会导致失败，因为模型的固有倾向会盖过设计指令，使其重复同样的错误（例如本该重新布局却只是调整了颜色，或是明明存在排版问题却只对文字进行了美化）。

这十种迹象如下（每出现一种即计一分；分数越低越好）：

1. **科技渐变风格**——所有元素均采用蓝色/紫色/靛蓝的亮面渐变效果。  
2. **通用科技色调**——默认强调色为靛蓝/紫色（并非基于品牌选择，而是模型偏好的颜色）。  
3. **功能卡片网格布局**——每行包含图标、标题与短句各3个，权重均等，无优先级区分。  
4. **强调色侧边栏**——卡片上方的彩色横条：仅作为装饰，用以模拟分类结构。  
5. **虚假模糊效果**——采用玻璃态设计，但缺乏真正的深度或立体感机制。  
6. **夸张数据展示**——使用过大的数字占据本应用于讲述产品故事的空间。  
7. **图标顶部装饰**——每个标题上方均有一个居中的圆角方形图标（源自Tailwind模板）。  
8. **居中堆叠布局**——由于未制定明确的构图规则，所有元素均被置于中心位置。  
9. **默认字体**——默认使用Inter或系统自带字体，而非经过精心挑选的字体。  
10. **表面风格不匹配**——整体布局与所使用的界面风格不相契合（例如在Monitor界面中使用英雄区域设计）。这正是其他诸多问题的根本原因。  

如何运行它：

- 为该作品给出1至10分的评分（10分代表最严重的缺陷）。在一份简短的报告中说明得分，并列出触发该评分的诊断结果。  
- 将此报告视为**背景信息而非待办清单**——它仅指示应在何处进行修复，而非规定具体的修改方式。  
- 根据诊断结果进行相应修复：  
  - 诊断结果为3、8、10 → **重新布局/重组结构**（需重新考虑版面元素的选择，无需调整颜色）。  
  - 诊断结果为1、2、9 → **重新着色/调整排版**（问题确实出在色彩方案与字体格式上）。  
  - 诊断结果为4、5、6、7 → **移除装饰元素**，改用真正的层次结构来体现层级关系（如大小、粗细、间距）。  
- 修复完成后需重新评分。只要诊断结果仍为3、8、10，就不得宣布任务已完成——这些是根本原因，其余通常仅为症状表现。  

将诊断与处理分开的目的是：先让审计工具指出问题，再仅针对其指出的问题，在其建议的范围内进行修复。  

## 字体设计  

若已有字体系统，请直接使用。  
若没有，则需根据作品类型慎重选择字体：  
- 编辑类内容：使用衬线体或人文主义风格标题字，正文选用简洁的无衬线体；  
- 软件/生产力工具类：选用精确度高的无衬线体，并确保数字显示清晰；  
- 奢华/极简风格：减少字体粗细种类，注重间距控制；  
- 技术文档类：仅使用等宽字体作为强调元素，但无需全程使用等宽字体；  
- 演示文稿类：选用大号字体、高对比度设计，确保清晰易读。  

在合适的情况下，应避免使用过于常见的默认字体。  
若使用网页字体，建议控制字体系列和粗细种类的数量。  
在添加框、图标或颜色之前，应先利用字体建立层次结构。  

## 颜色设计

请优先使用品牌或设计系统中的颜色。

若不存在配色方案：

- 先定义一个基础色彩系统，包括中性色、背景色、文字色、柔和文本色、边框色、强调色，以及必要时的危险/成功提示色；
- 除非有特殊要求需要更丰富的配色，否则仅使用一种主要强调色；
- 在浏览器支持良好的情况下，可选用 oklch 颜色模型来打造和谐的自定义配色方案；
- 务必检查重要文本和控制元素的颜色对比度。

切勿从零开始随意创造大量颜色。

## 布局与构图

以节奏感进行设计：

- 尺寸比例
- 空白空间
- 颜色密度
- 对齐方式
- 重复元素
- 对比效果
- 中断元素

避免所有板块都采用相同的卡片式网格布局。

对于产品界面，应注重信息的快速传达而非过度装饰。

对于营销页面，每个板块只需突出一个核心信息。

对于控制面板，要避免“数据冗余”，仅展示能够帮助用户做出决策或采取行动的数据。

## 动画效果

应将动画视为一种设计规范，而非单纯的视觉特效。

优秀的动画效果：

- 能清晰展现状态变化；
- 减少页面加载时的焦虑感；
- 体现不同界面之间的连贯性；
- 增加控制元素的交互感；
- 整体风格简洁自然。

糟糕的动画效果：

- 无目的地循环播放；
- 拖慢用户操作速度；
- 过度吸引注意力；
- 掩盖页面中不良的层次结构。

对于非必要的复杂动画，应尊重用户的 `prefers-reduced-motion` 设置。

## 图片与图标

在条件允许的情况下，请使用提供的真实图片。

如果缺少相关资源：

- 使用简洁的占位图；
- 用字体、布局或抽象纹理替代；
- 在图像质量至关重要的情况下，及时请求真实的素材。

除非任务明确要求制作插图，否则切勿自行绘制复杂的伪 SVG 插画。

除非图标能提升扫描效率或符合设计系统规范，否则请避免使用图标。

## 代码原貌保留

从代码仓库中复现或扩展用户界面时，请按以下步骤操作：

1. 浏览代码仓库的目录结构
2. 确定实际的界面源文件
3. 阅读主题、令牌、全局样式及组件相关文件
4. 在适当情况下直接沿用其中的精确数值
5. 保持间距、圆角、阴影效果、文本风格、密度以及交互模式的一致性
6. 之后再进行设计或修改

只要存在源文件，就切勿凭记忆进行开发。

对于 GitHub 链接，请正确解析所有者/仓库名/引用路径，并在设计前先查看相关文件。

## 文档与资源读取

在条件允许的情况下，可直接读取 Markdown、HTML、CSS、JS、TS、JSX、TSX、JSON、SVG 以及纯文本文件。

对于 DOCX、PPTX、PDF 格式的文件，若有本地提取工具可用则优先使用；若没有，则请用户提供导出的文本或图片，或选择其他可行的处理方式。

对于设计草图，除非原始的 JSON 文件是唯一可用的资料，否则应优先查看缩略图或截图，而非直接使用 JSON 数据。

## 版权与参考标准

除非用户明确拥有相关内容的使用权，否则不得复现任何公司的独特界面设计、专有命令结构、品牌化界面或完全一致的视觉标识。

不过，提取以下通用设计原则是可行的：

- 避免杂乱，保持合理密度
- 以命令操作为核心交互方式
- 以单色为主，辅以一处点缀色
- 明确的层级结构
- 清晰的空状态展示
- 强大的键盘操作支持

但复制专有布局、照搬完整的品牌界面元素或重现受版权保护的内容则是不可取的。

在运用参考资料时，需将既定理念与原则转化为独特的设计方案。

## 验证流程

在给出最终回复之前，应在现有环境允许的范围内尽可能进行全面验证。

最低要求：
- 文件存在于指定路径
- HTML文件已完整保存
- 无明显的语法错误

更佳做法：
- 在浏览器中打开文件并检查控制台错误
- 在主视口查看截图细节
- 测试各项关键交互功能
- 若存在不同主题或版本，需进行相应测试
- 如有必要，还需测试响应式断点

若受环境限制无法完成全部验证，应明确说明已验证及未验证的内容。

若文件实际上并未生成，请切勿声称“已完成验证”。

## 最终回复格式

保持最终回复简洁明了，需包含以下信息：
- 文件路径
- 文件内容概述
- 验证状态
- 如有必要，可附加后续建议操作

示例：

```text
Created: /path/to/Prototype.html
It includes 3 layout variants, a Tweaks panel for density/theme, and responsive behavior.
Verified: file exists and opened cleanly in browser, no console errors.
Next: pick the strongest direction and I’ll tighten copy + motion.
```

## 可移植的提示词模式

在将 Claude Design 风格的请求转换为 CLI/API 模式时，可参考以下思维转换方式：

```text
You are running in CLI/API mode, not hosted Claude Design. Ignore references to hosted-only tools or preview panes. Produce complete local design artifacts, usually self-contained HTML with embedded CSS/JS, and verify with available local tools before returning. Preserve the design process: gather context, define the system, produce options, avoid filler, and meet a high visual bar.
```

## 常见误区

- 不要将托管工具的架构直接粘贴到技能中，这会导致虚假的工具调用。
- 不要将过长的外部提示作为运行时上下文提供给该技能，否则会造成功能偏差。
- 在移除工具相关代码时，切勿忽视设计原则。
- 当用户已给出足够指示时，不要过度提问。
- 若缺乏品牌相关背景信息，就不要试图完成高精度的任务。
- 不要使用通用的SaaS界面布局却称其为精心设计的作品。
- 除非确实完成了浏览器验证，否则切勿谎称已完成该步骤。
