# Relay ↔ Connector 接口规范（v1，实验性版本）

> **状态：** 实验性版本。在至少有两个一级平台（Discord 和 Telegram）对其完成验证之前，该接口**可能随时变更**且无需经过弃用流程。实验阶段的修改仅限于**增量式添加**，并通过 `contract_version` 进行控制。任何破坏性变更都会同步更新两个代码库。

本文档定义了 **Hermes 网关**（Python，位于 `gateway/relay/` 目录）与 **连接器**（Node/TypeScript，位于 `NousResearch/gateway-gateway` 目录）之间的正式接口。连接器实现者首先需要阅读此文档。

网关会运行一个通用的 `RelayAdapter`，该适配器会**主动连接**连接器，在握手阶段接收 `CapabilityDescriptor`，之后通过每轮双向 WebSocket 交换标准化的 `MessageEvent`（入站消息）及操作指令（出站指令）。网关不会知晓自身背后具体的平台是哪一个；所有与特定平台相关的套接字及身份识别逻辑均由连接器负责处理。

---

## 1. 握手流程

1. 网关建立传输连接（调用 `connect` 方法）。
2. 网关调用 `handshake()` 方法，连接器则返回一个 `CapabilityDescriptor`（见第2节），其中描述了该适配器所支持的平台信息。
3. 网关根据描述符配置适配器的相关参数（如字符限制、长度单位、草稿/编辑/线程/Markdown功能等），并注册入站消息处理函数。
4. 此后连接器开始流式发送入站事件，并接收网关发出的出站操作指令。

`contract_version` 字段（当前值为 `1`）会包含在描述符中。为保持向后兼容性，网关会忽略未知的描述符字段；对于缺失的可选字段，则会使用默认值填充。

---

## 2. CapabilityDescriptor（握手数据包内容）

该字段为 JSON 对象，其定义来源为 `gateway/relay/descriptor.py`。

| 字段 | 类型 | 是否必填 | 含义 |
| --- | --- | --- | --- |
| `contract_version` | int | 是 | 接口版本号（同一版本内仅支持增量式扩展）。 |
| `platform` | string | 是 | 平台名称（例如 `"discord"`、`"telegram"`）。 |
| `label` | string | 是 | 便于人类理解的标签。 |
| `max_message_length` | int | 是 | 字符限制上限；网关会将其暴露为 `MAX_MESSAGE_LENGTH` 参数。若值为 0，则视为 4096 字符。 |
| `supports_draft_streaming` | bool | 是 | 是否支持原生草稿流预览功能。 |
| `supports_edit` | bool | 是 | 是否支持基于编辑的流式传输；若该值为 false，客户端将只能以每段一条消息的方式接收数据。 |
| `supports_threads` | bool | 是 | 是否具备 `create_handoff_thread` 功能。 |
| `markdown_dialect` | string | 是 | Markdown 语法版本，可选值包括 `"plain"`、`"markdown_v2"`、`"discord"` 等（该字段会决定是否支持代码块功能）。 |
| `len_unit` | string | 是 | 长度计量单位，可选值为 `"chars"`（使用内置字符计数）或 `"utf16"`（Telegram 使用的 UTF-16 代码单元）。 |
| `emoji` | string | 否 | 显示用的表情符号，默认为 🔌。 |
| `platform_hint` | string | 否 | 系统提示用的平台标识符。 |
| `pii_safe` | bool | 否 | 是否会在会话描述中隐去个人身份信息。 |

大部分字段实际上都是从网关现有的 `PlatformEntry` 对象中提取而来的；而那些仅在运行时才需要的字段（如 `len_unit`、各类 `supports_*` 开头的字段以及 `markdown_dialect`）则直接来自对应平台适配器的功能方法。

## 3. 入站消息：`MessageEvent` 数据结构

连接器会将每个平台的原始消息事件转换为标准的 `MessageEvent` 对象（定义位于 `gateway/platforms/base.py`），然后将其发送给网关。入站消息是通过网关的**出站方向 `/relay` WebSocket** 传输的（详见下文的传输说明）——连接器会通过网关已建立的套接字，向下推送 `inbound` 类型的数据帧。网关会利用嵌入在消息中的 `SessionSource` 对象通过 `build_session_key()` 方法生成会话密钥；因此，确保正确填充各类识别字段是连接器需要承担的最重要的职责。

### 入站传输方式（使用 WebSocket 通道，而非 HTTP）

网关会**主动连接**连接器的 `/relay` WebSocket，用于进行握手、发送出站操作指令（见第4节）以及发送自身的 `/stop` 停止指令（见第5节）。入站消息则通过同一套接字的**反向通道**传输：连接器会通过网关的出站 WebSocket，向下推送 `inbound` 类型的数据帧（若需要中断入站传输，则会使用 `interrupt_inbound` 数据帧，见第5节）。网关**没有专门的入站 HTTP 接口**——托管式的网关无需也不可能暴露任何入站端口；所有数据都通过其自身建立的连接进行传输。

**多实例路由机制。**负责处理某个平台消息的连接器实例（即生成入站事件的实例），通常**并非**网关建立出站 WebSocket 连接的目标实例。因此，生成事件的实例会将消息发布到连接器内部的**中继总线**上（基于 Redis 的发布/订阅机制，对应 `src/core/relayBus.ts` 文件中的 `RelayBus` 类），并使用租户标识作为键值。每个连接器实例都会订阅该总线，并将收到的每条消息路由到该租户的**本地会话**中（通过 `RelayServer.routeBusMessage` 方法实现）；最终，只有持有网关套接字的那个实例才会处理该消息，而那些没有对应租户本地会话的实例则不会执行任何操作。因此，跨实例的消息传递实际上只是集群内部的 Redis 通信，而非公共 HTTP 调用。

连接器向网关发送的数据帧格式如下（通过 WebSocket 传输）：

- `{"type":"inbound", "event": <MessageEvent>, "bufferId"?}`
- `{"type":"interrupt_inbound", "session_key", "chat_id"}`（用于中断入站传输，见第5节）
- `{"type":"passthrough_forward", "forward": <PassthroughForward>, "bufferId"?}`（用于转发请求，见第5.1节）

`PassthroughForward` 字段表示经过转发的请求数据，其格式与二级/三级 webhook 请求类似（如 Discord 交互、Twilio 接口）：`{platform, botId, method, path, headers: [[k,v],…], bodyB64}`。请求体采用 Base64 编码，这样即使消息内容包含换行符，也能在以 JSON 格式传输的过程中保持完整；网关会对其进行 Base64 解码，从而得到连接器转发的原始字节数据（连接器已在边缘节点验证了服务提供商的签名，并去除了任何共享身份凭证——见第6节），因此网关只需处理经过净化、不含令牌的请求体，再通过无需令牌的 `follow_up` 机制来处理该请求。详情请参见第3.1节。

**信任机制。** WebSocket 升级过程会使用网关为每个网关配置的专用密钥进行身份验证（见第6.1节），因此整个通信通道是端到端可信的——入站数据帧无需再单独进行 HMAC 签名（因为经过身份验证的套接字本身就已经具备了旧版 HTTP 接口所需的传输来源证明功能）。而通过中继总线进行的消息传递则发生在连接器的信任域内（与该连接器用于存储租约、缓冲区及功能信息的存储区域处于同一安全域）。

> 该接口规范的早期版本是通过带签名的**HTTP POST**请求将入站消息发送到 `gatewayEndpoint` 地址（即 `HttpGatewayDelivery` 机制，以及网关端的 `inbound_receiver` 组件），并且使用针对每个租户的专用密钥进行 HMAC 签名。但这种方式要求每个网关都必须暴露一个可访问的入站 URL，这对于没有公网 IP 的托管式网关来说是不可能的。上述基于 WebSocket 的通道传输方式已取代了旧方案；虽然为保持向后兼容性，仍会保留针对每个租户的专用密钥，但该密钥已不再用于入站消息传输。至于**直通传输层**（即二级/三级 webhook，如 Discord 交互、Twilio 接口），历史上仍使用 `gatewayEndpoint` 作为后续响应的发送地址；在第五阶段第5.1节中，这一机制也被引入 WebSocket 通道（即上述 `passthrough_forward` 数据帧），因此托管式网关完全无需暴露任何公网入站接口，等迁移完成后 `gatewayEndpoint` 也将被废弃。

### 3.1 直通传输层的请求转发（见第5.1节）

直通传输层会在连接器的边缘节点处，响应服务提供商发出的那些对延迟要求极高的确认请求（例如 Discord 在约 3 秒内返回的延迟交互响应），之后会**直接转发**原始请求至网关，且这种转发属于“发完即忘”的模式——因为服务提供商已经收到了响应，所以无需再等待回复。因此，这类请求会通过与入站消息相同的出站 WebSocket 通道传输，但使用的是 `passthrough_forward` 数据帧，而非 HTTP POST 请求。网关会通过常规的处理路径来解析该请求（例如 Discord 的交互请求会被解析为 `MessageEvent` 对象，并像普通消息一样被处理；回复则通过出站的 `/follow_up` 通道发送）。当请求在传输过程中被缓存时，`bufferId` 字段会出现（详见第五阶段第5.3节关于仅支持缓存的配置），网关会在完成持久化转接后对该请求予以确认。

### SessionSource 字段（即网络层传输的字段内容）

这些字段的定义来源为 `gateway/session.py` 文件中的 `SessionSource.to_dict()` 方法。它们代表了网关在网络层上接收到的所有字段。`platform`、`chat_id`、`chat_type`、`user_id`、`user_name`、`thread_id`、`chat_name` 以及 `chat_topic` 这些字段始终都会出现（可能值为 `null`）；其余字段则仅在被设置时才会包含在传输数据中。

| 字段 | 类型 | 是否始终发送 | 含义 |
| --- | --- | --- | --- |
| `platform` | string | 是 | 平台名称，与描述符中的 `platform` 字段对应。 |
| `chat_id` | string | 是 | 主要对话标识符（频道/聊天室），同时也是会话密钥的生成依据。 |
| `chat_type` | string | 是 | 对话类型，可选值包括 `dm`、`group`、`channel`、`thread`、`forum`。 |
| `chat_name` | string\|null | 是 | 便于人类理解的聊天室名称。 |
| `user_id` | string\|null | 是 | 消息发送者的标识符，也是会话密钥的生成依据。 |
| `user_name` | string\|null | 是 | 发送者的显示名称。 |
| `thread_id` | string\|null | 是 | 当消息位于线程中时，用于标识该线程或论坛主题的编号，同样可作为会话密钥的生成依据。 |
| `chat_topic` | string\|null | 是 | 频道或聊天室的标题/描述信息（适用于 Discord、Slack 等平台）。 |
| `user_id_alt` | string | 否 | 平台特定的备用标识符，例如 Signal 的 UUID 或飞书中的 union_id。 |
| `chat_id_alt` | string | 否 | 备用聊天标识符，例如 Signal 群组内部的内部编号。 |
| `guild_id` | string | 否 | Discord 社群、Slack 工作空间或 Matrix 服务器的层级标识。**对于实现 Discord 服务器间的消息隔离功能而言，该字段是必需的**，也可作为会话密钥的生成依据。 |
| `parent_chat_id` | string | 否 | 当 `chat_id` 指向某个线程时，用于标识该线程所在的父频道。 |
| `message_id` | string | 否 | 触发当前消息的编号（用于固定消息、回复或回应操作）。 |

> 在网关端的数据结构中存在 `is_bot` 字段，用于标识消息发送者是否为机器人或属于 webhook 请求；但在 v1 版本中，该字段**有意未包含在网络层传输的数据中**——它并不属于 `to_dict()` 方法返回的字段范围。在将该字段添加到连接器的 `SessionSource` 中之前，必须先在网关端将其加入对应结构并同步更新 `to_dict()` 方法（属于增量式扩展）。

### 各平台的 SessionSource 识别字段对照表

| 平台 | chat_id | chat_type | user_id | thread_id | guild_id |
| --- | --- | --- | --- | --- | --- |
| **Discord** | 频道编号 | `dm`/`group`/`thread` | 消息发送者编号 | 线程内的频道编号（仅在线程中存在） | **社群编号**（实现服务器间隔离功能所必需） |
| **Telegram** | 聊天室编号 | `dm`/`group`/`forum` | 发件人编号 | 论坛主题编号（仅适用于论坛） | — |

> 若将 Discord 的 `guild_id` 设置错误，就可能导致两个不同的服务器被合并到同一个会话中。这是该接口存在的首要高严重性风险。网关的 `build_session_key()` 方法是判断是否符合规范的依据：对于给定的 `SessionSource`，连接器经过标准化处理后生成的密钥，必须与 Python 适配器生成的密钥完全一致。（第一阶段的测试用例会确保输入已知数据时，生成的密钥也始终已知。）

### 机器人身份与租户的区分（单机器人服务多个租户的场景，详见附录 A）

消息数据中会携带**发送机器人的身份信息**，该字段与租户标识是相互独立的。租户身份是通过消息本身的识别字段来确定的（如 Discord 的 `guild_id`、Telegram 的 `chat_id`，以及 webhook 的路径或子域名），**绝不会**根据发送消息的令牌、套接字或进程信息来确定租户身份。这样的设计使得同一个机器人能够同时为多个租户提供服务（见第六阶段），而无需占用额外的字段空间。

### 以发送者为优先的识别机制以及账号关联（私信场景，见第七阶段）第7阶段新增了**面向用户的自助式共享机器人入职流程**，该功能改变了路由进站消息时用于确定实例的标识符，并为用户提供了绑定自己账户的管理路径。

**作者优先解析机制（多租户公会规则，D-7.2）**。一个Discord公会可容纳**多个**租户——不同成员各自关联独立的代理。因此，在消息投递时，连接器会根据**已认证的作者绑定信息**（通过`resolveByUser`，以`(tenant, platform, platform_user_id)`为键的`user_instance_binding`）来确定目标实例，而非通过公会→实例的路由方式。具体而言：

- 由**已关联**用户发送的路由消息只会送达**该用户**的实例——即便同一公会的另一位已关联用户由不同的实例处理，各自的消息也仅能送达对应实例。
- 由**未关联**用户发送的消息不会解析出任何实例，会被直接丢弃（即“失败即终止”，不会广播给公会中的其他租户）。
- 所使用的作者ID是**来自实际事件的真实`user_id`**，也就是上文提到的`SessionSource.user_id`——绝非网关主动设定的值或管理帧中携带的数值。

这正是连接器在`WsGatewayDelivery`中实施的“按`user_id`区分、仅所有者可访问”的路由机制（网关侧的多租户公会端到端驱动程序`gateway_multitenant_guild_driver.py`则是跨仓库的参考实现）。

**账户绑定（私信）路径**。用户可通过一次性代码将自身账户绑定到某个实例，该代码需通过向共享机器人发送私信来使用：

1. 账户所有者通过门户网站（或自托管CLI）触发绑定流程。连接器会为**已认证的**实例生成一个短效的**链接码**（通过`POST /manage/link`接口；instanceId来自调用方的身份凭证——即经过NAS签名的`aud=agent:{instanceId}`令牌，或是该实例自身的网关专用密钥——**绝非**请求体中的内容）。
2. 用户使用需绑定的账户，向共享机器人发送包含`/link <code>`内容的**私信**。
3. 连接器的进站消息监听器会**接收**这条私信（不会将其路由给任何代理），并利用私信事件中记录的**真实`user_id`**创建`user_instance_binding`。此后，基于作者优先解析机制，该用户的消息将直接发送到已绑定的实例。

**取消绑定由连接器掌控**。当某个实例被停用时（通过`POST /manage/deprovision`接口），其对应的作者绑定关系会被解除（因此相关用户将不再能通过该实例接收消息），同时该实例的网关专用密钥也会被撤销（导致其套接字无法再进行身份验证——下一次WS升级请求会收到**4401**错误）。如果网关在之前已成功完成握手后却收到**4401**错误，它会将其视为最终性的撤销指令：停止尝试重新连接，并将该中继平台标记为**已禁用**（不属于可重试的错误类型）。而在任何成功握手之前出现的4401错误仍属于可重试范畴（属于冷启动或尚未完成配置导致的异常，而非真正的撤销）。

### 3.2 进入空闲状态/缓冲翻转原语（§5.3）

这是一种用于实现“零规模运行”的原语（并非指实际让机器进入睡眠或暂停状态的行为——此类操作由后续的工作流处理；该原语仅负责创建相关帧）。它允许网关在进入空闲状态时，不会丢失在此期间到达的进站消息，具体做法是让连接器为该实例创建缓冲区，并在重新连接时重新投递这些消息。

相关帧共有三种（均以连接过程中**已认证的**实例唯一标识符为键——该标识符来自WS升级时存储的密钥记录，不会出现在任何帧中）：

- `{"type":"going_idle"}`（网关 → 连接器）——作为网关现有空闲状态转换过程的一部分被发送（适配器在关闭套接字之前会发送此帧）。该帧要求连接器将当前实例切换为**仅缓冲模式**。
- `{"type":"going_idle_ack"}`（连接器 → 网关）——表示连接器已完成切换：实时投递已停止，此后该实例接收的所有进站消息都将被持久存储在缓冲区中。网关会**持续提供服务，直到收到此确认帧**（因此，在切换窗口内到达的消息仍能实时投递，不会丢失——这与消息总线所遵循的“先订阅再投递”顺序规则一致）。只有在收到确认帧后，才能安全地关闭连接。
- `{"type":"inbound_ack", "bufferId"}`（网关 → 连接器）——表示已成功接收并持久存储了通过缓冲区投递的进站消息（该消息会携带其`bufferId`，在重新连接时会被重新投递）。连接器只有在收到此帧后才会确认该缓冲条目，从而在**投递环节实现无重复处理**：如果在进入空闲状态过程中实例意外关闭，系统只会重新投递那些尚未被确认的未处理消息；而已被确认的条目则不会再被重复投递。

**缓冲与清空机制**。在处于仅缓冲模式时，连接器会将新收到的进站消息追加到该实例对应的持久性投递缓冲区中（路径为`delivery:<instanceId>`），而非立即进行实时投递。当网关**重新连接**时（即在意外断开后通过全新的重连循环重新拨号并完成握手），新的握手请求会促使连接器按顺序、在收到确认后再通过新建立的套接字清空缓冲区中的积压消息，之后再取消仅缓冲模式，从而恢复实时投递。这一机制与Discord→连接器之间的消息接收流程所使用的“无重复清空”逻辑相同，只是应用在了连接器→网关的投递环节。整个过程始终由连接器掌控：网关只能对自己拥有的实例执行切换/清空操作。

> 不在本功能范围之内（待实现的功能）：自动决定进入空闲状态的定时器、实际的机器暂停机制，以及NAS实现的健康状态监控模型。该原语仅定义了“当网关进入空闲状态时，中继层应切换为缓冲模式，并在重新连接时重新投递消息，且不会造成消息丢失或重复”；而触发空闲状态的具体机制则不在其范畴之内。

### 3.3 唤醒操作（§5.2）

这是睡眠/唤醒循环的另一半：用于让处于**暂停状态**的网关知晓自己有缓冲中的待处理消息。这也是一种原语——此处并不涉及任何机器暂停操作；它仅负责建立唤醒信号，以便未来的零规模运行功能层能够基于“缓冲消息 ⇒ 唤醒信号”这一机制来工作。

- **注册流程**。网关在注册/配置阶段需指定一个**唤醒URL**——即连接器可以通过GET请求访问以唤醒该网关的任何可访问地址（例如Fly平台的自动启动主机地址，或控制面板主机地址）。对于自托管场景，可使用命令`hermes gateway enroll --wake-url <url>`进行设置（或通过`GATEWAY_RELAY_WAKE_URL`/`gateway.relay_wake_url`参数设置）；对于托管型或NAS管理的网关，该URL会与`GATEWAY_RELAY_URL`一同被写入容器环境变量中。在 `/relay/provision` 请求的请求体中，该URL会以`wakeUrl`的名称被传递，并由连接器存储在其密钥记录中（该URL由网关提供，但具有严格的访问限制——其权限范围与`instanceId`相同；由于组织/租户身份仍需通过令牌验证，因此网关只能为自己拥有的实例注册唤醒目标）。该唤醒URL与已废弃的`gatewayEndpoint`不同：它是一个**唤醒目标**，而非消息投递目标。
- **唤醒操作本身**。当处于仅缓冲模式（即进入空闲状态）的目标实例收到第一个缓冲中的消息时，连接器会**直接**向该实例注册的`wakeUrl`发送一个**不带有效载荷、未签名**的GET请求（不会通过NAS中间件传递——因此中继层仍保持与NAS解耦的状态）。该请求不包含任何租户相关数据，也不携带进站消息，仅表示“你有缓冲中的待处理消息，请重新连接”。当网关再次尝试建立连接时（即通过已认证的WS升级流程），租户身份会以常规方式重新验证，因此即使唤醒URL被泄露或被猜测，最多也只会导致该网关尝试重新连接自己的实例。该唤醒操作会对每个实例进行速率限制（每个冷却周期内仅允许一次唤醒请求，而非针对每条消息都触发一次），且属于尽力而为的机制——如果唤醒请求失败，系统也会忽略该请求；网关仍会在下次自动重新连接时尝试清空缓冲区。该操作不会生成新的消息帧：唤醒操作是通过独立的HTTP GET请求实现的，而非通过中继WS消息发送的（因为此时套接字已断开——这正是该机制的设计初衷）。

> 不在本功能范围之内（待实现的功能）：实际的机器暂停操作（Fly平台中的`autostop:"suspend"`命令），以及自动决定让机器进入睡眠状态的定时器。该原语仅定义了“处于睡眠状态的实例有缓冲消息时，其唤醒URL会被触发”；而决定让实例进入睡眠状态（以及之后再次唤醒以恢复服务）的逻辑则属于功能层的职责。

### 3.4 对未来零规模运行功能层的要求

§3.2和§3.3部分提供了相应的**原语**；本节则规定了**另一个专门负责实现零规模运行功能的团队在安全使用这些原语时必须遵守的契约**。该团队负责做出是否暂停实例的**决策**、执行实际的机器暂停操作，以及设计平台/健康状态监控模型——这些内容并未在这些原语中定义——但它**必须满足以下保障条件**，这些条件也是这些原语所依赖的：

1. **在实例被暂停之前，必须先注册一个`wakeUrl`**。如果某个已暂停的实例没有注册唤醒URL，那么它就相当于一个“黑洞”——缓冲中的进站消息永远不会触发唤醒操作，因此该实例会一直处于睡眠状态，直到有其他实例重新连接它。功能层必须确保在允许暂停之前，已注册一个可访问的唤醒目标（自托管场景下通过`--wake-url`参数设置；托管场景下则由系统自动添加），并将其作为暂停操作的前提条件。如果机器处于暂停状态时该唤醒URL无法访问（例如指向的是处于暂停状态的机器本身，且没有平台自动启动机制），那么该URL就等同于不存在。
2. **在关闭套接字或暂停实例之前，必须先通过`going_idle`状态完成消息清空，并等待收到`going_idle_ack`确认**。绝不能在尚未收到确认的情况下就暂停实例。该确认帧是连接器发出的，表示该实例的投递功能现已完全切换为仅缓冲模式；如果在发送`going_idle`请求后但在收到确认帧之前就暂停实例，那么那些在切换过程中到达的进站消息可能会被丢失。网关本身已在Q-5.3c部分规定，只有在收到确认帧后才能关闭套接字；因此暂停操作必须等待完整的消息清空流程完成后才能执行，绝不能与之并行。
3. **在暂停实例之前，必须确保新的重连循环处于活跃状态**。唤醒→清空的契约要求是“触发唤醒 → 网关重新拨号 → 连接器在重新连接握手时清空缓冲区”。如果重连循环被禁用，那么唤醒信号虽然已发送，但机器却不会重新拨号，导致缓冲区中的消息无法被处理。功能层绝不能对那些其中继传输层在收到唤醒信号后不会重新连接的实例进行暂停操作。
4. **在健康状态监控模型中，必须将“暂停状态”视为与“关闭状态”不同的状态（Q-5.3b）**。处于暂停状态的实例仍属于“健康睡眠”状态，而非故障状态。健康/监控层必须能够区分这两种状态（例如通过平台记录的机器状态来实现），这样才能避免对处于暂停状态的实例进行重启、发送警报或标记为异常状态——否则就会破坏暂停机制的初衷，还可能引发与唤醒/清空流程的冲突。
5. **唤醒操作属于尽力而为的机制，并且会受到速率限制——切勿假设一定会立即收到唤醒信号**。每个实例在每个冷却周期内最多只能被唤醒一次，而且如果唤醒请求失败，系统也会忽略该请求。功能层绝不能将唤醒操作视为一种可靠或即时的信号；系统的正确性仍然取决于“网关会在下次重新连接时自动清空缓冲区”这一原则。如果需要更可靠的唤醒机制（例如通过定时任务来触发重新连接），那也是功能层的职责，而非原语的职责。
6. **只有在真正处于空闲状态时才进行暂停操作——而且空闲状态必须由连接器检测，而非由网关猜测**。究竟什么情况算作空闲状态（即没有正在处理的请求，且连续N分钟没有新的进站消息）是由功能层根据自身策略来确定的，但它必须与现有的清空机制相协调（例如基于`gateway_state`中“运行中”或“正在清空”等状态），而不能引入另一种独立于现有机制的、仅用于检测空闲状态的路径——这与§3.2部分对`going_idle`状态所规定的集成约束是相同的。这些是行为层对基础组件所承担的保证；而基础组件仅需履行§3.2/§3.3中已规定的义务（在空闲时触发操作、为每个实例提供持久缓冲区并配合确认机制进行重连，以及针对已触发状态的实例在首个缓冲事件到达时发起唤醒）。

## 4. 出站：动作集

网关通过动作字典调用传输层。权威来源为：
`gateway/relay/transport.py` + `gateway/relay/adapter.py`。

| `op` | 字段 | 返回结果 |
| --- | --- | --- |
| `send` | `chat_id`, `content`, `reply_to?`, `metadata?` | `{success: bool, message_id?, error?}` |
| `edit` | `chat_id`, `message_id`, `content`, `metadata?` | `{success: bool, error?}` |
| `typing` | `chat_id` | `{success: bool}` |
| `follow_up` | `session_key`, `kind`, `content`, `metadata?` | `{success: bool, message_id?, error?}` |

`get_chat_info(chat_id)` 是一个独立的代理调用，至少返回 `{name, type}`。媒体相关动作采用相同的结构格式（将在后续协议修订中进一步细化，属于可叠加内容）。

**`follow_up`（A2能力动作）。**某些入站数据包会携带用于操作**共享**机器人身份的凭证（例如Discord交互续传令牌）。根据§6规定，连接器会在边缘层移除该凭证，并将其按会话键存储在自身的能力库中——该凭证**绝不会传递到网关**。若要使用此功能，网关需发起`follow_up`请求，指定其当前所处的**会话键**以及能力类型`kind`（例如`discord.interaction_token`）——**绝不能传递令牌本身**。连接器会从其能力库中获取真实值，验证租户匹配性（租户B无法使用租户A的能力），随后将数据发送出去。当对应能力不存在/已过期或租户不匹配时，返回`success: false`——按设计，网关无需进行重试（泄露的网关不会持有任何能力相关数据）。权威来源：
`gateway/relay/transport.py` (`send_follow_up`) + `gateway/relay/adapter.py`。

## 5. 中断（`/stop`）路由

- **网关 → 连接器：**通过出站WS发送`send_interrupt(session_key, reason?)`请求，以在当前对话过程中触发 `/stop` 操作。根据路由不变性，连接器**必须**将此请求转发给正在处理该`session_key`的网关实例。
- **连接器 → 网关：**针对某个`session_key`的入站中断请求会以`interrupt_inbound`帧的形式通过网关的出站WS传递（参见§3中的传输说明）——通过中继总线跨实例路由至持有该套接字的实例——随后由适配器的`on_interrupt(session_key, chat_id)`函数将其接入现有的会话级中断机制，从而取消当前对话流程（其他对话不受影响）。

两种方向的通信均通过网关的出站WS进行：网关→连接器的 `/stop` 请求通过该通道发送，而连接器→网关的中断请求则作为标准化事件通过相同的**入站回传通道**传输。

## 6. 信任边界与签名体处理（A2）

**连接器是唯一的加密/身份边界。网关不会对任何内容进行重新验证。**

Webhook签名（Discord的ed25519、Twilio的HMAC、WeCom的BizMsgCrypt）是基于原始字节直接计算的，部分数据包还会使用共享密钥进行**加密**。连接器为多个租户托管同一个**共享**机器人，并保存每个租户的平台密钥，因此它会：

- 在边缘层进行**验证/解密**（这是密钥存储的唯一位置）；
- 将数据包**标准化**为针对特定租户的`MessageEvent`格式（参见§3）；
- 从数据包中移除任何与共享身份相关的能力信息，并将其按会话键存储在自身的能力库中（参见§4中的`follow_up`说明）；
- **仅转发经过清洗的`MessageEvent`**——绝不会传递原始的签名体。

因此，网关在中继路径上不会对平台签名或加密内容进行任何验证，而是直接信任标准化后的事件。这是网关端强制遵循的不变性（参见`tests/gateway/relay/test_relay_sheds_crypto.py`：中继模块不会导入或调用任何平台级加密功能）。

**为何不“逐字节转发签名体以便网关重新验证”？**
在不可信且可被替换的租户网关环境下，这种方案存在问题：

- 要重新验证Twilio的HMAC或WeCom的加密内容，就必须将**共享签名密钥**交给网关——而这本身就是安全漏洞，且在共享机器人场景下会导致**跨租户信息泄露**；
- WeCom的数据包是使用共享密钥加密的，连接器仅为路由目的需在边缘层解密，因此若转发密文同样需要将密钥交给网关；
- Discord的交互令牌位于签名后的JSON体内部——你无法同时保留原始字节并移除该凭证，因为二者是同一组字节。

因此，故意放弃了字节级保留的做法：连接器会对清洗后的事件进行重新序列化，网关则直接信任该事件。这种方式还将直通传输与中继传输统一起来——两者均遵循“在边缘层验证 → 发送标准化事件”的原则，仅在传输方式上有所区别。完整的A2设计思路及连接器端的存储机制详见`docs/capability-trust-boundary.md`（连接器代码库位于`gateway-gateway`）。

### 6.1 频道认证（连接器⇄网关连接本身）

在A2架构中，由于网关可能是**由客户自行管理且暴露在互联网上**的，因此连接器成为平台密钥的唯一持有者，故连接器⇄网关之间的连接本身也需要进行认证。网关会持有由注册或配置流程生成的**每个网关专用的密钥**（通过`hermes gateway enroll`命令传递给连接器，路径为`/relay/enroll`；或通过自主配置生成，路径为`/relay/provision`），该密钥用于验证其出站WS升级请求。认证机制采用HMAC-SHA256算法，并配有多密钥轮换验证列表（网关端代码位于`gateway/relay/auth.py`；连接器端代码位于`src/core/relayAuthToken.ts`）。

| 通信方向 | 凭证 | 认证机制 |
|---------|------|----------|
| 网关 → 连接器WS升级请求 | 每个网关专用的密钥 | 在`/relay`升级请求中携带`Authorization`类型的Bearer头部。令牌格式为`base64url(payload:exp:sig)`，其中`payload = gatewayId`，`sig = HMAC(payload:exp, secret)`。连接器会验证该令牌，若存在不匹配、缺失或已被撤销的情况，则拒绝升级请求并返回**4401错误码**。经过认证的租户信息来自连接器的存储库，而非`hello`帧中传递的信息。 |
| 连接器 → 网关入站请求（`inbound`/`interrupt_inbound`帧） | 无（利用已认证的WS通道传输） | 入站请求通过网关已认证的出站套接字直接发送（参见§3），因此无需为每条消息单独签名。虽然注册或配置时仍会为每个租户生成**专用传输密钥**以保持向后兼容性，但该密钥不再用于对入站请求进行签名。 |

这就是**通道级**认证机制——与平台级加密不同，中继路径仍完全不涉及平台级加密（参见§6）。网关不会持有任何平台级密钥；每个网关专用的密钥仅用于验证连接器连接的安全性。完整的威胁模型以及注册、密钥轮换和紧急关闭机制的设计详见`docs/connector-gateway-auth-design.md`（连接器代码库位于`gateway-gateway`）。

## 7. 每个实例的交付机制与管理平面（第6阶段）

第1–5阶段将连接器视为单租户前端：针对某个租户的入站事件会直接发送到该租户的网关套接字。**第6阶段实现了按实例交付**——同一个共享机器人可以在一个租户下为多个用户/代理提供服务（例如一个Discord群组或一个Telegram机器人），而不会发生跨实例数据传递——同时还引入了一个小型**管理平面**，供代理或托管Portal用于指定“谁可以查看什么内容”以及“哪些内容是相关内容”。所有这些功能均位于**连接器端**；网关唯一需要承担的新职责是在启动时声明自身的**相关性策略**（参见§7.3）。

### 7.1 交付判定机制（连接器端，仅用于信息传递）

对于每条入站事件，连接器会通过组合三个“与”逻辑的过滤条件来确定哪些实例应该接收该事件。这些逻辑并非由网关实现——它们在连接器端运行——但它们定义了网关所依赖的交付规则：

| 判定层 | 判断问题 | 权威来源 |
|-------|----------|----------|
| **所有者/范围 ∧ 主体** | 该实例是否有权查看该消息的发送者？ | 每个用户的`user_id → instance`绑定关系（即所有者层级） + 每个实例的`(guild, channel)`范围授权设置 + `owner-only`/`allow-list`/`any`类型的主体策略。 |
| **可见性层级** | 该实例的所有者是否真的有权在Discord中查看该频道？ | Discord当前的ACL权限设置（实际生效的权限），采用“一旦不符合条件即拒绝”的策略。此层用于缩小过宽的范围授权范围。 |
| **相关性** | 在满足前两个条件的前提下，代理是否应该处理该消息？ | 根据§7.3中声明的相关性策略（如地址过滤、自由回复模式、允许机器人参与等）。 |

这些组合规则仅用于**缩小**可交付的消息范围（`deliver ⇔ authorized ∧ visible ∧ relevant`）；**所有者层级会直接绕过相关性判定**（发送者自己的消息始终会送达其自身的实例——因为你无法@提及自己的代理）。未被授权用户发送的消息则不会送达任何实例（直接拒绝）。完整的设计思路及相关不变量均位于连接器代码库`NousResearch/gateway-gateway`中；本节仅为面向网关方的概述。

### 7.2 管理接口（连接器端，需身份认证）

连接器会提供经过身份认证的管理接口。这些接口与WS升级过程采用相同的**双重认证机制**：要么是经过NAS签名的、带有`aud=agent:{instanceId}`字段的RS256 JWT令牌，**要么**是网关自身的每个网关专用密钥生成的Bearer令牌（参见§6.1中的`make_upgrade_token`函数）。在这两种情况下，连接器都会从其**存储的**记录中获取权威的`{tenant, instanceId}`信息——**绝不会**从请求体中获取（请求体中声明的`instanceId`将被忽略）。

| 接口路径 | 功能 |
|---------|------|
| `POST /manage/link` | 生成一个短期有效代码，用于将平台账户与已认证的实例绑定（即`/link <code>`流程；连接器会从入站事件中读取经过认证的`user_id`）。 |
| `POST /manage/scope`, `/manage/scope/release` | 为已认证的实例申请或释放`(guild, channel)`范围授权。一个频道最多只能被一个实例拥有（非重叠关系是该关系的关键约束）。 |
| `POST /manage/principal` | 设置该实例的主体策略，可选值为`owner-only`、`allow-list`或`any`。 |
| `POST /manage/dm-default` | 设置用户的默认私信接收实例（当用户关联了多个实例时，用于确定私信消息的默认接收方）。 |
| `POST /relay/policy` | 声明该实例的**相关性策略**（参见§7.3）。 |

这些接口均属于连接器管理范围（管理平面并不属于网关代理的处理流程）；网关仅需要调用`POST /relay/policy`接口（参见§7.3）。其余接口则由托管Portal或`hermes` CLI驱动。

### 7.3 相关性策略声明（网关的职责）

相关性判定层（§7.1）实际上相当于为网关自身的行为参数（如`require_mention`、`free_response_channels`、`{PLATFORM}_ALLOW_BOTS`等）定义了针对每个租户的统一规则。因此，用于中继交付的规则与这些参数一致，网关会将这些参数转换为**与具体平台无关的策略**，并在启动时（在获取到每个网关专用的密钥之后）通过`POST /relay/policy`接口将其上传。

相关代码位于`gateway/relay/__init__.py`中的`relay_relevance_policy()`函数及`send_relay_policy()`函数中。| 字段 | 类型 | 来源 | 含义 |
| --- | --- | --- | --- |
| `platform` | 字符串 | `relay_platform_identity` | 该策略适用的平台。 |
| `requireAddress` | 布尔值 | `require_mention` | 非所有者发送的消息必须@提及或回复机器人，才被视为有效内容。 |
| `freeResponseScopes` | 字符串数组 | `free_response_channels` | 可免除`requireAddress`要求的范围（频道）ID列表。其范围词汇与§7.1中定义的范围权限相同。 |
| `allowOtherBots` | 布尔值 | `{PLATFORM}_ALLOW_BOTS ∈ {mentions, all}` | 是否允许机器人发送的消息通过（默认为关闭）。 |

认证信息为每个网关专用的升级令牌（参见§6.1），因此连接器会将该策略附加到已通过认证的实例上。网关是**唯一真实的数据来源**，并在**每次启动时**重新声明策略（即完全替换策略，类似于配置阶段对`routeKeys`的更新操作——具备自修复功能）。当策略全部为默认值时，网关不会发送任何数据（因为连接器的空行默认设置已与之匹配）。该POST操作采用**容错机制**：出现故障时会记录日志并继续启动流程——相关性判断是建立在授权机制之上的优化层（参见§7.1），并非启动流程的必要条件。此机制**不新增网关入口**，也**无需新的凭证**——它直接复用每个网关的专用密钥以及与 `/relay/provision` 相同的服务器。

> 相关性判断会在连接器唤醒已缩减到零规模的代理（第5阶段）**之前**完成，因此被排除的聊天内容永远不会触发代理启动——相关性既是实现规模缩减的主要手段，也是确保内容准确性的过滤机制。

## 8. 策略版本控制

- `contract_version`为整数；仅在实验阶段进行**增量式修改**时才需升级版本（如新增可选字段、新的操作类型等）。
- 若出现破坏性变更（如字段重命名/删除、语义改变），则需同时协调更新两个代码库并提升版本号。
- 连接器提交的第一个拉取请求需注明其所依据的该文件的提交SHA值。
