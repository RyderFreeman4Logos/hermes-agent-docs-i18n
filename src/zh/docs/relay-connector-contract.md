# 中继 ↔ 连接器合约（v1，实验性版本）

> **状态：** 实验性版本。在至少有两个真实的一级平台（Discord + Telegram）对其完成验证之前，该合约**可能在不经过废弃周期的情况下发生变更**。在实验阶段，合约的演进仅允许**增量式修改**，且必须通过 `contract_version` 进行控制；若出现破坏性变更，则需同步更新两个代码仓库。

本文档是 **Hermes 网关**（Python，位于 `gateway/relay/` 目录）与 **连接器**（Node/TypeScript，位于 `NousResearch/gateway-gateway` 目录）之间的正式接口规范。连接器实现者首先需要阅读此文件。

网关会运行一个通用的 `RelayAdapter`，该适配器会**主动向外连接**连接器，在握手阶段接收 `CapabilityDescriptor`，之后通过每轮双向 WebSocket 交换标准化的 `MessageEvent`（入站消息）以及各种操作指令（出站指令）。网关永远不会知晓自身所对接的具体平台是哪一个；所有与特定平台相关的套接字及身份识别逻辑均由连接器负责处理。

---

## 1. 握手流程

1. 网关建立传输连接（调用 `connect` 方法）。
2. 网关调用 `handshake()` 方法，连接器则返回一个 `CapabilityDescriptor`（见第 2 节），其中描述了该适配器实例所对应的目标平台信息。
3. 网关根据该描述符配置适配器的相关参数（如字符限制、长度单位、草稿功能、编辑功能、线程功能及 Markdown 支持情况），并注册入站消息处理函数。
4. 此后，连接器开始流式发送入站事件，并接收网关发出的出站操作指令。

`contract_version` 字段（当前值为 `1`）会包含在描述符中。为保证向前兼容性，网关会忽略描述符中不存在的字段；对于缺失的可选字段，则会使用默认值进行填充。

## 2. CapabilityDescriptor（握手数据载荷）

该数据为 JSON 格式，其定义来源为 `gateway/relay/descriptor.py` 文件。

| 字段 | 类型 | 是否必填 | 含义 |
| --- | --- | --- | --- |
| `contract_version` | int | 是 | 合约版本号（同一版本内仅允许增量式修改）。 |
| `platform` | string | 是 | 平台名称，例如 `"discord"` 或 `"telegram"`。 |
| `label` | string | 是 | 便于人类理解的标签名称。 |
| `max_message_length` | int | 是 | 字符限制上限；网关会将其暴露为 `MAX_MESSAGE_LENGTH` 属性。若该值为 0，则视为 4096 字符。 |
| `supports_draft_streaming` | bool | 是 | 是否支持原生的草稿流式预览功能。 |
| `supports_edit` | bool | 是 | 是否支持基于编辑功能的流式传输；若该值为 false，则接收方只能以每段一条消息的方式处理数据。 |
| `supports_threads` | bool | 是 | 是否具备 `create_handoff_thread` 功能。 |
| `markdown_dialect` | string | 是 | Markdown 语法版本，可选值包括 `"plain"`、`"markdown_v2"`、`"discord"` 等；该字段还会决定 `supports_code_blocks` 的取值。 |
| `len_unit` | string | 是 | 长度计量单位，可选值为 `"chars"`（使用内置字符计数）或 `"utf16"`（Telegram 使用的 UTF-16 代码单元）。 |
| `emoji` | string | 否 | 显示用的表情符号，默认值为 🔌。 |
| `platform_hint` | string | 否 | 系统提示用的语境描述，用于辅助识别平台类型。 |
| `pii_safe` | bool | 否 | 是否会在会话描述中自动遮蔽个人身份信息。 |

大多数字段实际上都是从网关现有的 `PlatformEntry` 对象中提取而来的；而那些仅在运行时才需要的字段（如 `len_unit`、`supports_*` 系列字段以及 `markdown_dialect`）则直接来自对应平台适配器的功能方法。

## 3. 入站消息：`MessageEvent` 数据结构

连接器会将每个来自不同平台的原始消息事件统一转换为标准的 `MessageEvent` 对象（定义位于 `gateway/platforms/base.py` 文件中），然后再将其发送给网关。入站消息是通过网关的**出站方向 `/relay` WebSocket** 传输的（详见下文的传输机制说明）——连接器会通过网关已建立的套接字，向该 WebSocket 发送 `inbound` 类型的数据帧。网关会利用嵌入在消息中的 `SessionSource` 对象通过 `build_session_key()` 方法生成会话密钥；因此，正确设置各类识别字段是连接器必须履行的最重要职责。

### 入站传输机制（使用 WebSocket 通道，而非 HTTP）

网关会**主动向外连接**连接器的 `/relay` WebSocket，用于执行握手、发送出站操作指令（见第 4 节）以及发起自身的 `/stop` 停止请求（见第 5 节）。而入站消息则通过同一套接字的**反向通道**传输：连接器会通过网关的出站 WebSocket 发送 `inbound` 类型的数据帧（若需要中断入站传输，则会发送 `interrupt_inbound` 数据帧，见第 5 节）。网关**没有专门的入站 HTTP 接口**——托管式的网关无需也无法暴露任何入站端口；所有数据都通过其主动建立的连接进行传输。

**多实例路由机制。**负责处理某个平台消息的连接器实例（即生成入站事件的实例），通常**并非**网关主动建立出站 WebSocket 连接的那个实例。因此，生成消息的实例会将该事件发布到连接器内部的**中继总线**上（基于 Redis 的发布/订阅机制，相关实现位于 `src/core/relayBus.ts` 文件中的 `RelayBus` 类）。每个连接器实例都会订阅该总线，并将接收到的每条消息路由到对应租户的**本地会话**中（通过 `RelayServer.routeBusMessage` 方法实现）；最终，只有持有网关套接字的那个实例才会处理该消息，而那些没有该租户本地会话的实例则不会执行任何操作。因此，跨实例的消息传递实际上只是在同一集群内的 Redis 通信，而非公共 HTTP 调用。

连接器向网关发送的数据帧格式如下（通过 WebSocket 传输）：

- `{"type":"inbound", "event": <MessageEvent>, "bufferId"?}`
- `{"type":"interrupt_inbound", "session_key", "chat_id"}`（用于中断入站传输，见第 5 节）
- `{"type":"passthrough_forward", "forward": <PassthroughForward>, "bufferId"?}`（用于转发请求，见第 5.1 节）

`PassthroughForward` 数据结构代表了转发请求的原始格式（即二级/三级 webhook 请求的格式，例如 Discord 的交互请求或 Twilio 的请求），其结构为 `{platform, botId, method, path, headers: [[k,v],…], bodyB64}`。请求体采用 Base64 编码，这样即使数据以换行符分隔的 JSON 格式传输，其中的任意字节也能完整保留；网关会对该数据进行 Base64 解码，从而得到连接器发送来的原始字节数据（连接器已在边缘节点处验证了提供方的签名，并去除了任何共享身份凭证——见第 6 节），因此网关只需重新处理经过净化、已去除令牌的数据，再通过无需令牌的 `follow_up` 处理路径来执行相应操作。更多细节请参见第 3.1 节。

**信任机制。** WebSocket 升级过程会使用网关为每个网关配置的专用密钥进行身份验证（见第 6.1 节），因此整个通信通道是端到端可信的——入站数据帧无需再单独进行 HMAC 签名（因为经过身份验证的套接字本身就已经具备了旧版 HTTP 接口所需的每条消息来源证明功能）。而通过中继总线进行的传输则发生在连接器自身的信任域内（与该连接器的租约、缓冲区及能力信息存储处于同一安全域）。

> 该合约的早期版本是通过向 `gatewayEndpoint` 发送经过签名的 **HTTP POST** 请求来实现入站消息传递的（即 `HttpGatewayDelivery` 机制，配合网关端的 `inbound_receiver` 组件），并且会使用针对每个租户的专用密钥对请求进行 HMAC 签名。但这种方式要求每个网关都必须公开一个可访问的入站 URL，而托管式的网关由于没有公共 IP 地址，根本无法满足这一要求。因此，上文所述的 WebSocket 通道机制取代了旧方案；虽然为保持向前兼容性，仍会保留针对每个租户的专用密钥，但该密钥已不再用于入站消息传输。至于**转发平面**（即二级/三级 webhook 请求，例如 Discord 的交互请求或 Twilio 的请求），历史上仍然使用 `gatewayEndpoint` 作为请求发送后的后续处理地址；在第五阶段的第 5.1 节中，这类转发请求也被改由 WebSocket 通道来处理（即上文提到的 `passthrough_forward` 数据帧），这样一来，托管式的网关就完全不需要暴露任何公共入站接口，而 `gatewayEndpoint` 也将在过渡完成后被废弃。

### 3.1 转发平面的请求转发机制（见第 5.1 节）

在转发平面中，系统会在连接器的边缘节点处立即响应提供方发出的、对延迟敏感的 ACK 请求（例如 Discord 在约 3 秒内返回的延迟交互响应），随后会**直接将原始请求转发**给网关，且这种转发属于“发送即忘”型操作——因为提供方已经收到了响应，所以无需再等待网关的回复。因此，这类请求会通过与入站消息相同的出站 WebSocket 通道进行传输，但使用的是 `passthrough_forward` 类型的数据帧，而非 HTTP POST 请求。网关会通过其常规的处理路径来解析该请求（例如，Discord 的交互请求会被解析为 `MessageEvent` 对象，并像普通消息一样被处理；回复则通过出站的 `/follow_up` 通道发送）。当该请求在转发过程中被缓存时，`bufferId` 字段会出现（对应第五阶段的第 5.3 节中关于仅缓存处理的机制），网关会在完成持久化传递后对该请求予以确认。

## 4. 出站操作：操作指令集

网关会通过传输层发送包含操作指令的字典结构。相关实现代码位于 `gateway/relay/transport.py` 和 `gateway/relay/adapter.py` 文件中。| `op` | 字段 | 返回结果 |
| --- | --- | --- |
| `send` | `chat_id`, `content`, `reply_to?`, `metadata?` | `{success: bool, message_id?, error?}` |
| `edit` | `chat_id`, `message_id`, `content`, `metadata?` | `{success: bool, error?}` |
| `typing` | `chat_id` | `{success: bool}` |
| `follow_up` | `session_key`, `kind`, `content`, `metadata?` | `{success: bool, message_id?, error?}` |

`get_chat_info(chat_id)` 是一个独立的代理调用，至少会返回 `{name, type}`。媒体相关操作也采用相同的结构格式（具体细节将在后续的协议修订中补充）。

**`follow_up`（A2 能力操作）。**某些传入的请求数据会携带用于操作**共享**机器人身份的凭证（例如 Discord 交互跟进令牌）。根据第 6 条规定，连接器会在边缘层移除这些凭证，并将其存储在以会话为键的能力存储库中；这些凭证**绝不会传递到网关**。要使用该功能，网关需要发出 `follow_up` 请求，其中需指定**当前所处的会话**（`session_key`）以及能力类型 `kind`（例如 `discord.interaction_token`）——**绝不能直接传递令牌本身**。连接器会从其存储库中获取真实的凭证值，检查租户是否匹配（租户 B 绝不能使用租户 A 的能力），之后再将请求发出。如果该能力不存在/已过期或租户不匹配，则返回 `success: false`——按设计，网关没有可重试的内容（泄露的网关不会持有任何能力相关数据）。相关实现代码位于：`gateway/relay/transport.py`（`send_follow_up` 函数）和 `gateway/relay/adapter.py`。

## 5. 中断（`/stop`）路由机制

- **网关 → 连接器：**网关会通过出站 WebSocket 发送 `send_interrupt(session_key, reason?)` 请求，以在对话进行中插入 `/stop` 指令。根据路由规则，连接器**必须**将此请求转发给正在处理该 `session_key` 的网关实例。
- **连接器 → 网关：**针对某个 `session_key` 的中断请求会以 `interrupt_inbound` 数据帧的形式，通过网关的出站 WebSocket 传入（参见第 3 条传输说明）——通过中继总线在各个实例之间路由，直到找到持有对应套接字的实例——随后由适配器的 `on_interrupt(session_key, chat_id)` 函数将其接入现有的会话级中断处理机制，从而取消当前正在处理的对话（其他对话不受影响）。

两种方向的通信均基于网关的出站 WebSocket：网关→连接器的 `/stop` 请求通过该通道发送，而连接器→网关的中断请求则作为标准化事件，通过相同的**入站回传通道**传输。

## 6. 信任边界与签名体处理（A2）

**连接器是唯一的加密/身份验证边界。网关不会对任何内容进行重新验证。**

Webhook 签名（Discord 的 ed25519、Twilio 的 HMAC、WeCom 的 BizMsgCrypt）是基于原始字节直接计算的，部分请求数据还会使用共享密钥进行**加密**。连接器为多个租户托管同一个**共享**机器人，并保存所有租户的平台密钥，因此它会：

- 在边缘层对数据**进行验证/解密**（因为密钥仅存储在此处）；
- 将请求数据**标准化**为针对特定租户的 `MessageEvent` 对象（参见第 3 条）；
- 从请求数据中移除任何与共享身份相关的能力信息，并将其存储在以会话为键的能力存储库中（参见第 4 条的 `follow_up` 说明）；
- **仅转发经过清洗的 `MessageEvent` 对象**——绝不会传输原始的签名体。

因此，网关在数据中转过程中**不会**对平台签名或加密内容进行任何验证，而是直接信任标准化后的事件。这是网关端强制遵循的规则（参见 `tests/gateway/relay/test_relay_sheds_crypto.py`：中继模块不会导入或调用任何平台级加密函数）。

**为何不“逐字节转发签名体以便网关重新验证”？**
在不可信且可被替换的租户网关环境下，这种方案是行不通的：

- 要重新验证 Twilio 的 HMAC 或 WeCom 的加密内容，就必须将**共享的签名密钥**交给网关——而这本身就是安全漏洞，而在共享机器人场景下，这会导致**跨租户信息泄露**；
- WeCom 的请求数据是使用共享密钥加密的；连接器仅为路由目的就需要在边缘层解密，因此如果转发加密后的数据，同样需要将密钥交给网关；
- Discord 交互令牌就存在于签名的 JSON 数据体内部——你无法同时保留原始字节和移除该凭证，因为它们是同一组字节。

因此，刻意放弃了字节级保留的做法：连接器会对清洗后的事件进行重新序列化，网关则直接信任该事件。这种方式也实现了透传模式与中继模式的统一——两者都遵循“在边缘层验证 → 发送标准化事件”的原则，仅在传输方式上有所不同。完整的 A2 设计理念及连接器端的存储机制详见 `docs/capability-trust-boundary.md`（连接器代码库位于 `gateway-gateway`）。

### 6.1 频道身份认证（连接器⇄网关通道本身）

在 A2 模型中，连接器是平台密钥的唯一持有者，而网关可能是**由客户自行管理且暴露在公网上的**，因此连接器与网关之间的通道本身也需要进行身份认证。网关会持有由注册或配置流程生成的**每个网关专用的密钥**（通过 `hermes gateway enroll` 命令传递给连接器，路径为 `/relay/enroll`；或者通过自助配置生成，路径为 `/relay/provision`），该密钥用于验证其出站 WebSocket 升级请求。认证机制采用 HMAC-SHA256 算法，并配有多密钥轮换验证列表（网关端代码位于 `gateway/relay/auth.py`，连接器端代码位于 `src/core/relayAuthToken.ts`）。

| 通信方向 | 凭证 | 认证机制 |
|---------|-------|---------|
| 网关 → 连接器 WebSocket 升级 | 每个网关专用的密钥 | 在 `/relay` 升级请求中添加 `Authorization` 类型的承载头。令牌的格式为 `base64url(payload:exp:sig)`，其中 `payload = gatewayId`，`sig = HMAC(payload:exp, secret)`。连接器会验证该令牌，若存在匹配问题、令牌缺失或已被撤销，则拒绝升级请求并返回 **4401 错误码**。经过认证的租户信息来自连接器的存储库，而非 `hello` 数据帧。 |
| 连接器 → 网关 入站请求（`inbound`/`interrupt_inbound` 数据帧） | ——（利用已认证的 WebSocket 通道传输） | 入站请求会通过网关已认证的出站套接字直接发送（参见第 3 条），因此无需为每条消息单独签名。虽然注册或配置时仍会为每个租户生成**专用传输密钥**以保持向后兼容性，但该密钥不再用于对入站请求进行签名。 |

这就是**通道级**的身份认证机制——它与平台级加密是不同的概念，因为数据中转路径仍然完全不涉及平台级加密（参见第 6 条）。网关不会持有任何平台密钥；每个网关专用的密钥仅用于验证连接器与网关之间的连接。完整的威胁模型以及注册、密钥轮换和紧急关闭机制的设计详见 `docs/connector-gateway-auth-design.md`（连接器代码库）。

## 7. 版本控制策略

- `contract_version` 是一个整数；仅在实验阶段出现**新增内容**时才增加版本号（例如添加新的可选字段或新的操作类型）。
- 如果出现**破坏性变更**（如字段重命名/删除、语义改变），则必须同时更新两个代码库并提升版本号。
- 连接器的第一个 Pull Request 应注明其所基于的该文件的提交 SHA 值。
