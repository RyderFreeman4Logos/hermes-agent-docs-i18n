# Relay ↔ Connector 协议（v1，实验性版本）

> **状态：** 实验性版本。在至少有两个真正的 Class-1 平台（Discord 和 Telegram）对其完成验证之前，该协议**可能随时发生变化**，且不会经历废弃周期。在实验阶段，协议的演进仅限于**增量式修改**，并且会受到 `contract_version` 的限制。一旦出现破坏性变更，两个代码仓库中的相关内容将同步更新。

本文档是 **Hermes 网关**（Python，位于 `gateway/relay/` 目录）与 **连接器**（Node/TypeScript，位于 `NousResearch/gateway-gateway` 目录）之间的正式接口规范。连接器实现者首先需要阅读此文件。

网关会运行一个通用的 `RelayAdapter`，该适配器会**主动发起连接**至连接器，在握手阶段接收 `CapabilityDescriptor`，随后通过每轮双向 WebSocket 交换标准化的 `MessageEvent`（入站消息）以及各种操作指令（出站指令）。网关永远无法知晓自己所对接的具体平台是哪一个；所有与特定平台相关的套接字及身份识别逻辑均由连接器负责处理。

---

## 1. 握手流程

1. 网关建立传输连接（调用 `connect` 方法）。
2. 网关调用 `handshake()` 方法，连接器则返回一个 `CapabilityDescriptor`（见第 2 节），其中描述了该适配器实例所对应的目标平台信息。
3. 网关根据该描述符配置适配器的相关参数（如字符限制、长度单位、草稿/编辑/线程/ Markdown 支持能力等），并注册入站消息处理函数。
4. 此后，连接器开始流式传输入站事件，并接收网关发出的出站操作指令。

`contract_version` 字段（当前值为 `1`）会包含在描述符中。为保持向后兼容性，网关会忽略描述符中不存在的字段，而对于缺失的可选字段，则会使用默认值进行填充。

## 2. CapabilityDescriptor（握手数据载荷）

该字段为 JSON 格式。其定义来源为 `gateway/relay/descriptor.py` 文件。

| 字段 | 类型 | 是否必填 | 含义 |
| --- | --- | --- | --- |
| `contract_version` | int | 是 | 协议版本号（在同一版本内仅支持增量式修改）。 |
| `platform` | string | 是 | 平台名称（例如 `"discord"`、`"telegram"`）。 |
| `label` | string | 是 | 便于人类阅读的标签。 |
| `max_message_length` | int | 是 | 字符限制值；网关会将其暴露为 `MAX_MESSAGE_LENGTH` 参数。若该值为 0，则视为 4096 字符。 |
| `supports_draft_streaming` | bool | 是 | 是否支持原生的草稿流式预览功能。 |
| `supports_edit` | bool | 是 | 是否支持基于编辑功能的流式传输；若该值为 false，接收方将只能以每段一条消息的方式处理数据。 |
| `supports_threads` | bool | 是 | 是否具备 `create_handoff_thread` 能力。 |
| `markdown_dialect` | string | 是 | Markdown 格式版本，可选值包括 `"plain"`、`"markdown_v2"`、`"discord"` 等（该字段还会影响 `supports_code_blocks` 的行为）。 |
| `len_unit` | string | 是 | 长度度量单位，可选值为 `"chars"`（使用内置的字符计数方式）或 `"utf16"`（Telegram 使用的 UTF-16 代码单元计数方式）。 |
| `emoji` | string | 否 | 显示用的表情符号，默认值为 🔌。 |
| `platform_hint` | string | 否 | 系统提示用的平台标识信息。 |
| `pii_safe` | bool | 否 | 是否会在会话描述中隐去敏感个人信息（PII）。 |

大部分字段实际上都是从网关现有的 `PlatformEntry` 对象中提取而来的；而那些仅在运行时才需要的字段（如 `len_unit`、`supports_*` 系列字段以及 `markdown_dialect`）则直接来自对应平台适配器的能力检测方法。

## 3. 入站消息：`MessageEvent` 封装结构

连接器会将每个来自不同平台的原始消息事件转换为标准的 `MessageEvent` 对象（定义位于 `gateway/platforms/base.py` 文件中），然后再将其传递给网关。入站消息是通过网关的**出站方向 `/relay` WebSocket**进行传输的（详见下文的传输机制说明）——连接器会通过网关已建立的套接字，向下推送包含入站数据的帧。网关会利用嵌入在消息中的 `SessionSource` 对象通过 `build_session_key()` 方法为当前会话生成密钥；因此，确保正确填充各类识别字段是连接器需要承担的最重要的职责。

### 入站消息的传输方式（使用 WebSocket 通道，而非 HTTP）

网关会**主动发起连接**至连接器的 `/relay` WebSocket，用于完成握手、发送出站操作指令（见第 4 节）以及发送自身的 `/stop` 停止指令（见第 5 节）。而入站消息则通过同一套接字的**反向通道**传输：连接器会通过网关的出站 WebSocket，向下推送包含入站数据的帧（以及用于第 5 节中中断入站传输的 `interrupt_inbound` 框）。网关端**不存在专门的入站 HTTP 接口**——因为托管式的网关本身没有公网 IP，所以也不需要、也无法暴露任何入站端口；所有数据都通过其自身建立的连接进行传输。

**多实例路由机制。** 负责处理某个平台消息的连接器实例（即负责生成入站事件的实例），通常**并非**网关主动建立连接的那一个实例。因此，该生成事件的实例会将消息发布到连接器内部的**中继总线**上（基于 Redis 的发布/订阅机制，相关实现位于 `src/core/relayBus.ts` 文件中的 `RelayBus` 类）。每个连接器实例都会订阅该中继总线，并将接收到的每条消息路由至对应租户的**本地会话**中（通过 `RelayServer.routeBusMessage` 方法实现）；最终，只有那个真正持有网关套接字的实例才会处理该消息，而那些没有该租户本地会话的实例则不会执行任何操作。因此，跨实例的消息传递实际上只是在同一集群内的 Redis 通信，而非通过公网 HTTP 调用完成。

连接器向网关发送的帧格式如下（通过 WebSocket 传输）：

- `{"type":"inbound", "event": <MessageEvent>, "bufferId"?}`  
  表示入站消息帧，其中包含消息本身以及可选的缓冲区标识符。
- `{"type":"interrupt_inbound", "session_key", "chat_id"}`  
  用于中断当前正在处理的入站消息，其中包含会话密钥和聊天 ID。
- `{"type":"passthrough_forward", "forward": <PassthroughForward>, "bufferId"?}`  
  用于转发请求，其中 `forward` 字段包含了经过转发的请求信息（属于 Class-2/3 级别的 webhook 请求，例如 Discord 的交互请求或 Twilio 的请求），格式为 `{platform, botId, method, path, headers: [[k,v],…], bodyB64}`。请求体被编码为 Base64 格式，这样即使消息内容以换行符分隔，数据也能完整传输；网关会再次对其进行 Base64 解码，得到连接器所转发的原始字节数据（连接器已在边缘节点验证了服务提供商的签名，并去除了任何共享身份凭证——详见第 6 节），因此网关会处理经过净化、不含令牌的请求体，并通过无需令牌的 `follow_up` 机制来响应该请求。更多细节请参见第 3.1 节。

**信任机制。** WebSocket 升级过程会使用网关为每个网关配置的专用密钥进行身份验证（详见第 6.1 节），因此整个通信通道是端到端可信的——入站帧无需再单独进行 HMAC 签名（因为经过身份验证的套接字本身就已经具备了旧版 HTTP 机制中所需要的每次传输来源证明功能）。而通过中继总线进行的消息传递则发生在连接器自身的信任域内（与该连接器的租约、缓冲区及能力信息存储区域处于同一安全域）。

> 在该协议的早期版本中，入站消息是通过带签名的 **HTTP POST** 请求发送到 `gatewayEndpoint` 地址的（即 `HttpGatewayDelivery` 机制，以及网关端的 `inbound_receiver` 组件），并且会使用针对每个租户生成的专用密钥进行 HMAC 签名。但这种方式要求每个网关都必须暴露一个可访问的入站 URL，这对于没有公网 IP 的托管式网关来说是不可能的。因此，现在的方案改用了 WebSocket 通道；虽然为保持向后兼容性，仍会保留针对每个租户的专用密钥，但已不再用于入站消息传输。至于 **直通通道**（即 Class-2/3 级别的 webhook 请求，例如 Discord 的交互请求或 Twilio 的请求），过去仍然使用 `gatewayEndpoint` 作为请求确认后的转发地址；在第五阶段的第 5.1 节中，这一机制也被引入到了 WebSocket 通道中（即上述的 `passthrough_forward` 帧），这样一来，托管式网关就完全不需要暴露任何公网入站接口，而 `gatewayEndpoint` 也将在迁移完成后被废弃。

### 3.1 直通通道的请求转发机制（见第 5.1 节）

直通通道会在连接器的边缘节点处，立即响应服务提供商发出的那些对延迟要求极高的确认请求（例如 Discord 在约 3 秒内返回的延迟交互响应），之后会**直接将原始请求转发**给网关，且这种转发属于“发即忘”类型——因为服务提供商已经收到了响应，所以不需要再等待回复。因此，这种转发与入站消息一样，也是通过同一个出站 WebSocket 通道，以 `passthrough_forward` 帧的形式进行传输，而非通过 HTTP POST 请求。网关会通过其常规的处理流程来解析该请求（例如，Discord 的交互请求会被解析为 `MessageEvent` 对象，并像普通消息一样被处理；而回复则通过出站的 `/follow_up` 通道发送出去）。当请求在转发过程中被暂存时（即处于第五阶段的第 5.3 节所描述的“仅缓存”模式），`bufferId` 字段会出现在帧中；在完成持久化转接之后，网关会对该请求进行确认处理。

## 4. 出站消息：操作指令集

网关会通过传递包含操作指令的字典结构，来向连接器发送出站消息。相关实现代码位于 `gateway/relay/transport.py` 和 `gateway/relay/adapter.py` 文件中。| `op` | 字段 | 返回结果 |
| --- | --- | --- |
| `send` | `chat_id`, `content`, `reply_to?`, `metadata?` | `{success: bool, message_id?, error?}` |
| `edit` | `chat_id`, `message_id`, `content`, `metadata?` | `{success: bool, error?}` |
| `typing` | `chat_id` | `{success: bool}` |
| `follow_up` | `session_key`, `kind`, `content`, `metadata?` | `{success: bool, message_id?, error?}` |

`get_chat_info(chat_id)` 是一个独立的代理调用，至少返回 `{name, type}`。媒体操作采用相同的结构格式（将在后续合约修订中补充，属于扩展内容）。

**`follow_up`（A2 能力操作）。**某些传入的请求载荷会携带用于操作**共享**机器人身份的凭证（例如 Discord 交互跟进令牌）。根据第 6 条规定，连接器会在边缘层移除该凭证，并将其存储在以会话为键的能力库中；该凭证**绝不会传递到网关**。要使用该功能，网关需发起 `follow_up` 请求，指定其当前所在的**会话键**（`session_key`）以及能力类型 `kind`（例如 `discord.interaction_token`）——**绝不能是令牌本身**。连接器会从其能力库中获取真实值，验证租户是否匹配（租户 B 绝不能使用租户 A 的能力），之后再将数据传出。如果该能力不存在/已过期或租户不匹配，则返回 `success: false`——按设计，网关没有可重试的内容（泄露的网关不会持有任何能力相关数据）。相关实现代码位于：`gateway/relay/transport.py`（`send_follow_up`）和 `gateway/relay/adapter.py`。

## 5. 中断（`/stop`）路由

- **网关 → 连接器：**通过出站 WS 发送 `send_interrupt(session_key, reason?)` 请求，以在对话进行中插入 `/stop` 指令。连接器**必须**将其转发给正在运行该 `session_key` 的网关实例（这是路由的固定规则）。
- **连接器 → 网关：**针对某个 `session_key` 的入站中断请求会以 `interrupt_inbound` 数据帧的形式，通过网关的出站 WS 传递（参见第 3 条传输说明）——通过中继总线在各个实例之间路由，直到找到持有该套接字的实例——然后由适配器的 `on_interrupt(session_key, chat_id)` 方法将其接入现有的会话级中断机制，从而取消当前正在处理的对话（其他对话不受影响）。

两种方向的通信均基于网关的出站 WS：网关→连接器的 `/stop` 请求通过该通道发送，而连接器→网关的中断请求则作为标准化事件，通过相同的**入站回传通道**传输。

## 6. 信任边界与签名内容处理（A2）

**连接器是唯一的加密/身份验证边界。网关不会对任何内容进行重新验证。**

Webhook 签名（Discord ed25519、Twilio HMAC、WeCom BizMsgCrypt）是基于原始字节直接计算的，且部分载荷还会使用共享密钥进行**加密**。连接器为多个租户托管同一个**共享**机器人，并保存每个租户的平台密钥，因此它会：

- **在边缘层进行验证/解密**（因为密钥仅存储在此处）；
- 将载荷**标准化**为针对特定租户的 `MessageEvent` 格式（参见第 3 条）；
- 从载荷中移除任何与共享身份相关的能力信息，并将其存储在以会话为键的能力库中（参见第 4 条的 `follow_up` 说明）；
- **仅转发已清洗过的 `MessageEvent`**——绝不会传输原始的签名内容。

因此，网关在中继路径上**不会**对平台签名或加密内容进行任何验证；它只信任标准化后的事件。这是网关端强制遵循的规则（参见 `tests/gateway/relay/test_relay_sheds_crypto.py`：中继模块不会导入或调用任何平台级加密功能）。

**为何不“逐字节转发签名内容以便网关重新验证”？**
在不可信、可被丢弃的租户网关环境下，这种方案存在问题：

- 要重新验证 Twilio HMAC 或 WeCom 加密内容，就需要将**共享签名密钥**交给网关——而这本身就是信息泄露，而在共享机器人场景下，更是会导致**跨租户**的信息泄露；
- WeCom 的载荷是使用共享密钥加密的；连接器仅为路由目的需要在边缘层解密，因此如果转发密文，同样需要将密钥交给网关；
- Discord 交互令牌位于签名后的 JSON 内容中——你无法同时保留原始字节并移除该凭证，因为它们是同一组字节。

因此，刻意放弃了字节级保留的做法：连接器会对已清洗过的事件进行重新序列化，网关则信任该序列化后的内容。这样也实现了直通模式与中继模式的统一——两者都是“在边缘层验证 → 发送标准化事件”，仅在传输方式上有所不同。完整的 A2 设计理念及连接器端的存储机制详见 `docs/capability-trust-boundary.md`（连接器代码库位于 `gateway-gateway`）。

### 6.1 频道认证（连接器⇄网关连接本身）

在 A2 模型中，连接器是平台密钥的唯一持有者，而网关可能是**由客户自行管理且暴露在互联网上**的，因此连接器与网关之间的连接也需要进行认证。网关会持有由注册或配置流程生成的**每个网关专用的密钥**（通过 `hermes gateway enroll` 命令传递给连接器，路径为 `/relay/enroll`；如果是自主管理，则通过 `/relay/provision` 生成），该密钥用于验证其出站 WS 升级请求。认证机制采用 HMAC-SHA256 算法，并配有多密钥轮换验证列表（网关端代码位于 `gateway/relay/auth.py`，连接器端代码位于 `src/core/relayAuthToken.ts`）。

| 通信方向 | 凭证 | 认证机制 |
|---------|------|----------|
| 网关 → 连接器 WS 升级请求 | 每个网关专用的密钥 | 在 `/relay` 升级请求中包含 `Authorization` 类型的 bearer 标头。该令牌的格式为 `base64url(payload:exp:sig)`，其中 `payload = gatewayId`，`sig = HMAC(payload:exp, secret)`。连接器会验证该令牌，若存在匹配问题、密钥缺失或已被撤销，则拒绝升级请求并返回 **4401 错误码**。经过认证的租户信息来自连接器的存储，而非 `hello` 数据帧。 |
| 连接器 → 网关入站请求（`inbound`/`interrupt_inbound` 数据帧） | ——（通过已认证的 WS 通道传输） | 入站请求会通过网关已认证的出站套接字直接发送（参见第 3 条），因此无需为每条消息单独签名。虽然注册或配置时仍会为每个租户生成**专用传输密钥**并保留以保持向后兼容性，但该密钥不再用于对入站请求进行签名。 |

这就是**通道级**认证机制——与平台级加密不同，中继路径仍然完全不涉及平台级加密（参见第 6 条）。网关不会持有任何平台密钥；每个网关专用的密钥仅用于验证连接器连接的安全性。完整的威胁模型以及注册、密钥轮换和紧急关闭机制的设计详见 `docs/connector-gateway-auth-design.md`（连接器代码库）。

## 7. 每个实例的交付方式与管理平面（第 6 阶段）

第 1–5 阶段将连接器视为单租户前端：针对某个租户的入站事件会直接发送到该租户的网关套接字。**第 6 阶段实现了按实例交付**——同一个共享机器人可以在一个租户内为多个用户/代理提供服务（例如一个 Discord 社群或一个 Telegram 机器人），而不会发生跨实例的交付混淆——同时还新增了一个小型**管理平面**，供代理或托管的 Portal 用来指定“谁可以看到什么内容”以及“哪些内容是相关的”。所有这些功能都位于**连接器端**；网关唯一需要承担的新职责是在启动时声明其**相关性策略**（参见第 7.3 节）。

### 7.1 交付筛选机制（连接器端，用于信息判断）

对于每条入站事件，连接器会通过组合三个“与”逻辑的过滤条件，来确定哪些实例应该接收该事件。这些过滤条件并非由网关实现——它们在连接器端运行——但它们定义了网关所依赖的交付规则：

| 层级 | 判断问题 | 信息来源 |
|------|----------|----------|
| **所有者/范围 ∧ 主体** | 该实例是否有权查看此消息的发送者在此处的内容？ | 每个用户的 `user_id → instance` 绑定关系（即所有者层级）+ 每个实例的 `(guild, channel)` 范围授权设置 + `owner-only`/`allow-list`/`any` 类型的主体策略。 |
| **可见性层级** | 该实例的所有者是否真的有权在 Discord 中查看此频道的内容？ | Discord 实时的 ACL 权限设置（即实际生效的权限），采用“失败即阻断”原则。该层级用于缩小过宽的范围授权范围。 |
| **相关性判定** | 在满足前两个条件的前提下，代理是否应该处理该消息？ | 根据第 7.3 节声明的相关性策略（如地址过滤、自由回复模式、是否允许机器人参与等）。 |

这些过滤条件的组合只会**缩小**可交付的消息范围（即 `deliver ⇔ authorized ∧ visible ∧ relevant`）；**所有者层级会直接绕过相关性判定层**——发送者自己的消息始终会发送到其所在实例（因为你不会@提到自己的代理）。未被授权用户发送的消息则不会被任何实例接收（同样采用失败即阻断原则）。完整的架构设计及相关规则均位于连接器代码库 `NousResearch/gateway-gateway` 中；本节仅为面向网关的简化总结。

### 7.2 管理路由（连接器端，需身份认证）

连接器会设置需要身份认证的管理路由。这些路由与 WS 升级过程采用**相同的双重认证机制**：要么是经过 NAS 签名的、`aud=agent:{instanceId}` 格式的 RS256 JWT，要么是网关自身的每个网关专用的密钥 bearer 令牌（参见第 6.1 节的 `make_upgrade_token` 函数）。在这两种情况下，连接器都会从其**存储的**记录中获取权威的 `{tenant, instanceId}` 信息——**绝不会**从请求体中获取（请求体中声明的 `instanceId` 会被忽略）。

| 路由地址 | 功能 |
|---------|------|
| `POST /manage/link` | 生成一个短期有效的代码，用于将平台账户与已认证的实例绑定（即 `/link <code>` 流程；连接器会从入站事件中读取已认证的 `user_id`）。 |
| `POST /manage/scope`, `/manage/scope/release` | 为已认证的实例申请或释放某个 `(guild, channel)` 范围的访问权限。一个频道最多只能被一个实例拥有（非重叠关系是该设计的约束条件）。 |
| `POST /manage/principal` | 设置该实例的主体策略，可选值为 `owner-only`、`allow-list` 或 `any`。 |
| `POST /manage/dm-default` | 设置用户的私信默认接收实例（当用户关联了多个实例时，用于私信消息的路由决策）。 |
| `POST /relay/policy` | 声明该实例的**相关性策略**（参见第 7.3 节）。 |

这些功能均由连接器负责管理（管理平面并不属于网关的代理处理流程）；网关仅需要调用 `POST /relay/policy` 接口（参见第 7.3 节）。其余功能则由托管的 Portal 或 `hermes` CLI 来触发。

### 7.3 相关性策略声明（网关的职责）

相关性判定层（参见第 7.1 节）实际上相当于为网关自身的行为参数（如 `require_mention`、`free_response_channels`、`{PLATFORM}_ALLOW_BOTS`）定义了针对每个租户的统一规则。因此，中继交付过程也遵循相同的规则，网关会将这些参数转化为**与具体平台无关的策略**，并在启动时（在获取到每个网关专用的密钥之后）通过 `POST /relay/policy` 接口将其上传。

相关代码位于 `gateway/relay/__init__.py` 的 `relay_relevance_policy()` 函数中，该函数最终会调用 `send_relay_policy()` 方法来发送策略内容。| 字段 | 类型 | 来源 | 含义 |
| --- | --- | --- | --- |
| `platform` | 字符串 | `relay_platform_identity` | 该策略适用的平台。 |
| `requireAddress` | 布尔值 | `require_mention` | 非所有者发送的消息必须@提及或回复机器人，才被视为有效内容。 |
| `freeResponseScopes` | 字符串数组 | `free_response_channels` | 可免除`requireAddress`要求的范围（频道）ID列表。其范围词汇与§7.1中定义的范围权限相同。 |
| `allowOtherBots` | 布尔值 | `{PLATFORM}_ALLOW_BOTS ∈ {mentions, all}` | 是否允许机器人发送的消息通过（默认为关闭）。 |

认证信息为每个网关专用的升级令牌（参见§6.1），因此连接器会将该策略附加到已通过认证的实例上。网关是**唯一真实的数据来源**，并在**每次启动时**重新声明策略（即完全替换策略，类似于配置阶段对`routeKeys`的更新操作——具备自修复功能）。当策略全部为默认值时，网关不会发送任何数据（因为连接器的空行默认设置已与之匹配）。该POST操作采用**容错机制**：出现故障时会记录日志并继续启动流程——相关性判断是建立在授权机制之上的优化层（参见§7.1），并非启动流程的必要条件。此机制**不新增网关入口**，也**无需新的凭证**——它直接复用每个网关的专用密钥以及与 `/relay/provision` 相同的服务器。

> 相关性判断会在连接器唤醒已缩减到零规模的代理（第5阶段）**之前**完成，因此被排除的聊天内容永远不会触发代理启动——相关性既是实现规模缩减的主要手段，也是确保内容准确性的过滤机制。

## 8. 策略版本控制

- `contract_version`为整数；仅在实验阶段进行**增量式修改**时才需升级版本（如新增可选字段、新的操作类型等）。
- 若出现破坏性变更（如字段重命名/删除、语义改变），则需同时协调更新两个代码库并提升版本号。
- 连接器提交的第一个拉取请求需注明其所依据的该文件的提交SHA值。
