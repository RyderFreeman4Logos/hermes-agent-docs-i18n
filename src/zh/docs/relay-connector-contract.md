# Relay ↔ Connector 接口规范（v1，实验性版本）

> **状态：** 实验性版本。在至少有两个一级平台（Discord 和 Telegram）对其完成验证之前，该接口**可能随时变更**而无需经过正式的废弃流程。实验阶段的更新仅允许**增量式修改**，且必须通过 `contract_version` 进行控制；若发生破坏性变更，则需同步更新两个代码仓库。

本文档定义了 **Hermes 网关**（Python，位于 `gateway/relay/` 目录）与 **连接器**（Node/TypeScript，位于 `NousResearch/gateway-gateway` 目录）之间的正式接口。连接器实现者首先需要阅读此文档。

网关会运行一个通用的 `RelayAdapter`，该适配器会**主动发起连接**至连接器，在握手阶段接收 `CapabilityDescriptor`，随后通过每轮双向 WebSocket 交换标准化的 `MessageEvent`（入站消息）及操作指令（出站指令）。网关无需知晓自身背后具体的平台是哪一个；所有与特定平台相关的套接字及身份识别逻辑均由连接器负责处理。

---

## 1. 握手流程

1. 网关建立传输连接（调用 `connect` 方法）。
2. 网关调用 `handshake()` 方法，连接器则返回一个 `CapabilityDescriptor`（见第2节），其中描述了该适配器实例所支持的平台信息。
3. 网关根据该描述文件配置适配器的相关参数（如字符限制、长度单位、草稿/编辑/线程/Markdown功能等），并注册入站消息处理函数。
4. 此后，连接器开始流式传输入站事件，并接收网关发出的出站操作指令。

`contract_version` 字段（当前值为 `1`）会包含在描述文件中。为保证向前兼容性，网关会忽略未知的描述字段；对于缺失的可选字段，则会使用默认值进行填充。

---

## 2. CapabilityDescriptor（握手数据载荷）

该字段为 JSON 格式，其定义来源为 `gateway/relay/descriptor.py`。

| 字段 | 类型 | 是否必填 | 含义 |
| --- | --- | --- | --- |
| `contract_version` | int | 是 | 接口版本号（同一版本内仅允许增量式更新）。 |
| `platform` | string | 是 | 平台名称，例如 `"discord"`、`"telegram"`。 |
| `label` | string | 是 | 便于人类理解的标签名称。 |
| `max_message_length` | int | 是 | 字符限制值；网关会将其暴露为 `MAX_MESSAGE_LENGTH` 属性。若值为 0，则视为 4096 字符。 |
| `supports_draft_streaming` | bool | 是 | 是否支持原生的草稿流预览功能。 |
| `supports_edit` | bool | 是 | 是否支持基于编辑的流式传输；若为 false，客户端将只能以每段一条消息的方式接收内容。 |
| `supports_threads` | bool | 是 | 是否具备 `create_handoff_thread` 功能。 |
| `markdown_dialect` | string | 是 | Markdown 语法版本，可选值为 `"plain"`、`"markdown_v2"`、`"discord"` 等（该值会影响 `supports_code_blocks` 的行为）。 |
| `len_unit` | string | 是 | 长度计量单位，可选值为 `"chars"`（使用内置字符计数）或 `"utf16"`（Telegram 使用的 UTF-16 代码单元）。 |
| `emoji` | string | 否 | 显示用的表情符号，默认为 🔌。 |
| `platform_hint` | string | 否 | 系统提示用的平台标识信息。 |
| `pii_safe` | bool | 否 | 是否在会话描述中隐藏敏感个人信息（PII）。 |
| `supports_context` | bool | 否 | 连接器是否能够为该平台上当前处理的对话提供所在频道/群组的**上下文信息**（模型 A 会按需获取历史记录——适用于 Discord/Slack/Matrix；模型 B 则采用被动缓冲方式——适用于 Telegram/Signal/WhatsApp）。默认值为 false，即入站事件不会附带任何上下文信息。详见第3节。 |

大部分字段实际上都是从网关现有的 `PlatformEntry` 对象中提取而来的；而那些仅在运行时才需要的字段（如 `len_unit`、`supports_*`、`markdown_dialect` 等）则来自对应平台适配器的功能方法。

## 3. 入站消息：`MessageEvent` 数据结构

连接器会将每个平台发送的原始消息格式化为 `MessageEvent` 对象（定义位于 `gateway/platforms/base.py`），然后再将其传递给网关。入站消息是通过网关的**出站方向 `/relay` WebSocket** 传输的（详见下文的传输说明）——连接器会通过网关已建立的套接字，向上推送包含入站数据的帧。网关会利用嵌入在消息中的 `SessionSource` 对象通过 `build_session_key()` 方法为该会话生成密钥；因此，正确设置各类标识符是连接器需要承担的最重要的职责。

### 入站传输方式（使用 WebSocket 通道，而非 HTTP）

网关会**主动发起连接**至连接器的 `/relay` WebSocket，用于进行握手、发送出站操作指令（见第4节）以及发送自身的 `/stop` 停止指令（见第5节）。入站消息则通过同一套接字的反向通道传输：连接器会通过网关的出站 WebSocket，向上推送包含入站数据的帧（以及用于第5节的 `interrupt_inbound` 指令）。**网关端不存在任何入站 HTTP 接口**——因为托管型网关既没有必要，也无法暴露任何入站端口；所有数据都通过其自身建立的连接进行传输。

**多实例路由机制。** 负责处理某个平台消息的连接器实例（即生成入站事件的实例），通常**并非**网关主动建立连接的那一个实例。因此，生成消息的实例会将该消息发布到连接器内部的**中继总线**上（基于 Redis 的发布/订阅机制，具体实现位于 `src/core/relayBus.ts` 中），并且会为该消息添加租户标识作为键。每个连接器实例都会订阅该总线，并将收到的每条消息路由至该租户的**本地会话**中（通过 `RelayServer.routeBusMessage` 方法实现）；最终，只有持有网关套接字的那个实例才会处理该消息，而那些没有对应租户本地会话的实例则不会执行任何操作。因此，跨实例的消息传递实际上只是在同一集群内的 Redis 通信，而非公共 HTTP 调用。

连接器向网关发送的帧格式如下（通过 WebSocket 传输）：

- `{"type":"inbound", "event": <MessageEvent>, "bufferId"?}`
- `{"type":"interrupt_inbound", "session_key", "chat_id"}`（用于第5节）
- `{"type":"passthrough_forward", "forward": <PassthroughForward>, "bufferId"?}`（用于第5.1节）

**入站消息中的频道上下文功能（relay-channel-context 设计）。** 当源平台在描述文件中声明支持上下文功能（见第2节），且对话为多方对话时（即 `chat_type` 为 group/channel/thread/forum，绝不可能是 `dm`），连接器可以在入站的 `MessageEvent` 中附加两个可选的、增量式的字段：

- `context`：一个只读数组，包含该频道内附近的其他消息内容，按从旧到新的顺序排列——这些消息是连接器通过模型 A 获取的，或是通过模型 B 缓存的、与当前对话无关的聊天内容。该字段仅用于参考，**不会触发智能体执行任何操作**（因为是否触发智能体的决策早已在连接器端根据当前处理的消息单独完成）。网关会将该字段值填充到 `MessageEvent.channel_context` 中，该字段的填充方式与历史记录回填时使用的只读注入路径相同。
- `context_error`：布尔值，当平台具备上下文生成能力，但获取或缓存操作失败时，连接器会将该字段设置为 true，表示上下文为空（该字段用于监控目的，相关信息会在传输链路中由连接器端上报）。

如果这两个字段都不存在，那么入站消息的格式将与当前版本完全一致。那些从不发送这些字段的连接器、私信对话，或是不支持上下文功能的平台，其入站消息中将不会包含 `channel_context` 字段。

`PassthroughForward` 字段表示转发的请求数据，其格式类似于二级/三级 webhook 请求（如 Discord 交互、Twilio 接口）：`{platform, botId, method, path, headers: [[k,v],…], bodyB64}`。请求体采用 Base64 编码，这样即使使用以换行符分隔的 JSON 格式传输，任意字节内容也能完整保留；网关会对该编码进行解码，从而得到连接器转发的原始字节数据（连接器已在边缘节点验证了服务提供商的签名，并去除了任何共享身份凭证——详见第6节），因此网关会重新处理经过净化、不含令牌的请求体，并通过无需令牌的 `follow_up` 路径对该请求进行处理。详见第3.1节。

**信任机制。** WebSocket 连接的升级过程会使用网关为每个网关单独配置的密钥进行身份验证（详见第6.1节），因此整个通信通道是端到端可信的——入站帧无需再单独进行 HMAC 签名（因为经过身份验证的套接字本身就已经具备了旧版 HTTP 接口所需的每条消息来源证明功能）。中继总线的通信则发生在连接器的信任域内，该信任域与租约、缓冲区及功能配置存储所在的范围相同。

> 该接口规范的早期版本曾采用带签名的**HTTP POST**请求将入站消息发送至 `gatewayEndpoint`（即 `HttpGatewayDelivery` 机制以及网关端的 `inbound_receiver` 组件），并且会使用针对每个租户的专用密钥对请求进行 HMAC 签名。但这种方式要求每个网关都必须公开一个可访问的入站 URL，而托管型网关由于没有公网 IP，根本无法做到这一点。因此，现在的方案改用了 WebSocket 通道；虽然为了保持向前兼容性，仍会保留针对每个租户的专用密钥，但该密钥已不再用于入站消息的处理。至于**直通通道**（即二级/三级 webhook，如 Discord 交互、Twilio 接口），过去仍会使用 `gatewayEndpoint` 来发送确认后的转发请求；在第5阶段的第5.1节中，这一功能也被迁移到了 WebSocket 通道上（即上述的 `passthrough_forward` 帧），这样一来，托管型网关就完全不需要任何公网入站接口，而 `gatewayEndpoint` 也会在过渡完成后被废弃。

### 3.1 直通通道的转发机制（见第5.1节）

直通通道会在连接器的边缘节点处，立即响应服务提供商发出的那些对延迟敏感的确认请求（例如 Discord 在约 3 秒内返回的延迟交互响应），之后会**直接转发**原始请求至网关，且采用“发送即忘”的方式处理——因为服务提供商已经收到了响应，所以无需再等待回复。因此，该转发请求会通过与入站消息相同的出站 WebSocket 通道传输，但使用的是 `passthrough_forward` 帧，而非 HTTP POST 请求。网关会通过常规的智能体处理路径来解析该请求（例如 Discord 交互请求会被解析为 `MessageEvent` 对象，并像普通消息一样被处理；回复则通过出站的 `/follow_up` 通道发送）。当该请求被缓存时，`bufferId` 字段会出现（对应第5阶段的第5.3节中关于仅支持缓存的调整），网关会在完成持久化转接后对该请求予以确认。

### SessionSource 字段（网络层传输的字段结构）

这些字段的定义来源为 `gateway/session.py` 文件中的 `SessionSource.to_dict()` 方法。它们代表了网关在网络层上所接收的所有字段。`platform`、`chat_id`、`chat_type`、`user_id`、`user_name`、`thread_id`、`chat_name` 和 `chat_topic` 这些字段始终都会出现（但其值可能为 `null`）；其余字段则仅在被设置时才会出现在传输数据中。| 字段 | 类型 | 是否必传 | 含义 |
| --- | --- | --- | --- |
| `platform` | string | 是 | 平台名称（与描述符中的 `platform` 一致）。 |
| `chat_id` | string | 是 | 主对话 ID（频道/聊天室）。用于区分会话密钥。 |
| `chat_type` | string | 是 | `dm` / `group` / `channel` / `thread` / `forum`。 |
| `chat_name` | string\|null | 是 | 便于人类阅读的聊天名称。 |
| `user_id` | string\|null | 是 | 消息发送者 ID。用于区分会话密钥。 |
| `user_name` | string\|null | 是 | 发送者的显示名称。 |
| `thread_id` | string\|null | 是 | 若处于主题讨论中，则为该主题/论坛帖子的 ID。用于区分会话密钥。 |
| `chat_topic` | string\|null | 是 | 频道主题/描述（适用于 Discord、Slack）。 |
| `user_id_alt` | string | 否 | 平台特定的稳定备用 ID（如 Signal 的 UUID、飞书の union_id）。 |
| `chat_id_alt` | string | 否 | 备用聊天 ID（例如 Signal 群组内部 ID）。 |
| `scope_id` | string | 否 | 与平台无关的 **范围** 区分标识：Discord 社团 / Slack 工作区 / Matrix 服务器。**对于 Discord/Slack 的范围隔离是必需的**。用于区分会话密钥。（基于 D-Q2.5 线路迁移后的标准名称。） |
| `guild_id` | string | 否 | **旧版别名，连接器已不再读取**。从 D-Q2.5c 版本起，连接器仅读取和写入 `scope_id`；而网关端的代理级 `SessionSource.to_dict()` 仍会为非中继会话的持久化目的输出 `guild_id`（该值会被映射为 `scope_id`），因此它仍可能出现在网络数据中，但连接器会忽略它。请勿依赖此字段。 |
| `parent_chat_id` | string | 否 | 当 `chat_id` 指向主题讨论时，对应的父频道 ID。 |
| `message_id` | string | 否 | 触发消息的 ID（用于固定消息、回复、互动等功能）。 |

> `is_bot`（发送者是否为机器人/ webhook 分类）存在于网关侧的数据类中，但在 v1 版本中**有意未包含在网络数据中**——它不属于 `to_dict()` 的输出内容。在它被添加到此处以及 `to_dict()` 中之前，请勿将其加入连接器的 `SessionSource` 中（需进行增量更新）。

### 各平台的 SessionSource 区分标识

| 平台 | chat_id | chat_type | user_id | thread_id | scope_id |
| --- | --- | --- | --- | --- | --- |
| **Discord** | 频道 ID | `dm`/`group`/`thread` | 发送者 ID | 主题讨论频道 ID（针对主题讨论） | **guild_id**（用于服务器隔离，为必需项） |
| **Telegram** | 聊天 ID | `dm`/`group`/`forum` | 发件人 ID | 论坛帖子 ID（针对论坛） | — |

**若获取 Discord 的 `guild_id` 出错，两个服务器可能会被合并到同一个会话中。**
这是严重程度最高的风险点。网关的 `build_session_key()` 是一致性判定依据：对于给定的 `SessionSource`，连接器的规范化处理必须生成与 Python 适配器相同的密钥。（第一阶段的桩测试会验证已知输入应产生已知密钥。）

### 机器人身份与租户（单机器人多租户整合，附录 A）

消息包中会携带**发起消息的机器人身份**作为字段，该字段与**租户**是相互独立的。租户信息是通过事件自身的区分标识来确定的（Discord 的 `guild_id`、Telegram 的 `chat_id`、webhook 路径/子域名）——**绝不会**根据传递消息的令牌/套接字/进程来确定。这样的设计使得一个共享机器人能够为多个租户提供服务（第 6 阶段），而无需占用现有字段。

### 以发送者为优先的解析方式 + 账户关联（私信）路径（第 7 阶段）

第 7 阶段引入了**面向用户的自助式共享机器人注册流程**，这一变化改变了路由进站消息时用于确定具体实例的区分标识——同时还为用户提供了绑定自己账户的管理路径。

**以发送者为优先的解析方式（多租户社团规则，D-7.2）。** 一个 Discord 社团可以包含**多个**租户——不同成员各自关联到各自的代理。因此，在消息传递时，连接器会根据**已认证的发送者绑定信息**（`user_instance_binding`，通过 `resolveByUser` 按 `(tenant, platform, platform_user_id)` 进行键值匹配）来确定目标实例，**而非**通过社团→实例的路径来确定。具体而言：

- 由**已关联**用户发送的路由消息只会送达**该用户**对应的实例——即便同一社团中的另一位已关联用户由不同的实例处理，每位用户的消息也只会发送到自己的实例。
- 由**未关联**用户发送的消息则不会解析出任何实例，会被直接丢弃（属于**失败即终止**机制——永远不会被广播给社团中的其他租户）。
- 所使用的发送者 ID是**来自实际事件的真实 `user_id`**，即上文所述的 `SessionSource.user_id`——绝非网关主动设定的值，也不是管理帧中携带的数值。

这正是连接器在 `WsGatewayDelivery` 中实施的、基于每个 `user_id` 的仅所有者可接收的路由机制（网关侧的多租户社团端到端驱动程序 `gateway_multitenant_guild_driver.py` 则是跨仓库的一致性判定依据）。

**账户关联（私信）路径。** 用户可通过一次性验证码将自身账户与某个实例绑定，该验证码需通过向共享机器人发送私信来使用：

1. 账户所有者通过门户网站（或自托管的 CLI）触发绑定流程。连接器会为**已认证**的实例生成一个短时效的**链接码**（通过 `POST /manage/link` 发送；instanceId 来自调用方的主体信息——即由 NAS 签名的 `aud=agent:{instanceId}` 令牌，或是该实例自身的网关专用密钥——**绝不会**来自请求体）。
2. 用户从希望绑定的账户出发，向共享机器人发送包含 `/link <code>` 的**私信**。
3. 连接器的进站监听器会**接收**该私信（它不会被路由到任何代理），并使用私信事件中记录的**真实 `user_id`** 来创建 `user_instance_binding`。从那时起，以发送者为优先的解析机制就会将该用户的消息路由到已绑定的实例。

**取消绑定的权限由连接器掌控。** 若要停用某个实例（通过 `POST /manage/deprovision` 发送请求），则会同时删除该实例的发送者绑定信息（从而使相关用户不再能将其解析为该实例的接收端），并撤销该实例的网关专用密钥（使其套接字无法再进行身份验证——下一次 WebSocket 升级将会以 **4401** 错误被拒绝）。如果网关在之前已成功完成握手后收到 **4401** 错误，就会将其视为最终性的撤销操作：网关将停止尝试重新连接，并将该中继平台标记为**已禁用**（不属于可重试的错误类型）。而在任何成功握手之前出现的 4401 错误则仍属于可重试范畴（属于冷启动或尚未完成配置的情况，而非撤销操作）。

### 3.2 进入空闲状态 / 缓冲切换原语（§5.3）

这是一种用于实现零资源消耗模式的**原语**（并非指具体行为——此处并未规定让机器进入睡眠或暂停状态；后续的工作流会处理这些数据帧）。它允许网关在进入空闲状态时，不会丢失在此期间到达的进站消息，其原理是让连接器为该实例创建一个缓冲区，并在重新连接时重放这些消息。

共有三个数据帧（均以连接过程中**已认证**的每个实例专属 ID 作为键值——该 ID 来自 WebSocket 升级时存储的密钥记录，绝不会在数据帧中明确指定）：

- `{"type":"going_idle"}`（网关 → 连接器）——作为网关现有空闲状态转换过程的一部分被发送（适配器在关闭套接字之前会发送此帧）。该帧要求连接器将当前实例切换为**仅缓冲模式**。
- `{"type":"going_idle_ack"}`（连接器 → 网关）——表示连接器已完成切换：实时消息传递已停止，此后该实例接收的所有进站消息都将被持久存储在缓冲区中。网关会**持续提供服务，直到收到此确认帧**（因此，在切换窗口内到达的消息仍会以实时方式送达，而不会丢失——这与消息总线的“先订阅后发送”顺序规则一致）。只有在收到确认帧之后，才能安全地关闭连接。
- `{"type":"inbound_ack", "bufferId"}`（网关 → 连接器）——表示已成功接收并持久存储了一个缓冲中的进站消息（该消息会携带自己的 `bufferId`），在重新连接时会进行重放。连接器只有在收到此确认帧后，才会对对应的缓冲条目予以确认，从而在**消息传输环节实现无重复传输**：如果在空闲状态下实例意外关闭，系统只会重新发送那些尚未被确认的未处理消息；而已被确认的条目则不会再被重发。

**缓冲与空闲模式。** 在处于仅缓冲模式期间，连接器会将新收到的进站消息追加到该实例专属的持久性传输缓冲区中（`delivery:<instanceId>`），而非立即以实时方式发送。当网关**重新连接**时（即因意外断开而进入全新的重连循环，需要重新拨号并完成握手），新的握手流程会促使连接器通过新的套接字，按照顺序且经过确认机制后，将缓冲区中的积压消息逐条传输出去，之后再清除缓冲状态，从而恢复实时消息传递。这一机制与 Discord→连接器方向的消息接收流程所使用的“无重复传输”逻辑相同，只是应用于连接器→网关的传输方向。整个过程中均由连接器掌控：网关只能对自己的实例进行切换/空闲处理。

> 不在本原语的覆盖范围内（属于后续实现的内容）：决定何时进入空闲状态的自主空闲计时器、实际的机器暂停操作，以及 NAS 的健康状态暂停机制。该原语仅定义了“当网关进入空闲模式时，中继层会切换为缓冲模式，并在重新连接时重放消息，且不会造成消息丢失或重复”；而触发空闲状态的机制则不在其覆盖范围内。

### 3.3 唤醒操作（§5.2）

这是睡眠/唤醒循环的另一半：用于让处于**暂停状态**的网关知晓有已缓冲的消息正在等待处理。这也是一种**原语**——此处并未规定让机器进入暂停状态；它只是定义了唤醒信号，以便未来的零资源消耗模式层能够基于“已缓冲消息 ⇒ 唤醒”这一机制来工作。

- **注册。** 网关在注册/配置阶段会指定一个**唤醒 URL**——即连接器可以通过 GET 请求访问的任何可到达地址，用于唤醒网关（可以是 Fly 的自动启动主机名，也可以是控制面板主机地址）。对于自托管场景，可使用命令 `hermes gateway enroll --wake-url <url>`（或设置环境变量 `GATEWAY_RELAY_WAKE_URL` / `gateway.relay_wake_url`）。对于托管型或 NAS 管理的网关，该地址会与 `GATEWAY_RELAY_URL` 一同被写入容器环境变量中。在 `/relay/provision` 请求的请求体中，该地址会被作为 `wakeUrl` 参数传递，并由连接器存储在每个实例的密钥记录中（该地址由网关指定，但具有严格的访问控制范围——与 `instanceId` 的安全性一致；由于租户/组织信息仍需通过令牌验证，因此网关只能为自己的实例注册唤醒目标）。该地址与已废弃的 `gatewayEndpoint` 不同：它是一个**唤醒目标**，而非消息传输目标。
- **唤醒操作。** 当处于仅缓冲模式（即进入空闲状态）的目标实例收到第一个缓冲中的消息时，连接器会直接向该实例注册的 `wakeUrl` 发送一个**不带有效载荷且未签名**的 GET 请求（**不会通过 NAS 中转**——因为中继层仍保持与 NAS 的解耦）。该请求不包含任何租户相关数据，也不携带进站消息内容，仅表示“你有已缓冲的消息，请重新连接”。当网关再次尝试建立连接并完成身份验证的 WebSocket 升级时，租户身份信息会以常规方式重新确认，因此即使唤醒 URL 被泄露或被猜测，最坏的结果也只会导致该实例自己发起不必要的重新连接。该唤醒操作的频率是按实例限流的（每个冷却周期内仅允许一次唤醒请求，而非针对每条消息），且属于尽力而为的机制——如果唤醒请求失败，也会被忽略；网关仍会在下次自行尝试重新连接时继续处理消息。此外，不会产生新的数据帧：唤醒操作是通过独立的 HTTP GET 请求实现的，而非通过 WebSocket 中继发送的消息（因为此时套接字已经断开——这正是该机制的设计目的）。

> 不在本原语的覆盖范围内（属于后续实现的内容）：实际的机器暂停操作（Fly 的 `autostop:"suspend"` 设置）以及决定何时进入睡眠状态的自主空闲计时器。该原语仅定义了“对于处于睡眠状态的实例，若有缓冲消息则向其唤醒 URL 发送唤醒请求”；而决定让实例进入睡眠状态（以及随后唤醒以开始处理消息）的机制，则属于上层行为逻辑的范畴。### 3.4 面向未来“零规模”行为层的责任

§3.2 和 §3.3 提供了**基础功能**；本节则规定了**独立的“零规模”行为工作流为安全使用这些基础功能必须遵守的契约**。该工作流负责*决策*是否暂停实例、执行实际的机器暂停操作，以及管理平台/健康状态模型——这些功能本身并不位于此处——但它**必须**提供基础功能所依赖的以下保障：

1. **在实例被暂停之前必须注册 `wakeUrl`**。若已暂停的实例未注册 `wakeUrl`，则相当于一个“黑洞”——进入缓冲区的入站消息将永远不会触发唤醒操作，因此该实例会一直处于休眠状态，直到有其他机制重新连接它。行为层**必须**确保在允许暂停之前，已注册一个可访问的唤醒目标（自托管场景下使用 `--wake-url` 参数指定；托管场景下由平台自动设置），否则等同于未注册。如果在机器处于暂停状态时该唤醒 URL 不可访问（例如指向了正在暂停的机器本身，且没有平台自动启动机制），则视为无效。

2. **在断开套接字或暂停实例之前，必须先通过 `going_idle` 步骤完成数据清空，再等待 `going_idle_ack`**。绝不能在正在处理的切换请求尚未得到确认的情况下就暂停实例。该确认信号表示连接器已确认该实例的发送操作现在仅处于缓冲状态；如果在发送 `going_idle` 后但在收到确认信号之前就暂停实例，那么那些在切换请求处理期间到达的入站消息将会丢失。网关已经根据确认信号来控制套接字的断开操作（参见 Q-5.3c）；因此暂停操作**必须**在数据清空完成后进行，而不能与之并行。

3. **作为暂停实例的前提条件，必须保持“全新重连循环”处于激活状态**。唤醒→数据清空之间的契约是“触发唤醒 → 网关重新拨号 → 连接器在重连握手过程中完成数据清空”。如果禁用了重连循环，那么唤醒信号发送到后，机器将不会重新拨号，导致缓冲区中的消息无法被处理。行为层绝不能暂停那些在唤醒后其传输机制不会重新连接的实例。

4. **在健康状态模型中，必须将“已暂停”视为与“已关闭”不同的状态（参见 Q-5.3b）**。已暂停的实例属于“健康休眠”状态，而非故障状态。健康/监控层**必须**区分这两种状态（例如通过平台记录的机器状态），这样才能避免对已暂停的实例进行重启、发送警报或判定为异常状态——否则就会破坏暂停机制，还可能引发与唤醒/数据清空流程的竞争。

5. **唤醒操作属于尽力而为型且受到速率限制——切勿假设一定会立即或恰好触发一次唤醒**。每个实例在每个冷却周期内最多只能触发一次唤醒操作，且失败的唤醒尝试会被忽略。行为层绝不能将唤醒操作视为一种必然或即时的信号；系统的正确性依然依赖于“网关在下次重新连接时就会进行数据清空”这一原则。如果需要更可靠的唤醒机制（例如通过定时任务来触发重连），那是行为层的职责，而非基础功能的职责。

6. **只有当实例真正处于空闲状态时才可暂停——而且这种空闲状态必须是连接器能够检测到的，而非网关推测的**。究竟什么算作空闲状态（没有正在处理的请求 + 在 N 分钟内没有入站消息），是由行为层根据自身策略来确定的，但它必须与现有的数据清空机制相协调（即当 `gateway_state` 显示为运行中时，应先进行数据清空），而不能引入一条独立的、仅依赖中继的空闲检测路径——这与 §3.2 中对 `going_idle` 功能所规定的集成约束是一致的。

以上这些就是行为层对基础功能所应承担的保障；而基础功能仅需履行 §3.2/§3.3 中已明确规定的职责（即在实例进入空闲状态时触发切换、为每个实例提供持久化的缓冲区并配合确认信号实现有序的重连，以及在对处于空闲状态的实例触发首次入站消息时进行唤醒操作）。

## 4. 出站操作：操作集

网关通过操作字典来调用传输层功能。相关实现代码位于：
`gateway/relay/transport.py` + `gateway/relay/adapter.py`。

| `op` | 字段 | 返回结果 |
| --- | --- | --- |
| `send` | `chat_id`, `content`, `reply_to?`, `metadata?` | `{success: bool, message_id?, error?}` |
| `edit` | `chat_id`, `message_id`, `content`, `metadata?` | `{success: bool, error?}` |
| `typing` | `chat_id` | `{success: bool}` |
| `follow_up` | `session_key`, `kind`, `content`, `metadata?` | `{success: bool, message_id?, error?}` |

`get_chat_info(chat_id)` 是一个独立的代理调用，至少会返回 `{name, type}` 信息。媒体相关操作也遵循相同的结构格式（具体细节将在后续的契约修订中定义，目前为可扩展设计）。

**`follow_up`（A2 能力操作）**。某些入站消息会携带用于操作**共享**机器人身份的凭证（例如 Discord 的交互后续令牌）。根据 §6 的规定，连接器会在边缘节点处提取这些凭证，并将其存储在以会话为键的能力存储库中；这些凭证**绝不会传递到网关**。若要使用这些凭证，网关会发起 `follow_up` 操作，需指定**当前所处的会话**（`session_key`）以及相应的能力类型 `kind`（例如 `discord.interaction_token`）——**注意不能直接传递令牌本身**。连接器会从其存储库中获取真实的凭证值，检查该凭证是否属于当前租户（租户 B 绝不能使用租户 A 的能力），之后再将处理结果发送出去。如果该能力不存在、已过期或租户不匹配，返回的 `success` 值将为 `false`——按照设计，网关没有可重试的凭证，因为泄露的网关根本不会持有任何能力相关数据。相关实现代码位于：
`gateway/relay/transport.py`（`send_follow_up` 函数）+ `gateway/relay/adapter.py`。

## 5. 中断操作（`/stop`）的路由机制

- **网关 → 连接器**：网关会通过出站 WebSocket 发送 `send_interrupt(session_key, reason?)` 操作，以在当前处理请求的过程中插入一个 `/stop` 请求。连接器**必须**将此请求转发给正在处理该 `session_key` 的网关实例（这是路由过程中的固有规则）。
- **连接器 → 网关**：针对某个 `session_key` 的入站中断请求会以 `interrupt_inbound` 数据帧的形式，通过网关的出站 WebSocket 传输过来（参见 §3 中关于传输的说明）——该请求会通过中继总线在各个实例之间路由，最终到达持有对应套接字的实例——随后由连接器的 `on_interrupt(session_key, chat_id)` 函数将其接入现有的会话级中断处理机制，从而取消当前正在处理的请求（其他并行处理的请求则不受影响）。

两种方向的通信都基于网关的出站 WebSocket：网关→连接器的 `/stop` 请求通过该通道发送，而连接器→网关的中断请求则作为标准化的事件，通过相同的“入站”回传通道传输。

## 6. 信任边界与签名内容的处理（A2）

**连接器是唯一的加密/身份验证边界。网关不会对任何内容进行重新验证。**

Webhook 签名机制（如 Discord 的 ed25519、Twilio 的 HMAC、WeCom 的 BizMsgCrypt）都是基于原始字节数据计算得出的，而且某些消息内容还会使用共享密钥进行**加密**处理。连接器为多个租户托管同一个**共享**机器人，同时存储着每个租户的平台密钥，因此它需要：

- **在边缘节点处进行验证/解密**（因为密钥仅存储在那里）；
- **将消息内容转换为针对特定租户的 `MessageEvent` 格式**（参见 §3）；
- **从消息中提取所有与共享身份相关的凭证**，并将其存储在以会话为键的能力存储库中（具体实现方式参见 §4 中关于 `follow_up` 的说明）；
- **仅转发经过处理的 `MessageEvent` 内容**——绝不会传输原始的签名内容。

因此，网关在传输过程中**不会**对消息的签名或加密内容进行任何验证，它完全信任已转换后的标准化事件。这是网关端所遵循的强制性规则（相关测试代码位于 `tests/gateway/relay/test_relay_sheds_crypto.py`：该传输处理模块不会导入或调用任何与平台加密相关的功能）。

**为何不采用“逐字节转发签名内容，让网关重新进行验证”的方式？**
因为在不可信、可被丢弃的租户级网关环境中，这种方案是行不通的：

- 要重新验证 Twilio 的 HMAC 或 WeCom 的加密内容，就必须将**共享的签名密钥**交给网关——而这本身就意味着信息泄露，而在共享机器的情况下，这属于**跨租户**的信息泄露。
- WeCom 的消息内容是使用共享密钥进行加密的；连接器仅为了路由目的就需要在边缘节点处解密，因此如果继续转发加密后的内容，同样需要将密钥交给网关。
- Discord 的交互令牌是存储在签名后的 JSON 内容中的——你无法既保留原始字节数据，又同时移除其中的凭证，因为它们实际上是同一组字节。

因此，故意放弃了字节级的原封传输方式：连接器会对处理后的事件进行重新序列化，然后网关再对其信任。这样一来，直接传输路径和中继传输路径就实现了统一——两者都遵循“在边缘节点进行验证，然后输出标准化事件”的原则，唯一的区别在于传输机制的不同。有关 A2 方案的完整说明以及连接器端的存储机制，可参阅 `docs/capability-trust-boundary.md`（连接器代码库位于 `gateway-gateway` 目录下）。

### 6.1 频道身份认证（即连接器与网关之间的连接链路）

在 A2 模型中，由于网关可能是由客户自行管理且暴露在公网上的，因此连接器成为唯一持有平台密钥的实体，所以连接器与网关之间的连接链路本身也需要进行身份认证。网关会持有由注册或配置流程生成的**每个网关专用的密钥**（可通过 `hermes gateway enroll` 命令让连接器执行 `/relay/enroll` 操作，或通过托管式的自服务流程执行 `/relay/provision` 操作），该密钥用于验证其出站 WebSocket 升级请求。该认证机制采用 HMAC-SHA256 算法，并配有多密钥轮换验证机制（网关端相关代码位于 `gateway/relay/auth.py`，连接器端相关代码位于 `src/core/relayAuthToken.ts`）。

| 通信方向 | 用于认证的凭证 | 认证机制 |
|---------|----------------|----------|
| 网关 → 连接器 WebSocket 升级请求 | 每个网关专用的密钥 | 在 `/relay` 升级请求中添加一个 `Authorization` 类型的承载头，其中包含的令牌格式为 `base64url(payload:exp:sig)`，其中 `payload` 的值为网关标识符，`sig` 的值为通过对 `payload` 和过期时间以及密钥进行 HMAC 计算得到的签名。连接器会验证该令牌，如果发现匹配失败、令牌缺失或已被撤销，就会拒绝升级请求，并返回 4401 错误码。经过认证的租户信息来自连接器的内部存储，而非来自初始的 `hello` 请求帧。 |
| 连接器 → 网关的入站请求（`inbound` / `interrupt_inbound` 数据帧） | ——（通过已认证的 WebSocket 通道传输） | 入站请求会通过网关已认证的出站套接字直接发送过来（参见 §3），因此无需对每条消息单独进行签名处理。虽然在注册或配置阶段仍会为每个租户生成一个**专用的消息传递密钥**，以保持向后兼容性，但该密钥目前已不再用于对入站消息进行签名。 |

这就是所谓的**通道级**认证机制——它与平台级的加密机制是相互独立的，因为传输过程中仍然会完全丢弃平台级的加密内容（参见 §6）。网关本身不持有任何平台级密钥；每个网关专用的密钥仅用于验证连接器与网关之间的连接链路。关于完整的威胁模型以及注册、密钥轮换和紧急关闭机制的设计方案，可参阅 `docs/connector-gateway-auth-design.md`（连接器代码库位于相应目录下）。

## 7. 每个实例的消息传递机制与管理平面（第 6 阶段）

在 1–5 阶段中，连接器被视作单租户的前端节点：某个租户的入站消息会被直接发送到该租户对应的网关套接字。**第 6 阶段则实现了按实例级别的消息传递**——同一个共享机器人可以在一个租户内为多个用户或代理提供服务（例如一个 Discord 社群或一个 Telegram 机器人），而不会发生跨实例的消息混传——同时还引入了一个小型**管理平面**，供代理或托管式门户使用，用于定义谁可以查看什么内容以及哪些内容是相关的。所有这些功能都位于**连接器端**；网关唯一需要新增的责任就是在启动时声明自身的相关内容处理策略（参见 §7.3）。

### 7.1 消息传递控制机制（位于连接器端，仅用于提供信息参考）对于每个传入的事件，连接器会通过组合三个“与”逻辑的过滤器来决定由哪些实例接收该事件。这些过滤器并非由网关实现——它们运行在连接器中——但它们定义了网关所依赖的消息投递规则：

| 层级 | 判断条件 | 权威信息来源 |
| --- | --- | --- |
| **所有者/范围 ∧ 主体** | 该实例是否有权限*查看*此消息的发送者？ | 每个用户的 `user_id → instance` 绑定（即所有者层级）+ 每个实例的 `(guild, channel)` 范围授权 + `owner-only`/`allow-list`/`any` 类型的主体策略。 |
| **可见性层级** | 该实例的所有者是否真的能在 Discord 中`VIEW_CHANNEL`此消息？ | Discord 的实时 ACL（实际权限），采用“失败即拒绝”原则。用于缩小过宽的范围授权范围。 |
| **相关性** | 在满足可见性条件的前提下，代理是否应当处理该消息？ | 第 7.3 节中定义的相关性策略（如地址过滤/自由回复/允许机器人参与）。 |

这些过滤器的组合仅用于**缩小**可投递的消息范围（`deliver ⇔ authorized ∧ visible ∧ relevant`）；**所有者层级会绕过相关性判断**（发送者自己的消息总会送达其所属实例——因为无需@提及自己的代理）。未被授权用户的消息则无法送达任何实例（直接拒绝）。完整的架构设计及不变量均存储在连接器代码库中（`NousResearch/gateway-gateway`），本节仅为面向网关的简要概述。

### 7.2 管理接口（连接器端，需认证）

连接器会配置需要认证的管理接口。这些接口与 WebSocket 升级过程采用**相同的双重认证机制**：要么使用由管理平台签发的、带有 `aud=agent:{instanceId}` 标识的 RS256 JWT，要么使用网关自身的专用密钥令牌（参见第 6.1 节的 `make_upgrade_token` 函数）。在两种情况下，连接器都会从其**存储的记录**中获取权威的 `{tenant, instanceId}` 值——**绝不会**从请求体中获取（请求体中指定的 `instanceId` 会被忽略）。

| 接口路径 | 功能 |
| --- | --- |
| `POST /manage/link` | 生成一个短期有效的代码，用于将平台账户绑定到已认证的实例（即 `/link <code>` 流程；连接器会从传入事件中读取已认证用户的 `user_id`）。 |
| `POST /manage/scope`, `/manage/scope/release` | 为已认证的实例申请或释放 `(guild, channel)` 范围授权。一个频道最多只能被一个实例拥有（非重叠性是主键约束的要求）。 |
| `POST /manage/principal` | 设置实例的主体策略（`owner-only` \| `allow-list` \| `any`）。 |
| `POST /manage/dm-default` | 设置用户的默认私信处理实例（当用户绑定多个实例时的私信处理优先级判定依据）。 |
| `POST /relay/policy` | 声明实例的**相关性策略**（参见第 7.3 节）。 |

这些接口由连接器管理（管理平面并不属于网关代理的处理路径）；网关仅会调用 `POST /relay/policy` 接口（参见第 7.3 节）。其余接口则由管理平台或 `hermes` CLI 控制。

### 7.3 相关性策略的声明（网关的职责）

相关性层（参见第 7.1 节）实际上是为网关自身的行为参数（如 `require_mention`、`free_response_channels`、`{PLATFORM}_ALLOW_BOTS`）定义的租户级统一规则。因此，用于消息中转投递的规则也与这些参数一致，网关会将这些参数转换为一个**与具体平台无关的策略**，并在启动时（在获取到网关专用密钥之后）通过 `POST /relay/policy` 接口将其上传。

相关逻辑位于代码库的 `gateway/relay/__init__.py` 文件中的 `relay_relevance_policy()` 函数，该函数最终会调用 `send_relay_policy()` 函数：

| 字段 | 类型 | 来源 | 含义 |
| --- | --- | --- | --- |
| `platform` | 字符串 | `relay_platform_identity` | 该策略适用的平台。 |
| `requireAddress` | 布尔值 | `require_mention` | 非所有者发送的消息必须@提及或回复给机器人，才被视为相关消息。 |
| `freeResponseScopes` | 字符串数组 | `free_response_channels` | 在这些频道范围内，可免除“必须@提及”的要求。其范围标识与第 7.1 节中的范围授权使用相同的词汇。 |
| `allowOtherBots` | 布尔值 | `{PLATFORM}_ALLOW_BOTS ∈ {mentions, all}` | 是否允许机器人发送的消息通过（默认为关闭）。 |

认证过程使用的是网关专用的升级令牌（参见第 6.1 节），因此连接器会将该策略绑定到已认证的实例上。网关是**权威信息来源**，并且会在**每次启动时**重新声明该策略（实现完全替换，类似于配置阶段对 `routeKeys` 的更新——具备自修复能力）。如果生成的策略均为默认值，网关则不会发送任何内容（因为连接器已有的默认规则与之匹配）。该 POST 请求采用**软失败机制**：即使出现错误，也会记录日志并继续启动流程——相关性判断只是叠加在授权机制之上的优化层（参见第 7.1 节），并非启动过程的必需条件。该机制**不会新增网关的输入接口**，也**无需新的凭证**——它直接复用网关专用密钥以及与 `/relay/provision` 接口相同的服务器。

> 相关性过滤会在连接器唤醒已缩减到零个实例的代理之前（即第 5 阶段）执行，因此被过滤掉的聊天内容不会导致代理被启动——相关性判断既是实现实例数量缩减的关键机制，也是一种用于确保正确性的过滤手段。

## 8. 版本控制策略

- `contract_version` 是一个整数；仅在实验阶段出现**增量式变更**时才进行版本升级（如新增可选字段、新增操作类型等）。
- 若发生**破坏性变更**（如字段重命名/删除、语义改变等），则需同时更新两个代码库并提升版本号。
- 连接器的第一个 Pull Request 应注明其所依据的该配置文件的提交 SHA 值。
