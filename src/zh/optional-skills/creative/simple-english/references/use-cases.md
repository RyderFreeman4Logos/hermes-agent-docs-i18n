# 超出文档应用场景的用法

STE最初是为飞机维护手册而设计的。其核心特性——每个词仅一个含义、短句结构、以条件优先的指令表述——同样适用于任何一旦理解错误就会造成严重后果的文本。到第8版发布时，64%的注册STE用户来自航空航天与国防领域之外。

下文中列举了各类应用场景及其相应调整方式。

## 错误信息与CLI输出

模式：流程导向型。这是STE最具价值的应用场景：一条错误信息就如同在凌晨2点向疲惫的读者下达的指令。

格式规范：首先说明发生了什么（用一般过去时），若已知原因则一并说明，最后给出修复所需的指令或条件。

> **修改前：** 哎呀！尝试建立连接时出现了问题。请确认您的凭据配置正确，然后重试。
> **修改后：** 与数据库的连接失败。用户`app`的密码不正确。请设置`DB_PASSWORD`后再尝试连接。

## 运维手册与标准操作程序

模式：偏向严格的流程导向型。这正是STE的强项领域——应急运维手册本质上就是一种维护手册。

- 每一步均为强制性指令，每步仅一条说明，且以条件优先。
- 每一步前先给出警告，先说明指令，再阐述相关风险。
- 严格限制在20字以内：处于紧急状态下的操作人员只需快速浏览每一句话。

## 事件报告与事后分析

模式：描述导向型。仅使用一般过去时——而用现在完成时描述时间线（如“我们已查明……”）则会掩盖事件实际发生的时间。

> **之前：** 我们发现了一个问题，可能影响了部分用户访问该服务的能力。  
> **之后：** 在协调世界时 14:02 至 14:31 期间，有 12% 的请求失败。14:00 进行的部署去掉了缓存预热步骤。  

STE 避免使用含糊表述（如“可能影响了”）——报告会明确已掌握的信息，其余情况则标注为“未知”。这样的写法更诚实，因为事实本就如此。  

## 提交信息与 PR 描述  

格式：正文采用描述性语言，主题行使用祈使句式。该格式已与 STE 的规范一致：主题行为祈使句，正文中仅陈述过去的事实。需遵循替换规则，并将正文长度控制在 25 单词以内。同时删除“此 PR 的目标是”这类表述。  

## API 变更日志与版本说明  

格式：采用描述性风格。尽可能做到每个条目对应一个变更，用一句话概括。属于“破坏性变更”的条目需遵循警告格式——先列出命令：“请将调用方式更新为 `v2/users`。`name` 字段已被拆分为 `first_name` 和 `last_name`。”  

## 面向 AI 智能体的指导（提示词、AGENTS.md、技能定义）  

格式：采用步骤化说明。系统提示词是一种由无法提问的读者执行的流程——这正是 STE 所设计的适用场景。  
- 每句只包含一条指令，这样规则既便于单独引用，也难以被部分执行。  
- 每个词仅有唯一含义，可避免模型将“check”、“verify”和“validate”视为三种不同的操作。  
- 先说明条件（“如果构建失败，则停止”）比在句尾列条件更有效，因为后者容易被模型忽略。  
- 不要使用“should”——模型会将“should”理解为可选操作。应使用“must”或直接删除该规则。
## 支持宏指令与状态页更新说明

格式要求：采用描述性语言，单条说明不超过25个单词。鉴于许多用户群体以非英语母语者为主，应避免使用“对于由此造成的不便，我们深表歉意”这类表述，而应直接说明情况，例如：“API服务中断了18分钟。在此期间上传的内容已保存，将于今日进行处理。”
