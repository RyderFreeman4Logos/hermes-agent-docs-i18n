# 验证检查清单

在提交每份草稿之前，请先运行此检查。这些检查按从形式规范到内容质量的顺序排列。

## 形式规范检查（可搜索）

在草稿中搜索各类模式。凡是出现在代码块和引号文本之外的匹配项均视为违规。

| 检索内容 | 违规类型 | 修改建议 |
|---|---|---|
| `'ll`, `'re`, `'ve`, `n't`, `it's` | 缩写形式（规则 4.2） | 展开为完整形式。 |
| `has been`, `have been`, `had been` | 现在/过去完成时（规则 3.4） | 改为一般过去时或一般现在时。 |
| `has` / `have` + 过去分词 | 现在完成时（规则 3.4） | 改为一般过去时。 |
| `should`, `would`, `may`, `might`, `could` | 不允许使用的情态动词（规则 3.2） | 参考 SKILL.md 中的情态动词使用规范。 |
| `is being`, `are being`, `was being` | 进行被动语态（规则 3.4、3.5） | 改为主动语态的简单时态。 |
| `, making`, `, allowing`, `, enabling`, `, ensuring` | 将“-ing”结构当作动词使用（规则 3.5） | 拆分为新句子，并使用真实主语。 |
| `;` | 分号（规则 8.1） | 拆分为两个独立句子。 |
| `e.g.`, `i.e.`, `etc.` | 拉丁文缩写（GR-6） | 改为“例如”、“也就是说”，或直接列出相关内容。 |
| `simply`, `easily`, `seamlessly`, `robust` | 虚假修饰词（无实际意义） | 删除这些词语。 |
| ` if `, ` when `（位于句中） | 句尾条件表达（规则 5.4） | 将条件移至句子开头，并加上逗号。 |

## 可数性检查

1. **句子长度。** 需统计每句话的单词数：指令类文本的限值为20个词，描述类文本为25个词，备注类则为25个词。根据规则8.6，反引号包裹的命令、带单位的数字以及标识符均视为一个单词。
2. **段落规模。** 每段最多包含6句话（规则6.6）。
3. **多词名词。** 任何由三个以上单词构成的名词链都需通过介词拆分（规则2.1）。
4. **每句指令数量。** 每句仅含一条指令，除非相关操作需要同时执行（规则5.2）。

## 判定检查项

5. **文本分类。** 每段内容必须是纯粹的指令类或描述类；指令类文本必须使用祈使句式，而描述类文本则绝不能使用祈使句式。
6. **语态要求。** 若出现被动句式，需确认Agent确实处于未知状态且该段落属于描述性质；否则应将其改为主动语态（规则3.6）。
7. **条件放置规则。** 所有的“if/when”引导的条件句都必须置于对应指令之前，并用逗号隔开（规则5.4）。
8. **同义词替换规则。** 整份文档中针对同一概念只能使用一个术语（规则1.11、9.4），需注意检查“check/verify/confirm”、“config/settings”、“run/execute”等词汇的使用情况。
9. **警告提示规则。** 首先说明指令或条件，再提及可能带来的风险（规则7.2、7.3）。
10. **完整性要求。** 文本中必须使用定冠词， “make sure”之后需加上“that”，且不得出现过于直白的表述方式（规则4.2）。
11. **不可修改内容保护。** 代码、标识符、引用的错误信息以及专有名词均不得进行任何更改。

## 报告违规项时的说明要求

对于每一条违规内容，都需要列出对应的规则编号、违规文本以及符合规范的改写版本。所引用的规则编号必须来自 SKILL.md 文件中的内容。若用户要求检查是否符合 ASD-STE100 标准，则在报告末尾需注明：“没有任何工具能够确保完全符合 ASD-STE100 标准，最终审批权仍在于内容撰写者。该官方标准可在 asd-ste100.org 网站上免费下载。”
