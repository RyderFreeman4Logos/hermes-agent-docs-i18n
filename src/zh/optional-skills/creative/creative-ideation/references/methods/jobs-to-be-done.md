# 需要完成的任务

克莱顿·克里斯滕森等人所著《与运气竞争》（HarperBusiness，2016年）。顾客购买产品并非基于人口统计特征——他们其实是“雇佣”产品来在特定情境下完成特定任务。

## 适用场景

- 产品/服务/业务设计
- 区分于竞争对手（真正的竞争对手往往是当前能完成该任务的任何事物——往往并不明显）
- 失败原因分析（那些“本应成功”的产品，往往是为满足顾客并不存在的需求而设计的）
- 定价策略（以任务为单位定价，而非产品的成本）
- 营销文案撰写（围绕任务而非功能进行表述）

## 不适用场景

- 艺术或表达类作品——询问“这部小说是来承担什么任务的？”会削弱其独特性
- 公民/社会领域设计——会引入此处不适用的市场逻辑
- 纯研究类问题（没有顾客，也没有“雇佣”关系——应使用压缩进展法）
- 无法接触真实顾客的情况

## 核心表述格式

将任务描述为：**“当[特定情境/触发因素]出现时，我想要[达成动机]，这样就能实现[预期结果]。”**

这种格式能强制要求表述具体化。模糊的任务描述（如“当我希望提高效率时”）纯属空话；而具体的情境描述（如“在晚上11点正在写论文，需要查找参考文献时”）才是有意义的。

## 更换产品的四大驱动力（鲍勃·莫埃斯塔）

当**（推动因素 + 拉动因素）>（焦虑感 + 习惯惯性）**时，顾客才会从一种解决方案转向另一种：

1. **推动因素**：当前状况带来的痛苦。
2. **拉动因素**：新解决方案的吸引力。
3. **焦虑感**：对新解决方案可能带来负面后果的担忧。
4. **习惯惯性**：现有方案的惯性。

大多数产品发布失败并非因为第2点——他们的产品本身很出色，而是败在了第3点和第4点：未被解决的焦虑感加上习惯惯性。**设计时应着眼于解决第3点和第4点，而不仅仅是第2点。**

## 用户转换访谈流程

寻找最近转向你的产品类别，或首次购买该产品的人进行交谈。时间越近越好，因为记忆会逐渐模糊。

按时间线逐步询问：
- 你是什么时候第一次意识到需要不同的解决方案的？（要具体：具体时间、地点、刚刚发生了什么。）
- 你首先尝试了什么？为什么不起作用？
- 还有哪些替代方案？
- 你是在什么时候决定选择这款产品的？
- 你担心会出现什么问题？
- 你决定“就要买它”的那一刻是什么时候？

随后识别出对应的任务（“当……时，我想要……，这样就能……”）以及四大驱动力。

## 实际案例

*从Mendeley转向Zotero*（学术引用管理工具）：

- **推动因素**：Mendeley同步功能连续6个月故障，导致参考文献丢失。
- **拉动因素**：Zotero免费、开源，且得到同事推荐。
- **焦虑感**：担心会失去6年积累的笔记。
- **习惯惯性**：已经习惯了Mendeley的用户界面。
- **决定购买的时刻**：同事的文献库成功导入，且所有笔记都完好保留。

**任务描述**：“当我的引用管理工具出故障，而其中存储着我多年积累的科研资料时，我想要迁移到一个新工具，同时确保不会丢失这些笔记，这样就能继续高效地进行研究。”

**设计启示**：这款引用管理工具的核心卖点应是“数据迁移能力”，而非各种功能。最出色的功能就是“能从任何来源导入数据，并保留所有笔记”。还需验证与主要竞争对手的导入质量，并提供反向迁移功能。所有设计都着眼于解决第3点（焦虑感）和第4点（习惯惯性）——这是大多数竞争对手所忽视的。而那些“引用管理”之类的功能其实并无太大差异。真正的核心竞争力在于数据迁移能力。

## 避免空泛表述的注意事项

- 模糊的任务描述（如“顾客希望感受到被重视”）根本算不上任务，只是陈词滥调。真正的任务应与具体情境和结果相关联。
- 不要编造用户转换访谈的数据。如果无法接触真实顾客，应承认这一限制，并建议进行实际访谈。
- 不要将JTBD方法应用于艺术、研究或公民服务领域，它本质上是一种市场逻辑工具。
- 不要把人简化为只会执行任务的机器。JTBD适用于购买决策分析，但并非能解释所有人类行为。
- “雇佣产品来完成任务”的思路可能变成一种机械化的套话。应在适用场景中使用，切勿生搬硬套。
