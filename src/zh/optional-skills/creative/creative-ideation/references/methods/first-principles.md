# 第一性原理

即亚里士多德所说的“原始原则”。将问题分解为那些你确信正确的假设，然后在不默认沿用任何既有设定的前提下重新构建解决方案。通常会结合“5个为什么”法来深入探究每个假设的由来。

## 适用场景

- 某个领域积累了大量可能已不再适用的实践经验；
- 你处于一个不熟悉的领域，需要逐步建立对它的理解；
- 你怀疑现有的标准框架存在错误；
- 希望降低成本或复杂度（往往累积的冗余成本才是主要开支）；
- 进行相关领域的教学（通过第一性原理的重新构建，能凸显初学者真正需要的内容）。

## 不适用场景

- 你对该领域了解不足——外人套用第一性原理往往会导致错误的结论；
- 替换方案所带来的交易成本高于其带来的收益；
- 问题本身无法进一步分解（涉及美学、社会因素或整体结构问题，过度分解会破坏其内在一致性）；
- 你试图显得独具创新性——生硬套用第一性原理思维只会显得粗糙低劣。

## 实施步骤

1. **精准描述问题。**
2. **列出传统解决方案中的所有假设。** 传统方法默认了哪些条件？列出5到10项，包括那些“不言而喻”的假设。
3. **对每项假设进行分类：**
   - **物理性假设**——基于自然法则，不可妥协；
   - **信息性假设**——基于逻辑、数学或信息论，若放宽会导致矛盾；
   - **传统性假设**——本可以有其他选择，但需考虑兼容性；
   - **历史性假设**——在某些阶段是必要的，但现在可能不再适用；
   - **教学性假设**——为便于教学而简化的设定，可能与专家的实际操作方式不同。
4. **针对每一项非物理性或非信息性假设**：它仍然起到关键作用吗？传统性和历史性假设才是带来改进的关键所在。
5. **重新构建。** 仅依据物理性和信息性约束以及具体场景，构建一个初步方案。
6. **运用切斯特顿的边界原则。** 对于每一个被移除的元素，找出最初添加它的原因。如果找不到原因，也*不要直接断定没有原因*——应认为自己还不够深入探究。
7. **决定是否采用新方案。** 即使重新构建后的方案在技术上更优，也要考虑交易成本、生态系统兼容性以及团队对它的熟悉程度。

## 实例分析

**问题**：典型的CRUD Web应用——包含登录功能、控制面板以及少量CRUD操作对象。传统技术栈包括React + Node/Express + PostgreSQL + REST API + 托管平台。代码量约12,000行，每月托管费用约为100美元。

**相关假设**：
- React：属于传统选择，具有历史背景（单页应用概念约出现于2014年），同时因被广泛用于教学而成为常见选择。
- 后端与前端分离：属于传统架构；在多客户端场景下是信息性假设，而在单客户端场景下则属于历史性假设。
- PostgreSQL：在需要高并发处理或遵循ACID事务规范时属于物理性假设，否则为传统选择。
- 前后端之间的REST API：最初是基于信息隔离需求而设计的（作为网络边界），但在单客户端应用中已变为历史性设定。
- 托管平台：属于传统选择，其存在源于早期数据中心的复杂性，同时也因教学目的而被广泛采用。

**具体场景**：仅有100名用户，数据量约10MB，无需实时功能，为单客户端Web应用，且没有高可用性要求。

**重新构建后的方案**：
- 服务器端渲染HTML，辅以少量JavaScript模块。（无需单页应用架构，也无构建流程和API层。）
- 使用SQLite单文件数据库。（无需PostgreSQL服务器，备份只需复制文件即可。）
- 仅需一台小型虚拟机。（无需托管平台，部署操作可通过`rsync`命令配合`systemctl restart`完成。）
- 仅使用一个Go/Python/Ruby编写的二进制程序。

**效果对比**：代码量从12,000行降至约1,500行，每月成本从100美元降至约5美元。但相应地，简历上的技术亮点减少，熟悉此类架构的外包人员较少，也无法快速支撑百万级用户规模。

**切斯特顿的边界原则应用**：上述传统方案对某些应用来说是有效的，而重新构建的方案仅适用于当前这个具有特定约束条件的应用。对于高并发、多客户端或处理海量数据的应用，则需要采用不同的设计思路。

## 避免低劣思维的注意事项

- 最糟糕的低劣表现，就是将第一性原理思维“表演”出来——声称要“从第一性原理出发思考”，结果只是稍作调整的传统方案。真正的输出应当有明显差异。
- 当你实际上只是在运用常识时，不要刻意标榜自己使用了第一性原理。
- 避免陷入“技术英雄”的刻板形象。真正的第一性原理往往只是揭示该领域早已知晓的道理。
- 不要建议移除自己并不理解的结构。切斯特顿的边界原则必须严格执行。
