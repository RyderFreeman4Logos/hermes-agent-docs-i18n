# 取消订阅操作流程指南

该指南介绍了代理如何使用Hermes原生工具执行各平台的`optout.method`指令。请严格遵守**最小信息披露原则**：
仅提交信息主体的**自身标识符**，且仅提交平台官方渠道要求的字段（具体列表可参考`pdd.py plan`中的各平台说明）。绝不可泄露更多信息，且在处理任何第三方或间接记录之前，必须先确认该记录确实属于信息主体（详见“区分信息主体”与“间接曝光”章节）。若存在无需确认记录即可操作的场景，可参考下文的对应说明。

**自主执行模式**：`pdd.py next <subject>`会自动完成整个流程——它决定适用哪种方法，优先处理上级平台记录，并将需人工处理的任务转交至汇总模块。在默认的`autonomy=full`模式下，系统会逐条提交信息并立即执行对应操作；初始收集时获得的同意即视为授权依据。这些流程指南详细说明了每种操作类型的具体执行方式。

## 取消订阅策略：默认采用盲式取消订阅（非备用方案）

**操作员指导策略**：对于所有提供可访问删除渠道的平台，无论相关记录是否已确认，都应提交取消订阅或删除请求——具体选择哪种方式由各平台自行决定。切勿仅列出“无法搜索到这些记录”的待办事项。

- **该策略的合理性（不违反最小信息披露原则）**：盲式取消订阅仅将信息主体的自身标识符发送至平台的官方删除渠道。您只是将数据提供给平台用于删除操作，而非泄露新信息或对第三方记录采取行动。（第三方/间接记录属于例外情况：此类记录仍需先确认其确实存在。）
- **取消订阅流程同时可作为权威查询手段**：通过电子邮件、出生日期和法定姓名进行匹配后仍显示“无结果”的引导式查询，其可靠性远高于任何爬虫搜索——因为平台是使用真实标识符自行进行匹配的。在采用引导式查询的平台上，“执行取消订阅”与“直接搜索”属于同一操作步骤（例如CheckPeople，详情见`site-playbooks.md`）。

### 表单无法使用时 → 默认使用规定的权利申请邮箱（核心规则）

当删除**表单**存在阻碍自动化操作的障碍（如复杂的验证码、无法清除的Cloudflare防护墙、JS加密的内容屏障）时，应直接使用平台规定的权利申请邮箱，而非仅标记为“已阻止”并等待人工处理——除非存在简单的浏览器内解决方案。各平台的决策顺序如下：

1. **是否有简单的浏览器内解决方案？**（如一键删除功能、验证码可在普通家用浏览器中自动清除的引导式流程、纯邮件验证）→ 直接在浏览器中完成操作。
2. **表单无法使用，但存在规定的权利申请邮箱？** → 由操作员通过网页邮箱发送删除/取消订阅邮件（仅包含姓名、所在州及联系邮箱）。目前这种方式优于仅标记为“已阻止”。
3. **既无简单解决方案，也无规定的权利申请邮箱** → 标记为“已阻止”（或记录为`human_task_queued`并明确最终处理状态）。
4. **仅有需要政府身份证明/实体邮件的处理渠道** → 不得自行尝试处理（遵循最小信息披露原则），需由人工决策。

所谓“规定的权利申请邮箱”，指的是平台自身公布的地址（隐私政策、取消订阅页面或有效的删除申请入口）。**切勿**使用仅来自第三方博客或Reddit的邮箱地址。各平台的处理流程及注意事项已预先记录在`references/site-playbooks.md`中，后续操作可直接引用，无需重复分析。

### 扫描前先对外部开源情报列表进行分类筛选

在核查任何外部“人员信息开源情报”目录时，需将**第一方平台**（需要删除的目标平台）、**元搜索/链接聚合平台**（无第一方数据，无需操作，也不需提交取消订阅请求）、**集群式前端平台**（由上级平台覆盖，例如addresses.com → Intelius）以及**非平台工具/API/管辖权不符的平台**区分开来，后者可直接跳过。这些跳过列表保存在`site-playbooks.md`中。

## 扫描流程（所有方法）

应优先以最低成本构建信息暴露地图（在具备可访问删除渠道的平台上，即使扫描结果不确定，也可采用盲式取消订阅方式——详见上文策略部分）。需运行`pdd.py plan`中列出的**所有**`search_vectors`项（即平台`search.by`支持的每一种姓名、地址、电话号码和电子邮件组合）——不同的查询向量会针对同一人生成不同的记录，需对找到的URL进行去重处理。

1. 对平台的`search.url`执行`web_extract`操作（快速将HTML转换为Markdown格式），查找`search.match_signal`。根据`search.url_patterns`生成对应查询的URL，并注意`search.url_format_quirks`中的特殊要求（详见下文）。
1b. **使用`site:`前缀查询搜索引擎（成本低，建议尽早并行执行）**：通过`web_search`执行`site:<broker-domain> "First Last"`查询（可添加城市/邮政编码或唯一的电话号码/地址，以减少同名干扰），通常能一次性返回**精确的资料页面URL**——这不仅能确认记录确实存在，还能直接给出原本需要手动推导的不透明URL，如 `/find/person/<id>` 或 `/p/<slug>`。实际应用中该方式具有两大优势：(a) 能快速区分同名人员——搜索结果中的摘要信息会显示年龄和城市，便于在获取任何数据前区分信息主体与同名亲属；(b) 使用宽泛的 `"First Last" <ZIP OR unique-address>` 查询（不加`site:`前缀）能发现**尚未收录在您数据库中的平台**（例如information.com、peoplefinders.com），可将其作为额外的信息来源记录下来。注意：返回空结果的`site:`查询属于“结果不确定”（许多平台页面未被索引或设置了`noindex`属性），并非“未找到”。
2. 如果页面为JS动态渲染或无有用信息，可使用`browser_navigate` + `browser_snapshot`操作（还可通过`browser_type`/`browser_click`模拟在网站内点击搜索框）。
3. 如果遇到隐形防护/Cloudflare封锁，可通过`terminal`调用`scraping`技能尝试破解。**如果平台记录中设置了`search.antibot`机制（例如datadome），结果将被设备检测验证码拦截**：使用云浏览器/隐形浏览器（Browserbase）或`scraping`技能可能可以突破封锁；如果没有合适的工具，切勿重复尝试——只需执行`pdd.py record <subject> <broker> blocked`并继续后续操作（稍后使用隐形浏览器重新扫描即可找到该记录）。
3b. **操作员浏览器路径（针对反爬网站的可靠解锁方式）**：通过数据中心IP地址和无头浏览器指纹获取Cloudflare/DataDome密钥，因此常规的`web_extract`操作、无代理的代理型代理浏览器甚至云浏览器往往都无法突破封锁——但**操作员日常使用的普通浏览器（家用IP地址、真实指纹）却能直接访问**。对于任何被封锁的网站，需将基于`search.url_patterns`生成的搜索URL以可直接复制的形式提供给操作员，同时提供可用于判断的身份参考信息（当前及历史地址、年龄、特殊特征），以及同名人员/亲属的监控列表，再请操作员给出最终判断或提供截图（代理可读取截图内容）。这是一种**优先级的扫描方式，而非备用方案**——应将操作员的实时核查结果视为权威依据，并记录真实的判断结果（“已找到”、“未找到”或“间接曝光”），同时标注`scanned_via: operator_browser`。对于代理浏览器无法访问的取消订阅表单，也应采用相同方式——按照最小信息披露原则逐项指导操作员填写，提交前需暂停确认。（这正是同一方法能用于破解代理无法打开的邮件验证链接的原因——详见验证流程章节。）
4. 收集证据：将记录的URL和`browser`截图保存到信息主体的`evidence/`目录中，然后执行`pdd.py record <subject> <broker> found --found true --evidence '{"listing_urls":[...]}'`命令。

如果确实不存在相关记录，则执行`pdd.py record <subject> <broker> not_found`并继续后续操作。

### 404错误（或空页面）属于“结果不确定”，而非“未找到”

如果生成的搜索URL返回404错误，几乎总是意味着**URL格式有误**，而非该人员确实不存在。绝不可仅因404错误就记录为“未找到”。正确的处理方式如下：
1. 重新检查平台的`search.url_patterns`/`url_format_quirks`设置，然后重新生成URL。
2. 转而使用**网站内的搜索框**：通过`browser_navigate`跳转至搜索页面，使用`browser_type`输入原始查询内容，点击`browser_click`执行搜索，再读取页面最终显示的**标准结果URL**。
3. 只有在平台自身的搜索功能也返回空结果集时，才能记录为“未找到”。
4. 如果是URL格式有误，需在`references/brokers/<id>.json`文件中修改`url_patterns`和`url_format_quirks`设置，确保下次扫描时使用正确的格式——具体规则见下文。

### 记录每个扫描平台的URL格式及特殊要求

每当您发现某个平台的URL实际结构如何（路径布局、连字符与斜杠的使用方式、是否需要邮政编码、缩写处理规则、查询参数搜索功能、反爬机制等），都需将其记录在该平台的`references/brokers/<id>.json`文件中，分别存放在`search.url_patterns`（URL模板）和`search.url_format_quirks`（特殊要求及导致404错误的表单类型）字段中。同时更新`last_verified`时间戳。这样就能确保每次扫描时都使用相同的URL结构，无需重复探索。如果取消订阅表单的实际要求与记录中的设置不同（如需要额外字段、验证码或账户登录），也需同步修改`optout.requires`/`optout.inputs`/`optout.tier`字段——这些参数决定了操作等级和最小信息披露范围。此外，还需在`optout.quirks`字段中记录取消订阅功能中的特殊问题（例如某些平台要求提供资料页面URL，但未为该信息主体提供此类链接；仅支持通过电子邮件处理；需授权代理才能操作等）——规划工具会以`optout_quirks`的形式列出各平台的这些特殊要求。例如：Radaris平台有时仅将信息主体显示为静态的地址表行，且没有“查看资料”链接，因此无法使用需要资料页面URL的 `/control-privacy` 功能，此时应改用 `optout.email` 方式，而非提交同名人员的URL。

### 区分信息主体与同名人员及亲属

人员搜索网站中存在大量同名人员和家族群体。在记录“已找到”结果之前，必须确认该记录确实属于**信息主体本人**（可通过出生日期、已知的当前/历史地址或查询时使用的标识符进行交叉验证）。以下两种情况可作为证据记录，但不属于信息主体本人的真实记录：
- **同名人员**：姓名相同，但为不同的人（出生日期和居住地均不同且无关联），并非信息主体本人。
- **亲属记录**：该记录涉及的是**其他人员**（即亲属），仅在“家庭成员”字段中提及信息主体的姓名，或仅将信息主体的电子邮件/电话号码作为辅助信息。这类记录属于第三方记录，同意机制会正确阻止对其采取操作。关于信息主体仍可请求处理的操作，详见网页表单章节中的“间接曝光”部分。

此外，还有两种容易被误判为“已找到”的虚假阳性情况，实际不应将其计入结果：- **房产记录 ≠ 个人敏感信息（以地址为依据的网站）。**反向地址查询/房产信息网站（如rehold、clustrmaps风格）可通过公开的**房产记录**（建造年份、卧室/浴室数量、上次成交价格、相关事件等）进行匹配，而无需泄露当事人的个人信息——居民/业主的姓名被设置在“查看完整报告”的付费墙或注册环节之后。需区分“该地址存在于公共房产数据库中”（无法移除，状态为`not_found`）与“显示了当事人的个人资料”（可移除，状态为`found`）。只有当与当事人匹配的居民姓名在公开信息中可见时，才记录为`found`；仅通过地址匹配的则记为`not_found`——此类情况无需选择退出，且公共房产记录本身也无法被删除。详情参见`rehold.json`中的`search.match_signal_notes`。

- **SEO模板生成的标题/H1会伪装成“已找到”结果。**许多人物查询网站会将搜索关键词自动插入页面的`<title>`、H1标签以及开头文字中（例如“在{城市}为{姓名}找到了免费公共记录”，“为{姓名}找到了100多条免费公共记录”）。这些内容只是**模板生成的文本，并非实际查询结果**——真正的结果卡片往往来自其他州的同名人士。仅凭标题或开头文字中的`match_signal`信号就会导致误报。必须要有由当事人地址或出生日期验证过的真实结果卡片，否则应完全忽略那些模板生成的标题、开头文字和H1标签。详情参见`truepeoplesearch.json`/`fastpeoplesearch.json`中的`search.match_signal_notes`。

正因如此，“上级代理在采取行动前必须重新核实每一个‘已找到’的结果”这一规则才显得至关重要（`pdd.py show <subject> <broker>`功能会调出子代理记录的证据，以便上级无需重新获取房源链接即可进行二次核实）。如果某个“已找到”的结果被证实是误报，则需通过新的`record ... not_found`操作进行更正，并附上说明撤回原因的证据备注。

## web_form

1. 使用`browser_navigate`导航至`optout.url`，再通过`browser_snapshot`获取表单内容。
2. 仅填写计划处理的`disclosure_fields`字段，并使用`browser_type`/`browser_click`记录操作信息；对于`profile_url`字段，则需粘贴从证据中确认的房源链接。
3. 提交表单后，通过`browser_snapshot`确认提交是否成功，再将截图保存至`evidence/`目录。
4. 调用`pdd.py record <subject> <broker> submitted --disclosed <field> --disclosed <field> --channel web_form`命令进行记录。
5. 如果经纪人要求通过电子邮件进行验证，则需按照下文的**验证流程**操作。

### 间接曝光（以亲属名义/在他人记录中出现你的电子邮件）

你问到了关键问题：如果经纪人列出某位*亲属*的信息，并在其“家庭成员”字段中填写你的姓名，或在其记录中显示**你的**电子邮件/电话号码，那即便该记录的主体是第三方，这也属于关于你的个人敏感信息。对此需通过两种独立途径处理：

- **自助选择退出表单无法解决此类问题。**该表单仅用于删除以你为*主要主体*的记录，它不支持“从其他人的记录中删除我的身份信息”这一功能。若试图使用亲属的地址提交该表单以强制匹配，既会泄露与你有关联但并未明确列出的信息，又属于基于第三方记录的操作，因此不可行。设置同意机制正是为了防止此类情况发生。
- **你可以采取的做法——提出针对性的“删除我的个人信息”请求（符合CCPA第1798.105条及GDPR第17条规定）。**这些权利适用于*你*的个人信息，无论企业将其存储在何处，包括作为他人资料中的数据项。因此，当事人可以给经纪人的隐私处理邮箱发送邮件，要求删除**其自身特定的身份信息**（如该电子邮件地址、电话号码、在家庭成员关系中的姓名等），并说明相关亲属记录是信息来源。这种请求的范围比全面选择退出更为有限，且无需获得亲属的同意——你只需要求他们删除关于*你*的信息即可。此时应使用`render-email`功能，并选择`ccpa`/`gdpr`模板，仅列出当事人自身的身份信息及其出现的位置链接，然后将该请求作为常规的“已提交”→“等待处理”类型的邮件案例进行记录。在法定期限过后，需重新扫描这些身份信息（如电子邮件、电话号码）以确认是否已删除；只有当当事人的身份信息完全消失时，才能标记为`confirmed_removed`。
- **注意事项：**经纪人可能拒绝修改第三方记录，仅允许删除与你相关的特定身份信息，而且他们可能会在重新发布记录时从公共资料中推断出“你在家庭关系中的姓名”。此时报告中应注明仍有残留信息，并不能视为已完全删除。（此为操作指南，非法律建议。）

## email

`pdd.py send-email <subject> <broker> --listing <url> [--kind ccpa|gdpr|ccpa_indirect]`命令会自动完成那些有固定规则的操作（接收者地址必须与经纪人记录中的信息一致，其他任何地址均会被拒绝；`--listing`参数为必填项；该命令会记录“已提交”状态、日志中会记载信息披露情况，并标注“下次重新检查时间”）。实际发送方式则取决于`email_mode`设置：

1. **浏览器模式（无需密码，自主操作）：**该命令会生成一个仅接收者地址固定的“撰写邮件”内容包（包含`to`/`subject`/`body`字段）。操作员需通过`browser_*`函数在已登录的网页邮箱中**新建一封邮件**，并将`compose.body`中的内容原样粘贴进去（不得添加任何额外信息），之后再发送邮件。该模式不会存储任何凭证，要求操作员使用的浏览器已登录Hermes系统。
2. **程序化模式（使用SMTP凭据）：**该命令会直接通过SMTP发送邮件，无需人工干预。
3. **仅草稿模式作为备用方案：**使用`pdd.py render-email <subject> <broker> --listing <url>`命令生成邮件内容，系统会生成一条摘要信息提示操作员发送邮件，之后代理会将“已提交 --channel email”的状态记录下来。

如果经纪人通过电子邮件发送确认链接，则需按照**验证流程**进行处理。

## 验证流程（针对支持email_verification的经纪人）

- **浏览器模式（自主操作，无需密码）：**在操作员的网页邮箱中打开经纪人发送的确认邮件（通过`browser_*`函数），然后调用`pdd.py verify-link <subject> <broker> --text '<email body>'`命令，即可获取经过反钓鱼评分后的链接。需在同一浏览器中点击该链接（对于PeopleConnect等需要绑定会话的经纪人，需确保打开链接的浏览器与操作流程相关联），完成验证流程后，将状态记录为“等待处理”。
- **程序化模式（使用IMAP）：**`pdd.py poll-verification <subject>`命令会定期查询IMAP账户中所有正在处理的案例，提取其中的链接（仅接受来自经纪人自身域名的、经过反钓鱼评分的链接），并自动将状态从“已提交”更新为“验证待处理”。之后代理会在自己的浏览器中点击该链接，完成验证流程，再将状态记录为“等待处理”。
- **仅草稿模式：**系统会生成摘要信息，提示操作员在当事人的收件箱中点击链接；代理则根据指示将状态记录为“等待处理”。
无论采用哪种方式，当经纪人的处理周期结束后，`pdd.py due`命令会将该案例重新纳入处理队列，以便进行再次扫描；只有经过再次扫描确认信息确实已被删除后，才能标记为`confirmed_removed`。

## 电话回调（例如Whitepages平台）

首先提交网页表单，随后该网站会自动拨打电话并发送一个数字验证码。如果操作员有时间查看验证码，即可记录下来并完成表单填写（流程阶段T2）。否则，则需将该任务放入人工处理队列。

## 电话（语音菜单）/传真/邮件/政府身份证明 → 人工处理任务（流程阶段T3）

**切勿尝试自动化处理此类任务。**应创建一个`todo`任务，并使用`pdd.py record <subject> <broker> human_task_queued`命令进行记录，同时需详细说明处理要求，并明确列出**不得包含的信息**（绝不能包含社会安全号码；除非当事人自行选择并划掉号码，否则也不能包含驾照号码）。当操作员完成处理后，需将确认信息重新录入系统。

## 验证码

**默认设置：软性/可管理的验证码会自动通过验证。**推荐的底层解决方案是Browserbase云浏览器（当设置了`BROWSERBASE_API_KEY`时，`setup --auto`命令会自动选择该浏览器）。由于它是运行在家庭IP地址上的真实浏览器，因此能够正常通过各类管理型验证码——如Cloudflare Turnstile、hCaptcha/reCAPTCHA的勾选式验证——所以使用此类浏览器的经纪人仍属于T1级别，可直接继续处理。这**并非**验证码破解行为：不涉及任何破解服务，也不进行指纹伪装。

只有当浏览器确实无法通过某种**硬性**验证码时（如交互式图像网格、会标记异常会话的行为评分机制），才会采用备用方案：记录为`... blocked`状态，然后重新排队，尝试通过隐秘模式/操作员自有浏览器进行验证（参见`methods.md`中的扫描层级3b——操作员自己的家庭浏览器是可靠的解封方式）。如果未配置云浏览器，使用软性验证码的经纪人将降级为T2级别，需转为人工处理任务。**绝对不要使用任何第三方验证码破解服务。**

### 验证码政策说明（针对经同意的第一方选择退出场景）

- **切勿尝试绕过**行为类/令牌类验证码：如不会自动清除的Cloudflare Turnstile、**DataDome**，以及**“滑动验证”类手势熵验证码**（属于InfoPay处理流程）。这些都是不可逾越的障碍——应选择电子邮件处理路径（遵循上述规则），或直接记录为`blocked`状态。
- **在当事人主动同意的第一方选择退出场景下，可尝试破解**以下类型的验证码：**静态变形文本图像验证码**（可使用视觉识别工具读取），或**简单的算术验证码**（如“8 + 13 = ?”）。这类验证码属于在当事人同意删除信息的前提下进行的OCR识别或算术题测试，而非试图规避机器人检测系统。
- **但是**，如果在该类验证码答对之后，网站仍拒绝处理整个提交请求（显示“验证码验证失败/该功能不可用”等提示），则说明网站是在检测自动化操作本身，而非对答案进行评分——**应立即停止，不要重复尝试**（例如PrivateRecords平台采用的先变形文本验证码再算术题的双重验证机制）。如果不存在相关的权利声明邮件，那就属于真正的`blocked`状态。
