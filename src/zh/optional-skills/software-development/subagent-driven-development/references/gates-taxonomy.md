# 门控分类体系

适用于所有会生成子代理、执行审核循环或需要人工审批暂停的工作流的验证检查点，均采用标准化的门控类型。每个验证检查点都会对应这四种类型之一——明确标注门控类型不仅能提升工作流的可读性，还能避免出现“若该检查失败会怎样？”的困惑。

## 四种门控类型

### 1. 飞行前门控

**用途：** 在开始操作之前验证先决条件是否满足。

**行为：** 若条件不满足，则阻止流程继续执行。不会产生任何部分结果——必须在有任何变化发生之前终止流程。

**恢复方式：** 修正缺失的先决条件，然后重新尝试。

**示例：**
- 实现阶段会在开始编写代码前检查计划文件是否存在。
- 被委托的子代理会在发起 API 调用前确认所需的环境变量已设置。
- 提交代码前会检查测试是否全部通过。

### 2. 修订门控

**用途：** 评估输出质量，若质量不足则引导流程进入修订环节。

**行为：** 向任务生成者反馈具体问题，并让其重新处理。该循环通常有最大迭代次数限制（一般为3次）。

**恢复方式：** 任务生成者根据反馈修正问题后，检查者会重新进行评估。如果连续多次迭代后问题数量仍未减少，则会提前触发升级流程（即检测到流程停滞）。达到最大迭代次数后，无论情况如何都会无条件将问题升级给用户——绝不会无限循环。

**示例：**
- 计划审核者阅读草拟计划，指出具体问题，规划者进行修改，审核者再次阅读（最多3轮）。
- 代码审核者检查子代理生成的代码是否符合基本要求；如果有任何基本要求未满足，则将修正任务发回给实现者。
- 测试覆盖率检查工具会验证新测试是否覆盖了所有新路径；如果没有，则将问题反馈给代码编写者。

### 3. 升级门控

**用途：** 将无法解决的问题提交给人工决策。

**行为：** 暂停工作流，列出可选方案，等待人工输入。绝不自行猜测，也绝不默认选择某个方案。

**恢复方式：** 由人工决定处理方案，工作流再沿选定的路径继续执行。

**示例：**
- 经过3次迭代后，修订循环仍无法解决问题。
- 自动化工作树清理过程中出现合并冲突。
- 需求表述模糊——存在两种合理的解读，且不同的选择会导致完全不同的处理方式。
- 子代理报告“计划中规定的是X，但实际代码库却是Y”——需要由人工判断哪种是正确的。

### 4. 中止门控

**用途：** 终止当前操作，以避免造成损害或资源浪费。

**行为：** 立即停止流程，保留当前状态（即检查点的进度），并说明具体的终止原因。

**恢复方式：** 由人工调查根本原因并解决问题后，从检查点处重新启动流程。

**示例：**
- 执行过程中上下文窗口使用率严重偏低（处于“差”级别，超过70%）——应干净地中止流程，而非生成不完整的输出。
- 运行过程中关键依赖项不可用（网络中断、API密钥被撤销）。
- 文件系统状态已无法恢复（磁盘已满、权限丢失）。
- 违反了安全约束条件（代理尝试在授权范围之外执行不可逆的破坏性操作）。

## 如何在技能中应用此分类体系

当你编写包含验证检查点的编排技能时，**需为每个检查点明确标注其所属的门控类型**，并回答以下三个问题：

1. **是什么条件触发了该门控？**（例如：“计划文件缺失”、“问题数量未减少”、“上下文使用率超过70%”）
2. **若该门控触发失败，将会发生什么？**（阻止执行/循环处理/请求人工决策/中止流程）
3. **由谁来继续执行流程，从哪个节点开始？**（修正先决条件后重新尝试、修改内容后再次检查、由人工决策、从检查点处重新启动）

提前明确回答这三个问题，就能确保你的技能在运行时不会出现“现在该怎么做？”的困惑。

## 示例——包含全部四种门控类型的审核循环

```
[Pre-flight] plan.md exists and is non-empty?   → no: bail, ask user to write a plan first
                ↓ yes
[Execute]  subagent implements task
                ↓
[Revision] reviewer checks against must-haves  → fail: loop back to subagent (max 3)
                ↓ pass
[Pre-flight] tests pass?                       → no: bail, report failing tests
                ↓ yes
[Commit]
                ↓
(on revision loop exhaustion)
[Escalation] "3 review cycles failed to converge on issue X — pick: force-merge, rewrite task, abandon"
                ↓ user picks
(on any tier-POOR context pressure during loop)
[Abort] "context at 73%, checkpointing and stopping"
```

该词汇表被刻意设计得较为精简。每个工作流中的每一个审核节点都应归属于这四类之一。如果您发现自己需要新增第五类节点，那很可能是带有额外分支的修订审核节点，或是伪装起来的升级审核节点。
