# Hermes 成就功能性能提升实施计划

状态：黑客松评审期结束后即可启动执行  
约束条件：在评审完成前，相关插件暂不可修改  
决策：`/overview` 页面及顶部横幅区域不在本次优化范围内，将被移除。

---

## 第 0 阶段 — 基线与安全性保障（无功能变更）

### 任务 0.1：添加性能基准测试脚本（本地运行）
目标：复现功能升级前后的性能基线数据。

验收标准：
- 能够输出 `/achievements` 接口的响应时间（需分别进行冷启动和热启动状态下的 3 次测试）。

### 任务 0.2：明确性能验收阈值
目标：提前确定功能成功的判定标准。

验收标准：
- 需明确文档化的服务等级指标（SLO）：
  - `/achievements` 接口的 p95 响应时间需小于 1 秒（基于缓存情况）
  - 同时运行的扫描任务数量最多为 1 个

---

## 第 1 阶段 — 移除未使用的页面与功能模块（确定性最高）

### 任务 1.1：移除 `/overview` 后端路由
目标：消除重复存在的、性能开销较大的接口路径。

验收标准：
- `plugin_api.py` 文件中不再包含 `/overview` 的相关实现。

### 任务 1.2：移除功能模块注册代码及 SummarySlot 前端逻辑
目标：取消跨标签页获取横幅信息的功能。

验收标准：
- 不再出现 `registerSlot(..."sessions:top"...)` 或 `registerSlot(..."analytics:top"...)` 这类调用。
- 前端也不再发起对 `api("/overview")` 的请求。

### 任务 1.3：更新插件清单文件
目标：反映最终的界面功能范围。

验收标准：
- `manifest.json` 文件中将删除所有与功能模块相关的声明。
- 各标签页的注册信息保持不变。

---

## 第 2 阶段 — 实现共享快照机制 + 统一处理 `/achievements` 请求

### 任务 2.1：引入快照存储抽象层 + 磁盘持久化机制
目标：为成就数据建立唯一可信的数据源，确保进程重启后数据不会丢失。

验收标准：
- 所有 `/achievements` 功能所需的数据都将存储在统一的结构中。
- 当缓存有效时，重复请求无需重新计算数据。
- 快照文件将保存在 `~/.hermes/plugins/hermes-achievements/scan_snapshot.json` 路径下。

### 任务 2.2：实现单次计算协调机制
目标：防止多个请求同时触发重复计算。

验收标准：
- 即使收到多个同步请求，也只会执行一次数据计算。

### 任务 2.3：重构 `/achievements` 功能，使其直接读取快照
目标：从请求处理流程中去除重复的计算操作。

验收标准：
- 当缓存有效时，`/achievements` 接口不会为每个请求都独立触发完整的数据计算。

---

## 第 3 阶段 — 实现“先返回旧数据，后台同步更新”机制

### 任务 3.1：引入过期状态标识（`FRESH`/`STALE`）
目标：当数据过期时立即返回现有缓存结果，同时在后台异步刷新数据。

验收标准：
- 即使缓存数据已过期，也能快速返回缓存结果。
- 数据刷新为异步操作。

### 任务 3.2：可选：添加 `scan-status` 接口
目标：让界面操作人员及运维人员能够查看扫描任务的当前状态。

验收标准：
- 该接口需返回扫描状态、上次成功时间、上次运行时长以及上次出现的错误信息。

### 任务 3.3：为 `/achievements` 接口的响应添加元数据字段
目标：提升功能的透明度。

验收标准：
- 响应结果中需包含 `generated_at`（生成时间）、`is_stale`（是否过期）字段，可选地还可包含 `scan_id`（扫描任务标识）。

---

## 第 4 阶段 — 实现增量扫描功能（非必需但推荐）

### 任务 4.1：为每个会话添加检查点文件
目标：不仅能记录整体扫描耗时，还能追踪单个会话内的变化情况。

验收标准：
- 检查点文件将保存在 `~/.hermes/plugins/hermes-achievements/scan_checkpoint.json` 路径下。
- 每个会话的检查点信息需包含 `session_id`（会话标识）、指纹信息（由 `updated_at`、消息数量和哈希值组成）以及该会话的缓存贡献数据。

### 任务 4.2：实现增量聚合计算
目标：仅对发生变化的会话重新计算数据，已不变的会话则直接复用之前的计算结果。

验收标准：
- 数据刷新所需的时间将显著短于完整扫描所需的时间。
- 在重新生成汇总数据时，只需减去旧会话的贡献值，再加上新会话的贡献值即可。

### 任务 4.3：保留完整重新扫描的备用方案
目标：确保功能的正确性始终得到保障。

验收标准：
- 始终可以手动触发完整的重新扫描操作。
- 如果接口的架构或版本发生变更，原有的检查点文件将失效，系统会强制进行完整重建。

---

## 测试计划

1. 单元测试
- 验证快照的生命周期转换逻辑
- 测试在高并发请求下的去重功能表现
- 检查 `/achievements` 接口在不同场景下的响应一致性

2. 集成测试
- 验证频繁打开成就页面时，最多只会触发 1 次高负载扫描任务
- 确认 `/achievements` 接口在热缓存状态下的加载速度足够快
- 验证手动重新扫描功能能否正确更新快照及时间戳信息

3. 手动性能测试
- 使用相同的历史数据集，对比功能升级前后的 `/achievements` 接口响应时间

---

## 上线计划

1. 先发布包含第 1 阶段功能（移除 /overview 页面及相关功能模块）的内部分支。
2. 验证成就页面的功能没有出现任何退化问题。
3. 接着添加第 2 阶段实现的快照存储与去重功能。
4. 随后加入第 3 阶段的功能，包括“先返回旧数据，后台同步更新”机制以及状态元数据展示功能。
5. 可选：后续可进一步添加增量扫描功能。

回滚方案：在某个版本发布周期内，可通过临时特性开关保留原有的计算逻辑，以便在出现问题时立即回退。

---

## 完成标准

- 成就页面的所有功能均保持正常运行（包括计数显示、最新数据展示、等级划分、卡片展示及过滤功能等）。
- 系统中不再存在 `/overview` 接口或相关功能模块的调用代码。
- 在热缓存有效的情况下，多次加载成就页面的响应速度都非常快。
- 相关指标及功能解锁规则与初始基线保持一致，没有发生变化。
